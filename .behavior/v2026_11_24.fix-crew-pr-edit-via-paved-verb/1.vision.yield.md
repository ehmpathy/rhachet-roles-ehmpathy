# 1.vision: a driver that edits an extant pr finds the paved verb

## .what this builds

two edits, one file: `git.commit.push.sh`.

**1. a `--help` section** that names the two paved pr edit verbs and when to reach for each:

```
usage: git.commit.push [--mode plan|apply] [--auth as-ehmpath|as-human] [--output tree|json] [--pr-title-fallback "..."] [--debug]

options:
  ...                          (unchanged)

to edit the pr after it is open:
  push opens the pr once; it never rewrites an extant pr's title or body
  rhx git.pull.title set --from <path|@stdin>         when the scope outgrew the title
  rhx git.pull.description set --from <path|@stdin>   when the body no longer tells the work
  each plans first; add --mode apply to write
  never raw `gh` to edit a pr: the paved verbs write under the credential that opened it, and sign the body
```

**2. one header line** in the same file's `guarantee:` block (fulcrum F3):

```
#   - never rewrites an extant pr; edit it via git.pull.title set / git.pull.description set
```

the header boots as `say` in every mechanic session (`boot.yml:69`). the `git.pull.*` verbs boot as `ref`, name only (`boot.yml:134-136`). so the header line reaches every driver at session start, whichever verb it pushes with.

an integration test clamps the help: push `[case31]` asserts `--help` stdout contains both verb names, and its snapshot records the full text. red without the section, green with it.

## .why it works

- **the driver reads what it already holds.** every mechanic boots the push header; a driver that wants the detail opens the push `--help`. a pointer in both reaches it at no extra search cost
- **the help states the gap.** push findserts the pr (`git.commit.push.sh:683-690`): a found pr keeps its title and body. one line says so. the driver learns push cannot do the edit, and why a second verb exists
- **each verb names its trigger.** "scope outgrew the title" and "body no longer tells the work" match the moment a driver feels the need. recognition over recall (`rule.require.discoverability`)
- **the paved verbs fit the incident's pr.** ahbode/svc-protools#128 was opened by `ehm-seaturtle`. `git.pull.description set` writes any pull its own credential opened (`git.pull.operations.sh:195-206`). on a current install, the verb works and only the pointer is absent (`rhx git.commit.push --help`, run live)
- **precedent.** a `ref` verb named by a `say` verb's surface is how this repo already surfaces `git.branch.cutover` (`boot.yml:115`)

## .the outcome world

**before.** a driver on svc-protools grew its route past the first commit. the pr body went stale. it pushed again; push found the pr and left the body as-is. its install (`rhachet-roles-ehmpathy@1.39.5`) held no verb to edit a pr, so it rewrote the body with raw `gh`. the body lost its seaturtle footer. on a current install the verbs exist (since v1.41.0), but push's help and header still never name them: the next driver walks the same path.

**after.** the same driver recalls from its boot that push never rewrites an extant pr, and that `git.pull.description set` does. for the flags, it opens `rhx git.commit.push --help`. it writes the body to `./.temp/body.md`, runs `rhx git.pull.description set --from ./.temp/body.md`, reads the plan, then `--mode apply`. the body lands under seaturtle, signed once.

**the aha.** push is a findsert, not a sync. the line that says so sends the driver to the right verb.

## .mental model

- a driver to a peer: *"push only opens the pr. to change it after, use the git.pull verbs."*
- analogy: push is the mail slot; it drops the letter once. to amend the letter, use your own pen (`git.pull.* set`), not a pen from the human's desk (raw `gh` under the human's login)
- their words vs ours: they say "edit the pr", "update the pr description". we say `git.pull.description set`. the help bridges both: it opens with "to edit the pr", then names the verb

## .evaluation

| goal (from the wish) | met by |
|---|---|
| `git.commit.push --help` names both verbs + when | the new section |
| a test clamps it, red without, green with | `toContain` on both verb names in push `[case31]`, plus the snapshot |
| a pr, `git.release --watch` green | execution + verification stones |

pros
- one file; one test case extended; no contract change; no new flag
- reuses verbs that already enforce ownership, signature, plan/apply, secret refusal

cons
- help is pull, not push: a driver that skims its boot and never opens `--help` sees only the header line. the deny hint on `gh pr edit` is the later net (c12)
- the header line is unclamped unless the blueprint adds a check; a boot snapshot or a grep test would hold it

edgecases + pit of success
- pr opened under the human's login → `git.pull.description set` refuses, exit 2, and names the rerun under `--auth as-human` (case=3). no write under the wrong identity
- no pr yet → the help says push opens it. the edit verbs default to the open pull of the cwd branch and refuse loud when none: `--which is absent, and branch '<b>' has no open pull` (`git.pull.comment.operations.sh:648-671`, shared by the `git.pull.*` family)
- body holds a secret or is empty → the paved verb refuses before any write (`git.pull.description.set.sh:103-107`)

## .what is awkward

- a pointer is a cue, not a guard. the guard already exists: the mechanic deny on `gh pr edit` names both verbs. the cue earns its place as the earlier net, but it does not close a bypass via `gh api`
- the section names verbs of another family (`git.pull.*`) inside `git.commit.*` help. that crosses a boundary on purpose: push is where the pr is born, so it is where the driver looks
- this fix would not have saved #128 by itself: that install predates the verbs. it saves the next driver on a current install
