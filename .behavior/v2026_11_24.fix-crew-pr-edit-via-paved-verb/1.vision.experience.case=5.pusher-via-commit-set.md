# case=5: a driver that pushes via git.commit.set --push

feel: happy · care: critipath · cell c10

## .narrative

most drivers never call `git.commit.push` by name. the paved pattern is `git.commit.set -m @stdin --mode apply --push`, which composes push. `git.commit.set --help` names no `git.pull` verb. but every mechanic session boots the push header as `say`, and its `guarantee:` block now reads: never rewrites an extant pr; edit it via `git.pull.title set` / `git.pull.description set`. the driver that wants to refresh its pr body names the verb from that boot line — it never opens push's or set's help. for the verb's own flags it reads `rhx git.pull.description set --help`, then walks case=1.

## .bdd sketch

```
given a driver that commits + pushes via `git.commit.set --push`, in a session whose boot holds the git.commit.push.sh header, and its pr body is stale
  when [t0] the driver recalls its boot context to find a pr edit verb
    then the driver reads `git.pull.title set` and `git.pull.description set` in the push header
    then the driver picks `rhx git.pull.description set`; it reads neither push's nor set's `--help`
  when [t1] the driver runs `rhx git.pull.description set --help`
    then stdout lists `--from <path|@stdin>`, `--mode plan|apply`, and an example
  when [t2] the driver runs `rhx git.pull.description set --from ./.temp/body.md`, then adds `--mode apply`
    then the walk proceeds as case=1 [t2]-[t3]
```
