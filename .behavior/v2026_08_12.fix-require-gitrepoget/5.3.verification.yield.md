### the installed gate then FAILED OPEN on a file-mode bit — FIXED

installed is not the same as effective. immediately after the install above, a rebuild made the
gate stop to block again — silently, with the registration still present in
`.claude/settings.json`.

the trace, in order: registration present → `diff src dist` identical → direct invoke returns

```
/bin/bash: line 1: …/pretooluse.forbid-cross-repo-access.sh: Permission denied
```

`git ls-files -s` settles it: every one of the 14 shipped hooks is mode `100755`. mine was
`100644`, because a file authored by the Write tool is born without the execute bit. and
`build:complete:dist` copies with `rsync -a`, which **preserves** mode — so a 644 source ships
a 644 hook.

**the severity is the direction of the failure.** claude code blocks a tool call only on
exit 2; any other outcome — a non-executable hook among them — is read as allow. so the gate
did not fail loudly, it failed **open**, which is the precise hazard the wish exists to
remove. a gate that cannot run is indistinguishable from a gate that approved you.

- **fix** — at the layer that governs what ships, not the one file:

  ```json
  "build:complete:exec": "find dist -type f -name '*.sh' -exec chmod +x {} +",
  ```

  wired into `build:complete` between `:dist` and `:repo`
- **why there, not on the one file** — `chmod` on the source was denied to me, but the deeper
  reason is `rule.require.solve-at-cause`. the true invariant is *"every `.sh` we ship must be
  executable"*, and to leave it to each author's file mode is exactly the fragility that let
  this through. the build now holds the invariant for every hook and skill, present and future
  (`rule.prefer.prevent-over-correct`: make the error impossible rather than message it)
- **blast radius: none.** the 14 extant hooks are already `755`, so the step is a no-op for
  every current file; it changes only files that would otherwise have shipped broken. the
  `.jsonc` data files are correctly untouched — the filter is `-name '*.sh'`
- **proof** — `tree -pf dist/…/claude.hooks` now shows
  `[-rwxrwxr-x] pretooluse.forbid-cross-repo-access.sh`; the live `Read` of a peer repo returns
  `🛑 BLOCKED: adhoc cross-repo access — Read`; the printed fix line runs verbatim and yields
  `found: 1 file`; the hook suite is `48 passed, 0 failed`; format and lint stay green
- **the residual gap widens fulcrum #3.** two seams past "the tests pass" now have no automated
  guard: the gate must be *registered* (`.claude/settings.json`) and it must be *executable*.
  both are config/artifact state rather than behavior, and both fail open. the build step closes
  the second one by construction; the first is still a note

**the lesson worth a place in memory:** i verified this gate at three layers and all three were
green while it was inert — twice, for two unrelated reasons. behavior tests prove the code is
right; they cannot prove the artifact is wired and runnable. for a fail-open guardrail, the only
sufficient proof is a live runthrough against the real harness.

the obvious reads are both wrong.

- it is **not a regression**: `git diff main` on that file is empty. the branch never touched it.
- it is **not a flaky test**: the design is deliberate. `REPEATABLY_CONFIG_LLM` declares
  `attempts: 3, criteria: process.env.CI || process.env.LOCALLY ? 'SOME' : 'EVERY'`, with the
  note "LLM outputs are probabilistic; test mode uses SOME (any 1 of 3)".

the cause is env, not code: a local `rhx git.repo.test` run sets neither `CI` nor `LOCALLY`,
so the suite degrades to `EVERY` — all 3 attempts of a probabilistic classifier must block.
CI sets `CI` itself, so CI runs at the intended tolerance and this case does not gate it.

**left on record, not fixed.** the one-line change (have `git.repo.test` export `LOCALLY` for
local runs) sits in a shared runner every role uses, and outside this wish's bound (cross-repo
access + `--tree`). the assertion itself must NOT be loosened — that would change what the test
verifies rather than why it failed. flagged for the wisher.

## i019 — the fulcrum ruled, and two of its three premises disproven

the wisher ruled **no escape hatch** (2026-08-16), and asked whether untracked files should be
served, clearly labeled. the answer turned out to be that they already are — which also
corrects the vision, where I had overstated the gap the hatch was weighed against.

### what the code actually does, verified live

| mode | tracked | untracked | gitignored |
|------|---------|-----------|------------|
| default (`origin/main`) | ✅ | ❌ | ❌ |
| `--tree <name>` | ✅ | **✅ already** | ❌ (deliberate) |

`--tree` enumerates through `ls-files --cached --others --exclude-standard`, so a brand-new
file that lives in no ref at all is listed, searched, and read — under `tree: <name>
(inflight)`. no new labels or render work were needed: the tree-level label already tells a
reader the whole set is un-latest.

**`--tree` is also not worktree-only.** it resolves any local tree of the selected repo, the
repo's own main clone among them (`--tree main`). verified live — and, fittingly, discovered
because the cross-repo hook built by this very wish blocked my own `cd` into a neighbor clone
and its message named `--tree main` as the fix.

so two of the three pressures behind the hatch never existed:

| premise for the hatch | verdict |
|---|---|
| untracked files unreachable | **false** — `--tree` serves them |
| a peer clone's dirty state unreachable | **false** — `--tree main` serves it |
| gitignored + binaries unreachable | **true**, and gitignored is a deliberate refusal in all three modes, not an oversight |

gitignored is a guarantee rather than a gap: the file list passes `--exclude-standard`, the
search passes `--untracked`, and read mode checks `check-ignore`, precisely so the quiet mode
cannot become the way around the other two — one flag, one sense.

### the one real gap: read mode's untracked path had no clamp

case31 covered the file LIST and the SEARCH of an untracked file (t0), its absence without
`--tree` (t1), and read mode's refusal of a gitignored file (t2). the positive case between
them was unpinned: read mode that serves an untracked-but-not-ignored file's CONTENT.

that is the whole reason a caller reaches for `--tree`, so a regression that made read mode
index-only would have defeated the flag while t0 and t2 both stayed green.

**case31 t3 added, clamp proven to bite**: with read mode tightened to `ls-files
--error-unmatch` (the exact regression it guards) → **1 failed, and only t3** — the other
three stayed green, as predicted. probe reverted → **4 passed**.

### i020b: the two boundaries the audit found unclamped

the coverage audit turned up exactly two gaps. both are now clamped, and both clamps were
proven to bite (`rule.require.clamp-edge-cases`).

**case34 t3 — a symlink escape.** t0 and t1 both escape *lexically*: a `../` segment and a
`/` at the front are visible in the string itself, so a naive prefix compare catches them
and looks sufficient. a symlink escapes only once the filesystem expands it — which is why
`is_path_within_tree` uses `realpath -m` and not a string compare. no case proved that.

- probe: `realpath -m` → `realpath -m -s` (lexical only, no symlink expansion)
- **RED, and loudly**: the skill printed `TOPSECRET-do-not-leak` from outside the tree —
  a real host-file leak through the one tool every cross-repo read is redirected to
- only t3 failed; t0/t1/t2 stayed green, confirming t3 is the sole cover for this boundary
- probe reverted → green

**case42 — a binary read through `--tree`.** the `--tree` read is the ONE content path that
reads raw bytes off disk; every other path asks git, which refuses binary itself (`git grep`
answers "Binary file X matches" rather than print the bytes). so read-through-tree was the
sole mode that could hand a terminal a stream of control bytes dressed as source lines.

worse than ugly, it was UNTRUE: the read is `content=$(cat ...)`, and a command substitution
silently drops every NUL byte — so the render was not the file on disk, with no signal that
bytes went absent (`rule.forbid.failhide`).

- this one was a **defect, not just a gap**: written to expect exit 2, the case went RED at
  exit 0 — the binary read straight through
- fixed with `is_file_binary` (a NUL in the first 8000 bytes — git's own `buffer_is_binary`
  test), which refuses up front and names the file-list alternative
- t1 pins that the guard is not over-broad: normal text in the same tree still reads
