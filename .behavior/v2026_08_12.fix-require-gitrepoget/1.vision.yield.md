# 1.vision — forbid adhoc cross-repo access; mandate git.repo.get

> wish: forbid adhoc access to cross-repo `~/git/*` paths; mandate `git.repo.get` to read
> cross-repo, so callers always look at latest. also verify we support worktree access via a
> `--tree` arg, so they can peek at inflight work too.

---

## the outcome world

### day-in-the-life

a mechanic is working in `~/git/ehmpathy/rhachet-roles-ehmpathy` and wants to see how
`DomainEntity` is declared in a sibling repo, `ehmpathy/domain-objects`.

**before** (today): the mechanic reaches straight into the other clone —

```
Read ~/git/ehmpathy/domain-objects/src/index.ts
Grep "DomainEntity" ~/git/ehmpathy/domain-objects/
```

this "works", but it silently reads whatever happens to be checked out in that clone: a
stale branch from three weeks ago, a half-finished experiment, a dirty working tree. the
mechanic has no idea. they reason about code that does not match `origin/main`, and draw
wrong conclusions.

**after** (this wish): the same reach is stopped at the door —

```
Read ~/git/ehmpathy/domain-objects/src/index.ts
🛑 BLOCKED: adhoc read of a cross-repo path

  ~/git/ehmpathy/domain-objects is a different repo than your current one.
  its working tree may be stale or dirty — reading it directly is a trap.

  use git.repo.get instead (always reads origin/main, the latest):
    rhx git.repo.get lines --in ehmpathy/domain-objects --paths 'src/index.ts'

  to peek at that repo's inflight worktree work:
    rhx git.repo.get lines --in ehmpathy/domain-objects --tree <branch> --paths 'src/index.ts'
```

the mechanic runs the suggested command, gets the **latest committed** `src/index.ts`, and
reasons about reality.

### before/after contrast

| dimension | before | after |
|-----------|--------|-------|
| what you read | whatever is checked out in the other clone | `origin/main` (latest), by default |
| staleness risk | invisible — no signal the clone is behind | absent — the ref is explicit in every output |
| dirty-tree risk | invisible — you might read a half-edit | absent — committed state only, unless you opt into `--tree` |
| inflight peek | reach into a worktree dir by hand, hope you found it | first-class `--tree <name>` with a labeled ref |
| current repo | reach freely | reach freely — unchanged |

### the "aha" moment

the value clicks the first time the block fires on a path the mechanic *thought* was
current. "wait — that clone was on a feature branch, i'd have read the wrong thing." the
guardrail converts a silent, invisible class of wrong-conclusion bugs into a loud, one-line
redirect. the pit of success: the easy path (git.repo.get) is now the *only* path, and it is
correct by construction.

## user experience

### usecases / goals

1. **read one file** from another repo at latest → `git.repo.get lines --in <slug> --paths <file>`
2. **search** another repo (or org) at latest → `git.repo.get lines --in <slug> --words <pat>`
3. **list files** in another repo at latest → `git.repo.get files --in <slug>`
4. **peek at inflight work** in another repo's worktree → same commands `+ --tree <name>`
5. **work in the current repo** → unchanged; adhoc Read/Grep/Glob still free

### contract inputs & outputs

**enforcement (part 1)** — a new `PreToolUse` hook, `pretooluse.forbid-cross-repo-reads`:

- **input**: the tool-call JSON on stdin (`tool_name`, `tool_input.file_path` for
  Read/Edit/Write, `tool_input.path` + `pattern` for Grep/Glob, `tool_input.command` for
  Bash).
- **decision**: resolve the target path. if it lands under `~/git/` (i.e. `$GIT_REPO_ROOT`)
  but **outside the current repo root** (cwd's toplevel), block with exit 2 + guidance.
  otherwise allow (exit 0).
- **output**: on block, a turtle-flavored stderr message naming the offending path and the
  exact `git.repo.get` command to run instead.

**`--tree` (part 2)** — a new flag on `git.repo.get`:

- **composes with the normal repo selector** (wisher-confirmed, 2026-08-12): `--tree` is a
  modifier on top of the usual `--in <org/repo>` (or `--repos`) selection — it works for any
  repo, exactly like a normal cross-repo query. it simply lets the caller prescribe a specific
  **local worktree** of that already-selected repo instead of its committed `origin/main`.
  e.g. `--in ehmpathy/domain-objects --tree feat/new-refs`.
- **input**: `--tree <name>` where `<name>` identifies a local worktree of the selected repo
  (best guess: the branch/slug, looked up via `git worktree list`).
- **effect**: instead of committed `origin/main`, read the worktree's **live files on disk** —
  inflight, uncommitted edits included (wisher-confirmed scope).
- **local-only**: worktrees exist only in local clones, so `--tree` requires a local clone of
  the selected repo; on a cloud-only repo it fails loud.
- **output**: same tree format, but the `ref:` line reads `tree: <name> (inflight)` so the
  reader always knows they are looking at un-latest, un-committed state.

Read ~/git/ehmpathy/domain-objects/src/index.ts

### timelines

- **T0** — mechanic issues a cross-repo Read/Grep/Glob.
- **T1** — hook resolves the path, sees it is another repo under `~/git`, blocks (exit 2).
- **T2** — mechanic reads the one-line redirect, runs `git.repo.get`.
- **T3** — mechanic gets latest committed state (or `--tree` inflight), reasons correctly.

for the current repo, T0 → done. no interception.

## mental model

### how a user describes it to a friend

> "you can't peek into your neighbor's garage and assume you saw their finished car — the
> stuff in there might be half-built or last year's model. if you want to know what they
> actually shipped, you ask through the front door (`git.repo.get`), and you always get the
> latest. if you specifically want to see what they're building *right now*, you say `--tree`
> and they show you the workbench, clearly labeled 'work in progress'."

### analogies / metaphors

- **the front door vs the side window** — `git.repo.get` is the front door (latest, greeted,
  labeled); adhoc reach is climbing through a side window (you might grab anything).
- **published vs draft** — `origin/main` is the published edition; `--tree` is the author's
  draft, clearly stamped so you never mistake it for print.
- **the sea turtle** — you stay in the water (the sanctioned flow) instead of crawling onto
  dry land (a stale foreign clone). 🐢

### terms: theirs vs ours

| user says | we say |
|-----------|--------|
| "another repo" | cross-repo target (outside the current repo root) |
| "my repo" | current repo (cwd toplevel) |
| "the latest" | `origin/main` (the default ref) |
| "work in progress" / "inflight" | worktree working-tree state (via `--tree`) |
| "the ~/git folder" | `$GIT_REPO_ROOT` (default `$HOME/git`) |

## evaluation

### how well it solves the goals

- **"always look at latest"** — fully solved for the sanctioned path: `git.repo.get` already
  fetches `origin` and reads `origin/main` (`git.repo.get.operations.sh:105` `refresh_local_repo`,
  `:161` `get_default_branch`). the new hook closes the *only* bypass (adhoc Read/Grep/Glob),
  which is currently ungated.
- **"peek at inflight"** — solved by `--tree`, with a loud label so inflight is never confused
  with latest.

### pros

- converts an invisible failure mode (stale/dirty cross-repo reads) into a loud redirect.
- one obvious way to read cross-repo → less drift, consistent output, easy to review.
- current-repo ergonomics untouched — no friction where it is not needed.
- reuses an extant, tested skill; `--tree` is an additive flag, not a rewrite.

### cons / costs

- **friction** on legitimate cross-repo reads: a mechanic who *knew* the clone was current
  now takes an extra step. mitigated by the copy-paste redirect.
- **hook must be precise**: false-positives (blocking current-repo reads) would be
  infuriating; false-negatives (missing a bypass) would leak. the current-repo boundary must
  be computed correctly (see edgecases).
- **`--tree` reads uncommitted state** — intentionally un-latest; the label must be
  unmissable or it defeats the wish's own "always latest" guarantee.
- **git.repo.get serves only NON-IGNORED files** — narrower than it first appeared, and the
  correction matters. the default (`origin/main`) path reads via git refs (`git show`,
  `git ls-tree`), so it serves committed files only. but `--tree` reads the filesystem
  through `ls-files --cached --others --exclude-standard`, so it serves **untracked files
  too** — a brand-new file that lives in no ref at all is listed, searched, and read, under
  the `tree: <name> (inflight)` label.
  so the true leftovers are two, not three: a **gitignored** file (a `.env`-style scratch, a
  `dist/` output) and a **binary**. gitignored is refused deliberately and identically in all
  three modes — the file list passes `--exclude-standard`, the search passes `--untracked`,
  and read mode checks `check-ignore` — precisely so the quiet mode cannot become the way
  around the other two. that is a guarantee, not a gap.
  **verified 2026-08-16**, live against a real repo and pinned by case31 t0/t2/t3.
- **the "always latest" premise is sometimes the wrong goal — and `--tree` already answers
  it.** when a caller debugs *why a peer clone behaves as it does on disk right now*, they
  need that clone's actual checked-out (possibly dirty) state. `origin/main` hides it, but
  `--tree` does NOT only target worktrees: it resolves any local tree of the selected repo,
  the repo's own main clone among them (`--tree main`), and reads the live files on disk.
  the earlier read here — that no mode could serve this — was wrong; the usecase is covered.
  **verified 2026-08-16** by a live `--tree main` read of a neighbor repo's checked-out tree.
- **latency / fetch cost.** `git.repo.get` runs `git fetch origin` on every call
  (`operations.sh:105`). a flow that makes many cross-repo reads pays a network round-trip
  each time, and may hit remote rate limits. `--refresh off` avoids it but forfeits the
  "latest" guarantee — a direct tension between the wish's guarantee and its ergonomics.

### edgecases & pit-of-success

| edgecase | hazard | how the contract keeps you safe |
|----------|--------|--------------------------------|
| working in a **worktree** of repo X, read the **main clone** of X | is that "cross-repo"? same repo, different tree | best-guess: treat same-repo-other-tree as allowed *only* via `--tree`; a raw reach is blocked and redirected. **fulcrum — see open questions** |
| read your **own** current repo under `~/git` | must not block | allow: path is under cwd toplevel |
| `node_modules`, `.agent/` symlinks pointing outside repo | could resolve to another `~/git` path | resolve symlinks before the boundary check; allowlist in-repo `node_modules` |
| Bash `cat ~/git/other/repo/file` | already gated by check-permissions? no — `cat` is allow-listed as a prefix | the new hook must also inspect Bash commands for cross-repo paths (like forbid-tmp-writes does) |
| `--tree` name matches no worktree | silent wrong read | fail loud: "no worktree named X; run `git worktree list`" |
| `--tree` on a **cloud** (non-local) repo | worktrees are local-only | fail loud: "--tree requires a local clone" |
| repo lives outside `~/git` (custom `GIT_REPO_ROOT`) | boundary math wrong | honor `$GIT_REPO_ROOT`, same var `git.repo.get` uses (`get_git_root`, `operations.sh:17`) |
| blocked path is inside a **worktree** (`~/git/<org>/_worktrees/<repo>.x/...`) | naive slug derivation would emit `--in <org>/_worktrees` (wrong) | the redirect's `--in <org>/<repo>` slug derivation assumes `$GIT_REPO_ROOT/<org>/<repo>/<file>`; a worktree path breaks that mapping. derive the true repo slug from the worktree's own git metadata, not the path segments |

## open questions & assumptions

### assumptions

1. **"current repo" = cwd's git toplevel.** any path under it is allowed; any other path
   under `$GIT_REPO_ROOT` is cross-repo. (needs the hook to compute toplevel reliably, incl.
   from within a worktree.)
2. **enforcement targets Read, Grep, Glob, Edit, Write, Bash.** Read/Grep/Glob are the
   ungated loophole; Edit/Write to another repo should also be blocked (you should never
   mutate a sibling clone). Bash needs command-string inspection like forbid-tmp-writes.
3. **`--tree` reads the worktree working directory** (true inflight, incl. uncommitted), not
   just the worktree's HEAD commit. "peek at inflight work" implies uncommitted.
4. **worktree identity = branch/slug**, looked up via `git worktree list` against the target
   repo. the layout `~/git/<org>/_worktrees/<repo>.<user>.<slug>` is an **observed sample
   (my own cwd), NOT a guaranteed convention** — `git worktree add` can place a worktree at
   any path, even outside `$GIT_REPO_ROOT`. two consequences the design must honor:
   - `--tree` MUST look up the worktree via `git worktree list` on the target repo, never by a
     path pattern. a pattern would miss worktrees placed elsewhere.
   - the hook gates only paths under `$GIT_REPO_ROOT`; a worktree placed **outside** it is
     ungated — an accepted blind spot (reaching a random out-of-root path is not the "cross
     `~/git` repo" case the wish targets), but worth stating plainly.

### questions for the wisher (fulcrums — best-guessed, flagged for the end)

> **triage: all six below are [wisher]** — each turns on the wisher's intent or a scope
> preference that logic and code cannot settle. all but #0 carry a best-guess clean enough to
> drive on now and confirm at the end; **#0 is the one worth an explicit ask up front**, since
> a wrong guess there builds a redundant flag.

0. **[resolved by wisher] "inflight" INCLUDES uncommitted edits.** the wisher confirmed
   (2026-08-12): inflight covers **uncommitted** worktree state, not just committed-but-unmerged
   commits. that state lives in no ref, so `--ref` cannot reach it — therefore `--tree` earns
   its place and is warranted (my best-guess held). `--tree` must read the worktree's live
   files on disk (uncommitted edits included), not merely its HEAD commit.
1. **same-repo, other-tree reads** — when I'm in a worktree of repo X and reach into X's main
   clone (or another worktree of X), is that "cross-repo"? **best guess:** yes, block it and
   require `--tree`, because the *other* tree can still be stale/dirty relative to what you
   want. clean to reverse (loosen the boundary) later.
2. **`--tree` argument shape** — does `<name>` mean the branch, the worktree dir name, or the
   user-slug? **best guess:** branch name, resolved via `git worktree list`; fall back to
   dir-name match. clean to adjust.
3. **Edit/Write to cross-repo** — block outright, or allow (some flows legitimately scaffold a
   sibling)? **best guess:** block; mutating another clone by hand is never the sanctioned
   path. clean to carve exceptions.
4. **[resolved by wisher, 2026-08-16] NO escape hatch.** the redirect is mandatory; there is
   no opt-out env var or flag. the guarantee is worth more than the rare adhoc read, and a
   hatch would dilute it from day one.
   the ruling was made on a corrected picture. this fulcrum was originally weighed against
   three pressures; two of them turned out not to exist:
   - **untracked files** — already served by `--tree` (`--others --exclude-standard`), under
     the `(inflight)` label. never a gap.
   - **debug a peer clone's actual dirty state** — already served, because `--tree` resolves
     the repo's own main clone (`--tree main`), not worktrees alone. never a gap.
   - **gitignored files + binaries** — the only true leftovers, and gitignored is a
     deliberate refusal in all three modes rather than an oversight (one flag, one sense).
   so the hatch was weighed against a much smaller gap than first stated, and declined. the
   wisher also confirmed untracked coverage needs no new render work: the tree-level
   `tree: <name> (inflight)` label already tells a reader the whole listing is un-latest.
5. **whose reads does this govern — mechanic only, or every role?** the hook would live in
   mechanic's inits (`src/domain.roles/mechanic/inits/claude.hooks/`). but architect,
   ergonomist, and others also read cross-repo. is the requirement mechanic-scoped or a global
   guardrail? **best guess:** global in spirit (the staleness hazard is role-agnostic), so it
   should register for every role that reads code — but the wish does not say, and the
   registration surface differs per role. worth one confirmation before we pick a home.

### risks / questions to validate before build

- **[answered] PreToolUse CAN intercept Grep/Glob.** confirmed against the Claude Code hooks
  docs (code.claude.com/docs/en/hooks): PreToolUse fires before `Grep` and `Glob`, a matcher
  `Grep|Glob` targets them, and **exit code 2 blocks the call and surfaces stderr to the
  model** — the same enforcement semantics as Bash. so the wish's first half IS enforceable
  via a hook. note no extant hook matches `Grep`/`Glob` (`getMechanicRole.ts:56,80,98`), so we
  are first to use it — but the capability is documented, not hypothetical.
  - **[research] one field-name detail to confirm at build:** the docs describe `tool_input`
    with a `paths` array + `pattern` for Grep/Glob, but this harness's live Grep/Glob schema
    uses `path` (singular). the hook must read whatever field the live tool sends — confirm
    against the actual tool_input JSON in a smoke test before wiring the matcher.
- **[answered] read-mode output currently omits the ref.** the testdrive examples above show a
  `ref:`/`tree:` line in *read* mode, but the extant read path prints only `repo:` and
  `paths:` — no `ref:` line (`operations.sh:1115-1120`). so surfacing the ref/tree label in
  read mode is a **proposed enhancement**, not current behavior. it is arguably required by
  the wish (you must know whether you read latest or inflight), but it is net-new output.
- **[answered]** the hook can derive the current-repo toplevel from inside a worktree — git
  records the worktree's `.git` as a file, not a dir, and `git rev-parse --git-dir` /
  `--show-toplevel` handle it (the rebase op already relies on this via `get_git_dir` at
  `git.branch.rebase.operations.sh:18`). no build blocker here.
- **[answered]** `git.repo.get`'s test harness (sets `HOME` → temp `git/` root,
  `--refresh off`) can stand up a worktree fixture for `--tree` coverage via `git worktree
  add` — a straightforward extension of the extant temp-repo setup.

## groundwork

### external research

none — no external dependencies. this is entirely local tooling (bash hooks, the
`git.repo.get` skill, git worktrees). no external APIs/services referenced by the wish.

### internal research (verified)

- **the loophole is real**: Bash is gated by `pretooluse.check-permissions.sh`; Write/Edit/Read
  are gated only by `pretooluse.forbid-tmp-writes.sh` (which blocks `/tmp`, not cross-repo).
  Grep/Glob are gated by no hook at all. so adhoc cross-repo Read/Grep/Glob is currently
  unguarded. (verified via hook inventory in `src/domain.roles/mechanic/inits/claude.hooks/`
  and the live permission block I hit when running `cd ~/git`.)
- **hook template**: `pretooluse.forbid-tmp-writes.sh:23-160` is the exact pattern — read JSON
  from stdin, branch on `tool_name`, inspect `file_path` (Read/Edit/Write) and `command`
  (Bash), block with exit 2 + stderr guidance. a cross-repo hook mirrors this.
- **hook registration**: hooks are declared in TS under `hooks.onBrain.onTool`
  (`getMechanicRole.ts:27` `onBrain`, `:51` `onTool`) as `{ command, filter: { what, when } }`,
  serialized to `.claude/settings.json`. `what` is a pipe-delimited tool-name string, e.g.
  `filter: { what: 'Write|Edit|Read|Bash', when: 'before' }` (`:98`, forbid-tmp-writes). a new
  pretooluse hook wires in the same way — BUT no extant `what` includes `Grep`/`Glob` (see
  risks).
- **git.repo.get contract to conform to**: subcommands `repos|files|lines`; flags
  `--repos --in --paths --words --radius --ref --refresh` (`git.repo.get.sh:42-115`). `--tree`
  slots in beside `--ref`. default ref is `origin/<default-branch>`
  (`operations.sh:161` `get_default_branch`), and `refresh_local_repo` (`operations.sh:105`)
  fetches origin first — this is what guarantees "latest".
- **stdout format to match**: turtle header + `🐚 git.repo.get <sub>` tree with `├─`/`└─`
  branches, a `ref:`/`tree:` line, and a `found: N` footer (verified against the integration
  test snapshot). `--tree` adds a `tree: <name> (inflight)` line where `ref:` sits today.
- **git root var**: `get_git_root` honors `$GIT_REPO_ROOT`, default `$HOME/git`
  (`operations.sh:17`). the hook must use the same var so the boundary matches the skill.
- **worktree handling precedent**: `git.branch.rebase.operations.sh:14-23` already resolves
  git-dir correctly from inside a worktree — the technique the hook and `--tree` both need.

### vocab / name patterns to reuse

- `--tree` (flag), `tree: <name> (inflight)` (output label), `cross-repo` (domain term),
  `current repo` vs `cross-repo target`, `$GIT_REPO_ROOT`. hook name follows the extant
  pattern: `pretooluse.forbid-cross-repo-reads.sh`.

## what is awkward?

- **"same repo, different tree" is genuinely ambiguous.** the wish frames enforcement around
  *repos*, but worktrees blur "a repo" into "many trees of a repo." blocking a read of repo
  X's main clone *while working in a worktree of X* may feel pedantic — yet it is exactly where
  a stale/dirty read bites. the `--tree` flag is the pressure-release, but the boundary rule
  needs the wisher's blessing (fulcrum #1).
- **`--tree` reads uncommitted state — a deliberate hole in "always latest".** the whole wish
  is "callers always look at latest," and `--tree` intentionally does the opposite. it is
  justified (peeking at inflight is a real need), but the label must be so loud that no reader
  ever mistakes inflight for latest. the design leans hard on one output line doing that work.
- **friction vs guarantee — settled, no hatch.** the redirect adds a step to every legit
  cross-repo read. an escape hatch would soften it but dilute the guarantee. the wisher ruled
  for the narrow pit (2026-08-16), and the ruling costs less than it first looked: the two
  usecases that made a hatch feel necessary (untracked files, a peer clone's dirty state) are
  both already served by `--tree`.
- **Bash command-string inspection is inherently leaky.** matching cross-repo paths in
  arbitrary Bash (like forbid-tmp-writes does for `/tmp`) will always have edge gaps
  (variables, subshells). the tool-level gates (Read/Grep/Glob) are precise; the Bash gate is
  best-effort. we should be honest that Bash coverage is a heuristic, not a proof.
