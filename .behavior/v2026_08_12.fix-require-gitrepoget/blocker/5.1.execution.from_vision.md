## how these reviews could be improved (the exhaustion feed-forward)

1. **bound the review glob in the guard template.** an unbound `'**/*'` walks `node_modules`
   and OOMs every reviewer. this cost ~63 reviewer runs across 7 iterations and hid 6 real
   blockers. the guard template should default to a bounded root.
2. **let a reviewer's budget reset when its own critique is addressed.** r9 spent its last
   round on a claim i then fixed *and* covered — and its stale verdict now blocks a stone
   that 8 reviewers approve. budget is spent per-round, not per-unresolved-issue.
3. **do not cache an l3 verdict across a changed revision.** r10/r11 block on i007 state
   while the code sits at i011.
4. **reviewers should verify a security claim before they raise it.** r10's "planted in your
   tracked files" was a conflation of its own tool-wrapper output with file content.
5. **two concurrent `--as arrived` runs race on one iteration, and the loser is overwritten.**
   observed directly at i017: a backgrounded re-arrive and a foreground one both ran against
   hash `6311f5c603fe0d3f95`, and returned **contradictory verdicts** — one `rejected, 1
   blocker, 0 nitpicks`, the other `approved, 0 blockers, 2 nitpicks`. same content, same
   reviewer, opposite outcomes. whichever finished last wrote the `.given`.

   two separate things to fix, and the second is the worse one:
   - **the harness should refuse a second concurrent arrive on a live iteration** (a lock, as
     the route already uses elsewhere), so a `.given` is never silently replaced under a
     `.taken` that answered the other copy.
   - **the reviewer is non-deterministic enough to flip its own verdict** on identical input.
     that is worth knowing on its own: a single run's verdict is a sample, not a measurement.
     it also means an `exhausted` can be an artifact of sampling rather than of insatiability.

   the trail here is intact — the surviving `.given` is the one my `.taken` answers, and the
   defect it named (the bare-repo fix-line shape with zero coverage) was real and is clamped
   by case21. but that was luck, not design.

## the debt i did not fold in (each with a reason)

- **the 9th hand-copy of path containment.** `realpath -m` + prefix-compare is now
  independently reimplemented in `rmsafe`, `cpsafe`, `mvsafe`, `teesafe`, `mkdirsafe`,
  `grepsafe`, `globsafe`, this skill's `is_path_within_tree`, and the hook's `is_cross_repo`.
  for a **security boundary**, N hand-copies IS the hazard. there is no shared seam across
  `claude.tools/` today, and to invent one inside a `--tree` behavior is the scope leak.
  **this is the one i would argue deserves a wish of its own.**
- **the duplicate slug derivation** — the hook derives a slug from the git remote, the skill
  from path segments; no test pins them to agree. same absent-seam reason.
- **a TOCTOU** between the `-f`/`-r` check and the `cat` in `--tree` read mode. the fix wants
  an fd held open across an `fstat`, which bash cannot do without a helper binary, and an
  attacker who can win that window already has write access to the tree they would exfiltrate.
- **`get_all_cloud_repos`'s failhide** — same family as the ones fixed, but it pre-dates this
  wish and serves the cloud path `--tree` never touches.
