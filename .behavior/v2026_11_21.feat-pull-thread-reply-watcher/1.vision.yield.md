# 1.vision — each new commander review thread reaches its crew as a reply task

## .what this builds

the pr-watch daemon learns what a review thread is. on each read of a watched pr it groups the inline review comments by thread and asks of each one: does a human await a reply from the crew? when yes, the crew gets a **reply task**: the lead section of that read's alert, ahead of any ci or approval news, that carries the whole of what was asked, the link, and the one command that answers it.

a thread the crew already answered raises naught. a bot's thread raises naught. the crew's own replies — under any of its logins — raise naught.

## .why it works

- **the daemon already reads every review comment.** `get_watch_pr_state` fetches `pulls/:n/comments` each read (`git.pull.watch.github.sh:265`); each reply row names its root in `in_reply_to_id`, and a root carries none, so the thread shape is in hand at no extra github cost
- **the daemon already knows the crew's words.** every reply sent through `git.pull.comment set` lands its id in the clone ledger (`git.pull.watch.operations.sh:440`), so "the crew answered" is a proof, not a guess at a login
- **"unanswered" keeps the sense the repo already uses.** a thread is unanswered when a human comment follows its last answer, and a bot never asks — the sense of `git.pull.comment get --unanswered` and of the shared rule open pr #1340 lands. the daemon holds its own copy of that sense in `WATCH_DIFF_JQ`, proved by the ledger rather than by login, and converges on #1340's rule once that merges (F3, a caught dream)
- **delivery is already safe.** a reply task rides the extant outbox: on disk before the cursors move, held while the crew is blocked, never forced (pr-watch F6, F8)

## .the contract

- **raised by**: a review thread on a watched pr that holds a trusted human's comment (owner, member, or collaborator, F20) after its last crew or peer answer (or has no answer yet), where that comment is new since the watch's cursor (F1); or a human comment whose text was edited since the daemon last read it, answered or not (F9)
- **not raised by**: an answered thread · a bot's comment · the crew's own comment · a peer clone's thread (that keeps today's `comment.new … (clone)`, F4) · a review body (it keeps today's `comment.new`; it has no reply target) · a top-level comment, a human's included (it keeps today's `comment.new`; out of scope, F10, a caught dream)
- **reaches**: the crew that holds the pr watch (`git.commit.push` sets it on each push, F5), on the pr's next read: one tick (60s) while the pr moves, at most 30 min once quiet
- **shape**: one alert per pr per read, as today (A9). the reply tasks lead it, one section per unanswered thread; the header names them first; the last `next` puts the replies before any code event (F2)
- **each section holds**: the thread id · `new`, `follow-up`, or `edited` · the author · `file:line` · the url · `re:` the root's first line (a follow-up, or an edit of a comment below the root; F14) · each unanswered comment whole under `says`, up to 2000 chars, fences kept (F6) · the reply command
- **seen once, whatever the order**: review comments are tracked by the set of ids seen, each with a hash of its body, as check runs already are tracked by id — not by the largest id; the prime tick reads a review's `submitted_at`. a draft review's comments keep their draft-time ids, so a max-id cursor drops a whole review that lands after a newer comment (F8, case 8); the body hash shows an edit, which keeps its id (F9, case 9)
- **the reply command**: `rhx git.pull.comment set --which <n> --in <repo> --reply-to <root id> --key answer-<id>-c<clone> --from <file|@stdin> --mode apply`; the key names the comment answered and the clone, so a rerun of the command edits its own answer. an `edited` task keys `answer-<id>-e<print>-c<clone>`. a keyed set edits in place and an edit sends no notice, so the answer to an edited ask, or a second clone, lands as a fresh comment, never an edit of an answer another wrote (F15)

```
🐢 heads up dude...

🐚 git.pull.watch — reply task on #7
   ├─ pr: ehmpathy/surf-demo#7
   ├─ thread 4601234567 · new · by @uladkasach
   │  ├─ file: src/wave.ts:42
   │  ├─ url: https://github.com/ehmpathy/surf-demo/pull/7#discussion_r4601234567
   │  └─ says
   │     ├─ basically, i dont want to slam github every hour for no reason.
   │     └─ we should be able to read a quiet pr for free via etags.
   └─ next: reply first, then resume: rhx git.pull.comment set --which 7 --in ehmpathy/surf-demo --reply-to 4601234567 --key answer-4601234567-c<clone> --from <file|@stdin> --mode apply
```

## .the outcome world

### a day in the life

the commander reviews `#7` after lunch and leaves six threads in five minutes. the crew is deep in a route stone. each read that sees a new thread queues one reply task; when the crew's turn yields, it answers each thread in two lines — what it will change, or why it holds — and resumes the stone. when a fix lands, it replies again in the thread under the printed key plus `-done`, so the commander is notified: "done in 4d7a5bd." the commander reads answers within the hour, not within days, and no director spends a turn to relay them.

### before and after

| | before (#1222, 11-06) | after |
|---|---|---|
| how the crew heard | a director's relay (`4506794557`: "your comments reached me through the director's relay") | a reply task on the next read |
| first reply | 47.6 h after the last thread | minutes after the crew's turn yields |
| what the crew sees | (with today's daemon) `new comment`, a 120-char first line, `next: rhx git.pull.comment get` | the whole comment, its link, and the reply command |
| a bot's review comment | alerts, labeled `(bot)` | naught |
| a thread the crew answered via relay | alerts on the next read anyway | naught |
| a follow-up in an answered thread | alerts as a bare `review comment` | a reply task with `re:` context |
| a draft review submitted after a newer comment was read | dropped, with no word | a reply task per thread |
| an edit that adds an ask to an answered comment | unseen: the id is old | a reply task, labeled `edited` |

### the aha

the crew never decides "is this worth a reply now?". the alert already decided: a human awaits a reply; here is what they said; here is the command. a reply costs one turn, and the code work goes on after it.

## .mental model

- **to a friend**: "when my reviewer leaves a comment, my agent gets a to-do that says what they asked and how to answer — not a nudge to go look."
- **analogy**: an inbox that files each question as its own ticket, with the reply button on it; a bot's notice never becomes a ticket, and a ticket you already answered never shows up.
- **their words vs ours**:

| a human says | we say | why ours |
|---|---|---|
| comment, review comment | thread | github groups replies under a root; the reply goes to the root |
| needs a reply, not answered yet | unanswered | the extant `git.pull.comment get --unanswered` sense, one word across every reader |
| notification, heads up | reply task | the wish's own word: a task the crew owns, apart from code work |
| reviewer | commander, or any trusted human | the daemon has no commander identity; any human the repo trusts (owner, member, collaborator) counts (F20) |

## .evaluation

### against the wish

| done means | how |
|---|---|
| a new thread reaches the crew within one watch cycle, with text and link | the next read raises it; cases 1, 4, 5 |
| an answered thread, or a bot's, raises naught | the ledger-proved unanswered rule; cases 2, 3 |
| a clamp test per case | each `[tn]` becomes an integration case beside `git.pull.watch.events.integration.test.ts`, on the extant fake-github scene (`__test_utils__/genWatchTestScene.ts`) |
| a pr up, ci green | 5.1 / 5.3 |

### pros

- no new process, no new token, no new github read: the daemon already holds every fact it needs
- no wait on another pr: the daemon's rule ships in this one
- no new alert shape: A9 holds, and the reply task is one more section kind beside `ci failed` and `approved`
- the whole comment arrives: 7 of 23 commander comments on #1222 and #1143 span several lines, and each arrives cut today
- the reply key makes a late or doubled task harmless

### cons

- two copies of the "unanswered" sense until #1340 merges and the convergence dream lands; they can disagree on a thread a human login answered with 🐢 but no ledger id
- a crew whose serial changed hears naught until its next push (F5)
- a human's top-level question still arrives as a bare `comment.new`: 2 of 17 commander comments on #1222 were top-level, and the first waited 13.4 h (F10, a caught dream)

### edgecases and the pit of success

| edge | the guard |
|---|---|
| the crew replies outside `git.pull.comment set` (web ui, raw `gh`) | no ledger id; the 🐢 peer proof still counts a 🐢 body from a proven login. a bare reply reads as a human follow-up and raises one task. the alert's reply command is the paved path, so the next reply is ledgered |
| a task delivered after the crew answered | marked `held N ticks`; the per-comment key turns the second answer into an edit (case 6) |
| a thread marked done before the read | still raised: rest carries no such flag; rare, cheap (inventory C4) |
| a review with many threads | one alert per read, one section each (F2) |
| a huge comment | 2000 chars, then a cut line with the read command (case 7) |
| github down, token locked | the extant pause and outage notes; cursors hold, so the thread raises once reach returns |

## .open questions & assumptions

### assumptions

- every crew pr is opened via `git.commit.push`, so the crew holds a watch on it (F5)
- any human the repo trusts who comments on a crew pr is one the crew owes a reply; the daemon does not single out the commander. a reply task hands the whole comment to the crew as work, so a human with no tie to the repo keeps today's one-line `comment.new` instead (F20)
- a reply sent through `git.pull.comment set` is the crew's normal path, so its ledger proves its answers

## .what is awkward

- **the crew answers under three logins.** `ehm-seaturtle`, `ehm-a-seaturtle[bot]`, and the human's own login with 🐢. the ledger carries the proof, so a reply posted outside the paved verb is invisible as an answer and re-raises once
- **#1340's rule calls an app bot's reply a non-answer.** the crew's own app login is a bot. the daemon's rule tests the ledger before the bot test, or every crew answer from `ehm-a-seaturtle[bot]` would leave its thread unanswered. the convergence must keep that order
- **the daemon cannot see a thread marked done.** a commander who opens and marks a thread inside one read gap still sends a task
- **top-level answers cannot be linked.** the conversation tab has no reply link, so "answered" there is an inference; that is why top-level questions wait for their own pr (the dream)
- **"reply first" is a nudge, not a gate.** the alert asks, and its order says so; naught enforces it. the release gate (#1290) is the only hard stop
- **a mixed alert is longer.** a burst of threads beside a red check makes one tall alert. it stays one alert because A9 has no read against it, and one read of the queue beats two
- **two copies of one sense, for a while.** the daemon's rule and #1340's state it two ways until the dream lands
