# case=9 · the commander edits his comment after the crew answered, to add an ask

covers: E1, E3. sharp · critipath.

## .narrative

on `#7` the commander asked "--pr -> --which plz". the crew renamed the flag and answered: "done in 4d7a5bd". an hour later the commander came back to the same comment and edited it, rather than reply under it: "--pr -> --which plz. and make a rule, so no verb says --pr again".

the edit keeps the comment's id. a daemon that tracks only ids sees no new comment, and the thread reads answered — the crew's reply is the last one. the new ask would be lost with no word, and the commander would wait on a crew that thinks it is done.

the daemon keeps a hash of each comment body it has seen. on the next read, this comment's hash has moved. its author is a human, so it raises one reply task, labeled `edited`, with the current text whole:

```
🐢 heads up dude...

🐚 git.pull.watch — reply task on #7
   ├─ pr: ehmpathy/surf-demo#7
   ├─ thread 4601270000 · edited · by @uladkasach
   │  ├─ file: src/flags.ts:3
   │  ├─ url: https://github.com/ehmpathy/surf-demo/pull/7#discussion_r4601270000
   │  ├─ says
   │  │  └─ --pr -> --which plz. and make a rule, so no verb says --pr again
   │  └─ note: an edit sends no notice, so this answer posts as a new reply, under its own key
   └─ next: reply first, then resume: rhx git.pull.comment set --which 7 --in ehmpathy/surf-demo --reply-to 4601270000 --key answer-4601270000-e<print>-c<clone> --from <file|@stdin> --mode apply
```

the crew sees the rule ask, writes the rule, and answers. the key carries the edit's print, so the answer lands as a fresh reply, not an edit of the first: github sends no notice for an edit, and the commander who added the ask must hear the answer (F15).

the crew's own edits raise naught: their ids sit in the crew's ledger (E3). an edit the crew answered inside the same read gap, carried by a relay, raises naught too, since the edit landed before that answer. a commander who fixes a typo in an answered comment costs the crew one read and one short reply; that is the price of no silent drop.

## .why it fails safe

- the seen state holds a body print per comment, so an edit can never hide behind a kept id
- only a trusted human's edit raises; the crew's own edits, a bot's, a peer's, and a stranger's stay quiet
- an edit raises only when it landed after the last answer, by github's `updated_at`
- the answer to an edit keys on the edit's print, so it notifies; a re-delivered task for the same edit keys the same answer, so no twin
