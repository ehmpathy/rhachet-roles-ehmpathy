# case=6 · the task waits while the crew is blocked

covers: S3, H1. sharp · critipath.

## .narrative

the commander opens a thread on `#7`. the daemon queues the reply alert. the crew sits at a permission prompt that only the human can answer, so `clone say` refuses: a modal is the human's. the alert stays in the outbox; the daemon never passes `--force` and never types into the modal.

the next tick refuses again, and the next. the daemon holds the alert and notes its cause; `rhx git.pull.watch get` names it:

```
         └─ ehmpathy/surf-demo#7 → @:mechanic (root: ~/git/ehmpathy/surf-demo) · 1 held
```

its json names `heldTicks` and `heldCause`, as today.

meanwhile the director, who reads the pr, relays the thread into the crew's session by another route, and the crew answers it the moment the prompt clears. one tick later `clone say` takes the held alert:

```
🐚 git.pull.watch — reply task on #7 (held 4 ticks; you were busy; check each thread first, you may have answered it)
```

the crew reads the mark, opens thread `4601250000`, and sees its own answer there, posted from the relay. it posts naught. the late task cost one read, not a duplicate answer.

the daemon cannot tell this case apart: an answer posted by another route carries no ledger id, so the task still lands. the mark is what keeps it from a twin, so the crew owes the check. had the crew answered through the alert's own command earlier, a second run under the same key would edit that answer in place.

## .why it fails safe

- the alert is on disk before the cursors move: a crash or a refusal holds it, never drops it (pr-watch F6)
- a held reply task says it is late and asks for a check of the thread first, on both delivery routes (`clone say` and the prompt hook)
- the reply command carries a per-comment, per-clone key: a rerun of the same command edits its own answer, never a second post
