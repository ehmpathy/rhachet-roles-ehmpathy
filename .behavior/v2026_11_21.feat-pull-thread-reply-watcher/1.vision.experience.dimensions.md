# 1.vision.experience.dimensions — a review thread reaches its crew as a reply task

the experience space of "a human opens or extends a review thread on a crew's pr; the crew hears it as a task to reply". the daemon's lifecycle (findsert, version keys, reaps, upgrades) is unchanged and was walked in `.behavior/v2026_10_31.feat-pr-watch-daemon/1.vision.experience.dimensions.md`; this walk covers the alert box alone.

## .actors

| actor | role in the experience |
|---|---|
| `crew` | the clone that holds the pr watch; the one tasked |
| `commander` | the human who reviews; opens and extends threads |
| `director` | a clone that reads the pr; today it relays threads by hand |
| `system` (the daemon) | reads github, judges each thread, delivers the task |
| other authors | a bot, a peer clone — walked as D2 |

## .dimensions

### D1 · motion — what one comment did since the last read

| value | sense |
|---|---|
| `root.new` | a comment first seen, with no `in_reply_to_id` — it opens a thread |
| `followup.new` | a comment first seen, with an `in_reply_to_id` — it extends a thread |
| `edit` | a comment seen before whose body changed (its body hash moved; its id stays) |
| `delete` | a comment seen before that the read no longer returns |

D1 names the move alone. whether the thread had an answer before the move, or has one after it, is D3's.

### D2 · author of that comment

`human` · `bot` (a third-party app: `user.type == "Bot"` with no ledgered comment on the pr) · `peer-clone` (another clone, proven by a clone ledger per `is_peer`) · `self` (this crew's ledger, under any of its logins)

### D3 · thread state at the read — after every move the read sees

| value | sense |
|---|---|
| `unanswered` | the thread's last human comment has no answer after it (the extant `--unanswered` sense) |
| `answered.by-crew` | the latest answer after the last human comment is this crew's |
| `answered.by-peer` | the latest answer after the last human comment is a peer clone's. the pr author is no answerer here, unlike #1340's rule: a commander who opens a pr a crew then pushes to is its author, and his own asks would read as answers |

D3 is read at the read, not before the move, so it is independent of D1: a human root can be answered before the daemon sees it; a crew followup can sit in a thread a human has since extended.

### D11 · done mark — github's flag on the thread, unseen by the daemon

`open` · `marked-done` (github's `resolved` flag; graphql only)

a thread can be answered and marked done at once, so the mark is its own axis, not a D3 value. the daemon's rest reads never see it, so no verdict can turn on it: every cell under `marked-done` takes its `open` verdict (row C4), save `root.new`, which opens a thread and so cannot land in one already marked.

### D10 · arrival — how the comment reached the api

| value | sense | seen |
|---|---|---|
| `posted-alone` | "add single comment": a review of one comment, submitted the second it is made | #1222: all 15 commander comments, one review each |
| `via-draft-review` | "start a review": comments drafted over minutes, all visible at submit; each keeps its draft-time id and `created_at` | #1143: 8 comments drafted over 12 minutes, submitted 6 minutes later in review `5646610469` |

D10 is orthogonal to D1–D3: a draft review can hold roots and followups, by any author, answered or not. it bites the cursor: a draft-time id can sit below a comment read before the submit.

### D4 · tick mix — what else rides the same read of the pr

`thread.alone` · `threads.several` (a review burst) · `thread+code-event` (a red check, an approval, an issue comment)

### D5 · text of the comment — three independent attributes

| axis | values |
|---|---|
| D5a · lines | `one-line` · `multi-line` |
| D5b · fence | `none` · `fenced` (a ```suggestion or code block) |
| D5c · size | `under-cap` · `past-cap` (over 2000 chars) |

a fence needs a line for its open, its body, and its close, so `fenced` implies `multi-line`: `one-line × fenced` is impossible. size is independent of both: a 2500-char comment can be one line or many, fenced or not. control bytes (an escape, a tab) ride any shape and are cleaned the same way, so they are walked once (row T5), not as an axis.

### D6 · crew state at delivery

`idle` · `busy` (mid-turn) · `held` (modal, dirty input, a wedged socket) · `dead`

### D7 · watch state

| value | sense |
|---|---|
| `live` | the crew pushed; `git.commit.push` set the watch |
| `none` | the crew holds the branch but no watch (it never pushed this session, or its serial changed) |
| `pre-watch` | the comment landed before the watch's `setAt` |
| `ended` | the watch ended: merged, closed, or idle past a week |

### D8 · github reach

`ok` · `not-ok` (rate limit, outage, auth) — the extant pause/backoff/outage paths

### D9 · surface kind

`review-thread` (inline, `pulls/:n/comments`) · `review-body` (a review's own text) · `issue-comment` (top-level conversation)

## .why these are orthogonal

- D1 is the move, D2 the mover, D3 the thread's state at the read. each can vary while the others hold: a human root can be answered before the read; a bot can extend an answered thread; a crew can edit its own answer
- D10 is how a comment reached the api; it changes only whether the comment reads as new
- D11 is github's done mark, apart from D3's answer state: a thread can be both answered and marked
- D4 is the rest of the pr's state that read; D5a–c are one comment's text. neither changes who or whether
- D6, D7, D8 are delivery-side: whether a task can reach the crew. each acts the same on every thread
- D9 sets scope: only `review-thread` carries `in_reply_to_id`, so only it has a thread to reply into

## .the walk

- **core box** = D1 × D2 × D3 on `review-thread`, `ok`, `live`, `idle`, `posted-alone`, `open`: all 48 cells, one grid per D1 value
- **done mark** = D11 = `marked-done` × the core: unseen by the daemon, so each cell takes its `open` verdict; walked once (C4), with the one impossible cell named
- **arrival** = D10 = `via-draft-review` × the core's raise cells: it changes only whether a comment is seen as new
- **text box** = D5a × D5b × D5c on the raise verdict: all 8 cells, 2 impossible
- **mix box** = D4 × D5c: D4 sets the alert's layout around each section, and only size changes what a long alert costs; all 6 cells
- **delivery box** = D6 × D7: all 16 cells; D8 = `not-ok` stalls every cell alike, so it is walked once
- **scope box** = D9 ≠ `review-thread`: keeps today's `comment.new` path → walked once each

## .hidden dimensions the walk surfaced

**answerer login** — D3 = `answered.by-crew` forced it. the crew answers under three logins on #1222: `ehm-seaturtle` (User, 🐢), `ehm-a-seaturtle[bot]` (Bot, 🐢), and the human's own login with a 🐢 body (`4568370294`, `4571586016`, posted `--auth as-human`). the proof of a crew answer is its id in a clone ledger, else a 🐢 body from a login that holds a ledgered comment; never the login alone.

**bot role** — D2 = `bot` × D3 forced it. a third-party bot's comment never asks and never answers; the crew's own app login is `self`, not `bot`, once it holds a ledgered comment. `rhelease[bot]` opens with 🐢 too, so 🐢 + bot alone proves naught.

**watchers per pr** — D6 × D3 forced it: one pr can hold `one-crew` or `two-crews` (two clones each pushed to it). a task to each is two answers to one thread. see `case=_` row S5.

**held-then-answered** — D6 = `held` × D3 forced it. a task held in the outbox while the crew answers by another route is delivered late, already answered. see `case=_` row H1.

**seen state** — D1 = `edit` forced it: the daemon must remember each comment's body hash, not only its id, or an edit is invisible (F9).

**D12 · upkeep and read shape** — the seen state, the knobs, and the readers forced it. each value acts the same on every core cell, so each is walked once (see `case=_` upkeep box):
- record age: `current` · `legacy` (written before the seen state) · `moved` (carried to a new key by an upgrade)
- knob: `valid` · `malformed` (a cap or checks-shown value that is no whole number)
- read shape: `whole` · `lagged` (a seen row omitted once, then served again) · `huge` (past one argv slot) · `moved-line` (`line` null, `original_line` set) · `whole-file` (both null: a comment on a whole file)
- outbox read: `whole` · `mid-write` (a temp file beside the entry it will replace)

see `1.vision.experience.case=_.md` for every cell and its verdict.
