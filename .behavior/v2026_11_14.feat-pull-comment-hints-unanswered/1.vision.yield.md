# 1.vision — every comment set names what still awaits a reply

## the outcome world

### before
a robot in a reply round answers one review thread. to learn what is left, it must remember to run `rhx git.pull.comment.get --unanswered`, or scroll the pr. it forgets often enough. a thread stays silent, the human approves "given the comments are addressed", and the release ships with the comment unanswered (#693).

### after
every `rhx git.pull.comment.set --mode apply` ends with a 🥥 that lists each comment on the pr that still awaits a reply, one row each, with the exact command to answer it. the round's to-do list arrives with each answer. when the last thread closes, one line says naught awaits.

### the aha
the robot answers thread 901 and, in the same output, reads "903 and 906 still await", each with its reply command. it never asks "what is left?". the list shrinks with each post until it reads "naught awaits".

### the contract (sketch)

```
🥥 did you know?
   └─ 2 comments on ehmpathy/surf-demo#7 still await a reply
      ├─ review 903 by surfer-kai, src/slug.ts:4: "forbid the dot"
      │  └─ rhx git.pull.comment.set --pr 7 --in ehmpathy/surf-demo --reply-to 903 --key answer-903 --from <file>
      └─ issue 909 by surfer-kai, top-level: "one more note: bump the docs too"
         └─ rhx git.pull.comment.set --pr 7 --in ehmpathy/surf-demo --key answer-909 --from <file>
```

row parts:
- first words = the body's first line, 🐢 prefix and key marker stripped, cut at 60 characters with `…`
- path:line = `path:line`, else `path:original_line` for an outdated comment; `top-level` for an issue comment
- the command's target flags come from `as_comment_cmd_target` (adds `--in`, and `--auth as-human` when the set ran so), as every fix line in this family does
- the key is prefilled as `answer-<id>`, so only `--from <file>` is left to fill (F8)

none await → `🥥 did you know?` + `└─ naught on <repo>#<n> awaits a reply`.
the read fails → one `⚠️` line with the cause and the `get --unanswered` command; exit 0.

### the rule (one operation computes it, for the hint and for `get --unanswered`)

a comment awaits a reply when all hold:
- its author is neither the robot nor the pr author, nor an app bot (`user.type == "Bot"`, e.g. `rhelease[bot]`; F9)
- its thread is not resolved (review comments)
- no comment from the robot or the pr author comes after it in its thread. the top-level (issue) conversation counts as one thread

"robot" = the current login, with a body that opens 🐢 (extant `is_robot`).
"pr author" = the pull's `user.login`, matched with the same `slug` ≡ `slug[bot]` equivalence as `is_login_self`, since an app token's login and its comments' login may differ by that suffix.

rows: one per review thread that awaits, named by the first human comment after the last answer. one per issue comment that awaits.

## mental model

- to a friend: "each time it posts a reply, it tells you which comments are still left."
- metaphor: a checkout receipt that prints "items still in your cart".
- the human says "unanswered comments"; we say "comments that await a reply". the flag stays `--unanswered`.

## evaluation

- goals: the hint lands where the robot already looks, after the write. it shares one read with `get --unanswered`, and #1171's gate will source that same read, so the three cannot disagree.
- pros: zero new verbs or flags; reply commands are copy-paste; read-only, so the set's exit code is untouched.
- cons: one more paginated read (issue list, review list, graphql threads) after each apply. a second round trip on every write.
- edges:
  - read fails → warn, exit 0 (case=3). hazard: every family refusal renders its full block to fd 3 (the real stdout) even inside `$(…)` (`operations.sh:33-35`, `emit_comment_refusal` → `>&3`). the hint read must mute that render and its exit, then print its own one line. a bare subshell catch would leak a whole `✋`/`💥` block
  - plan → no hint; plan's own 🥥 names the apply
  - json → unchanged; `get --unanswered --output json` is the json path
  - issue comment → top-level `--key` command, since `--reply-to` takes review ids only
  - a just-posted reply → the read runs after read-back, so the answered thread drops out

## what is awkward?

- the set's json and tree diverge: the tree carries the hint, the json does not (F5).
- the answerer set depends on `--auth` (F6). a bot reply does not close a thread for an as-human read unless the bot opened the pr.
- every apply now costs a second round of reads. it is cheap per call, but a rate-limited burst of replies spends it on every post.
- "review comment" in the wish vs "issue comment" in the code: the hint shows both, labeled `review` and `issue` to match `get`'s rows.
