# 1.vision — fix seaturtle contributor count on squashed PRs

## the wish, restated

when a seaturtle PR squash-merges, the merged commit should credit **exactly two** identities:

1. **ehm-seaturtle** (`seaturtle@ehmpath.com`) — the git author of the work
2. **the human co-author** — from the `Co-authored-by:` trailer

…even though a **github app** (the seaturtle ehmpath app) is the one that *creates* the PR.

today we get **three**: the app sneaks in as a contributor alongside the two we want.

---

## the outcome world

### day-in-the-life

a mechanic does work → `git.commit.set` authors commits as `seaturtle@ehmpath.com` with a `Co-authored-by:` human trailer → `git.commit.push` opens a PR via the app token (nice bot creator on the PR card) → `git.release` merges it.

the squash commit lands on `main`. you open it on github. the contributor strip shows **two avatars**: ehm-seaturtle and the human. the app is absent from the contributor list — it remains, correctly, just the *opener* of the PR.

### before / after

| | author | committer | co-authored-by | contributors shown |
|---|---|---|---|---|
| **before (broken)** | ehm-seaturtle | the app bot | human | **3** (app leaks in) |
| **after (wished)** | ehm-seaturtle | `GitHub` web-flow *(invisible)* | human | **2** ✅ |

### the "aha" moment

the value clicks when you realize **creating a PR and merging a PR are two separate identities**. the app being the *creator* is cosmetic and harmless — it never touches the squash commit's metadata. the app only becomes a *contributor* when it is also the *committer* of the squash commit, i.e. when it performs the merge. decouple "who opens" from "who merges" and the third contributor evaporates.

---

## user experience

### usecases / goals

- **clean attribution**: humans scanning history/changelogs see who actually did the work (turtle + human), not the plumbing (the app).
- **keep the pretty PR card**: the app still authors the PR title + creator, which folks like.
- **no behavior change for mechanics**: the fix lives in tooling (`git.release` / token wiring), not in how a mechanic commits.

### contract inputs & outputs

the relevant surface is the **token used per github action**, inside the skills:

- `git.commit.push.sh` → `gh pr create` — input: app token → output: PR opened by app *(unchanged, desired)*
- `git.release` (`enable_automerge` → `gh pr merge --auto --squash`) — input: **today the same app token** → output: squash commit whose committer/attribution pulls the app in *(this is the lever)*

the squash commit on `main` is the real "output" we care about. its observable contract:

```
Author:           Seaturtle of'Ehmpathy <seaturtle@ehmpath.com>
Committer:        GitHub <noreply@github.com>        # web-flow → not a contributor avatar
Co-authored-by:   <human> <human@email>
```

### what leveraging it looks like

a human verifies with one command:

```
git show <squash_sha> --format='Author: %an%nCommitter: %cn%n%b'
```

and sees only turtle + human. no app.

### timeline

commit (turtle author) → push (app opens PR) → merge (identity that is **not** the app) → squash commit shows 2 contributors → release proceeds as normal.

## mental model

### how a user describes it to a friend

> "the bot that *opens* our PRs was also the bot that *merged* them, so it kept showing up as a third author. we made something else do the merge, so now only the turtle and the human get credit."

### analogy

a **notary** vs an **author**. the app is the notary who files the paperwork (opens the PR). you don't want the notary listed as a co-author of the document. the author (turtle) and contributor (human) are who belong on the byline.

### terms

| we say | users say |
|---|---|
| committer of the squash commit | "who merged it" |
| PR author / creator | "who opened it" / "the bot card" |
| `Co-authored-by:` trailer | "co-author" / "contributor" |
| github app installation token | "the app", "the bot" |
| web-flow identity (`GitHub <noreply@github.com>`) | "github itself did it" |

## evaluation

### how well it solves the goal

directly. the three contributors are (hypothesis) author + committer + co-author. we want to keep author (turtle) and co-author (human) and drop the committer-app. the merge identity is the single knob that controls the committer slot.

### pros

- minimal blast radius — a token/identity swap at the merge step, no change to mechanic workflow.
- keeps the app PR-creator that folks like.
- attribution becomes honest and stable.

### cons / costs

- may require a **second credential** (an ehm-seaturtle *user* token) distinct from the app token, OR relying on github web-flow to be the committer. more keyrack surface.
- branch-protection interactions: the merging identity must satisfy required checks/reviews.
- automerge attribution: whoever *enables* `--auto` is the actor when it later completes — so the lever is "who enables automerge", not just "who clicks merge".

### edgecases & pit-of-success

- **multi-author PRs**: github sets squash author to the merger when commits have multiple distinct authors. our commits are single-author (turtle) + co-author trailer, so author stays turtle. ✅ (must confirm the co-author trailer doesn't count as a "distinct author" that flips this.)
- **release PRs** (`rhelease[bot]`): separate identity, separate flow — out of scope, but worth not regressing.
- **direct-merge fallback** (free-tier orgs): `enable_automerge` falls back to `gh pr merge --squash` (no `--auto`). same identity lever applies.

## groundwork

### external research

github attribution rules referenced but **not yet fully verified for the app-installation-token case**:

- squash merge commit gets a fresh author/committer; branch commit committers are discarded.
- known general rule: squash author = the single distinct commit author if one exists, else the merger.
- web-flow merges (UI / standard API) record committer as `GitHub <noreply@github.com>`, which is **not** rendered as a contributor avatar.

⚠️ what i did **not** verify: whether a github-app installation token performing the merge changes the committer from web-flow `GitHub` to the app bot. this is the crux and needs a real post-change squash commit to confirm. **cite-gap acknowledged.**

### internal research (verified against this repo)

- **author identity** — `src/domain.roles/mechanic/skills/git.commit/git.commit.set.sh:677` commits with `--author="$ROBOT_NAME <$ROBOT_EMAIL>"`, `ROBOT_EMAIL="seaturtle@ehmpath.com"` (`:38`). co-author trailer appended at `:671-673` from `git config user.name/email`.
- **PR creation token** — `src/domain.roles/mechanic/skills/git.commit/git.commit.push.sh:380` runs `gh pr create` under `GH_TOKEN=$EHMPATHY_SEATURTLE_GITHUB_TOKEN`, fetched from keyrack `--env prep` (`:275-279`). this is the token the wisher says is now an **app** token.
- **merge token** — `src/domain.roles/mechanic/skills/git.release/git.release.operations.sh:406-413` `enable_automerge()` runs `gh pr merge --auto --squash` under the exported `GH_TOKEN` from `git.release.sh:284`, sourced via the **same** `fetch_github_token` (`git.commit/keyrack.operations.sh`). → **create and merge currently share one token.** this is the structural cause: when that token became the app, the app gained the merge/committer role.
- **keyrack** — `src/domain.roles/mechanic/keyrack.yml:10-11` declares `EHMPATHY_SEATURTLE_GITHUB_TOKEN` under `env.prep` only. a second user token would need a new entry here.
- **empirical baseline** — `git log origin/main`:
  - `1eadc12` (feature PR squash): `Author: Seaturtle of'Ehmpathy <seaturtle@ehmpath.com>`, `Committer: GitHub <noreply@github.com>`, `Co-authored-by: Ulad Kasach`. → **exactly the 2-contributor state we want.** this proves the desired outcome is achievable and is in fact what web-flow merges already produce. the regression is introduced specifically by the app performing the merge.

### what this baseline tells us

the "after" world already existed before the app token. so the fix is essentially: **stop letting the app be the merge identity** — restore the merge to a non-app identity (web-flow `GitHub`, or an ehm-seaturtle user token) while keeping the app as PR creator.

## what is awkward?

- **two tokens for one bot** feels off — having both an "app token" (for creating) and a "user token" (for merging) for the same logical actor is more credential surface and a latent footgun (which one expired? which env?). it fights the mental model of "the seaturtle has one identity."
- **the fix depends on a fact i haven't nailed down** (which slot the app occupies). committing to the two-token design before capturing a real app-merged squash commit risks building on assumption #1. the honest move is to get that one data point first — it's cheap and decisive.
- **automerge timing**: the lever is "who *enables* automerge", not "who merges", because the merge completes asynchronously under the enabling actor. that indirection is easy to get wrong and worth calling out loudly in the design stone.
- if the real answer turns out to be a **`Co-authored-by:` trailer** rather than the committer, the whole "swap the merge token" framing is wrong and we'd instead adjust trailer handling — so the design must stay flexible until validation.

## summary

**outcome**: squash commits credit ehm-seaturtle (author) + human (co-author), no others — app stays a PR creator only.

**confirmed cause (declapract-typescript-ehmpathy PR #509, opened by the app)**: github sets the squash commit **author = the PR opener**. #509's squash commit shows author = `seaturtle-by-ehmpathy[bot]` (the app), committer = web-flow `GitHub` (invisible), and TWO trailers — `Co-authored-by: seaturtle[bot] <seaturtle@ehmpath.com>` and `Co-authored-by: Ulad Kasach`. so the 3 contributors are: the app (squash author, because it opened the PR) + seaturtle (co-author) + human (co-author). the committer is NOT involved (committer hypothesis fully refuted).

**the hard tradeoff (the wish may be infeasible as stated)**: because squash-author = PR-opener, "the app opens the PR" forces the app to be the squash author. under squash, you cannot have BOTH the app as opener AND only seaturtle+human credited. choose one:

- (A) open the PR as the seaturtle USER identity (not the app) → squash author = `seaturtle@ehmpath.com`, + human co-author = 2 contributors. exactly the pre-app behavior (declapract #506; this repo #455). cost: the PR card creator becomes the seaturtle user, not the app.
- (D) keep the app as opener, BUT author the commits with the app's own identity (`seaturtle-by-ehmpathy[bot]`) so opener == commit author. then squash author = app, + human co-author = 2 contributors. keeps the app card. cost: the credited "seaturtle" is the app bot (`seaturtle-by-ehmpathy[bot]`), not the legacy `seaturtle[bot] <seaturtle@ehmpath.com>` user.
- (B) keep the app as opener with the current split identities → 3 contributors (the present bug).
- (C) abandon squash (use merge or rebase) → preserves real commit authors; out of scope per the squash norm.

**the real decision** reduces to: which single seaturtle identity should be credited, and does the app open the PR?

- want the **legacy `seaturtle@ehmpath.com`** credited → option **A** (app no longer opens PRs).
- happy for the **app bot `seaturtle-by-ehmpathy[bot]`** to be the seaturtle → option **D** (app still opens PRs; align `git.commit.set` author to the app identity).

**recommendation**: ask the wisher which seaturtle identity they want on the byline. if they want the app card kept, **D** delivers both (app creator + 2 contributors); if they want the `seaturtle@ehmpath.com` user specifically, **A**. either way, the implied co-author email-on-squash privacy point (`git.commit.push.sh:370-372` strips it from PR bodies for a reason) must be confirmed acceptable.

## DECISION (wisher, 2026-06-26): option D — author derived from the token

the wisher chose **option D** with a refinement: **derive the commit author identity from the app token** so opener == author automatically, for consistency, and so it auto-adapts if the app/token changes.

### the rule (confirmed by github docs + PR #509)

github squash sets **squash-author = PR-opener**, non-configurable. per github community docs: you can only set both author and committer to the pull request submitter; github does not let you set them separately for a squash merge. so with the app as opener under a HARD squash requirement, the author MUST be the app — the only path to 2 contributors is to make the commit author equal the app too.

### the mechanism (verified)

a github App installation token maps to a deterministic bot identity:

- **name**: `<app-slug>[bot]` → `seaturtle-by-ehmpathy[bot]`
- **email**: `<bot-id>+<app-slug>[bot]@users.noreply.github.com` → `295111357+seaturtle-by-ehmpathy[bot]@users.noreply.github.com`

verified: `gh api users/seaturtle-by-ehmpathy[bot]` → login `seaturtle-by-ehmpathy[bot]`, id `295111357`, type `Bot`; matches the exact author email on #509's squash commit.

retrieval at runtime from an installation token:
- app JWT → `GET /app` yields `.slug`
- `GET /users/<slug>[bot]` yields `.id`
- compose email = `<id>+<slug>[bot]@users.noreply.github.com`
- (installation tokens cannot hit `/user`; the slug+id are stable, so cache them.)

### what changes (refined 2026-06-26: branch on token kind)

- `git.commit.set.sh:38,677` — replace the hardcoded `ROBOT_NAME`/`ROBOT_EMAIL` with an identity chosen by the active token's kind:
  - **app installation token** (`ghs_` prefix) → use the app bot identity (`seaturtle-by-ehmpathy[bot]` + its no-reply email), derived from the token.
  - **else (a PAT** — `ghp_` / `github_pat_`) → assume it is the turtle's own PAT → use `seaturtle[bot] <seaturtle@ehmpath.com>`.
- this keeps author == PR opener in BOTH cases: an app-opened PR squashes to the app bot; a PAT-opened PR squashes to the turtle user. either way → **2 contributors**, consistently, with no per-repo config.

### term note (wisher 2026-06-26)

the two seaturtle identities are peers, picked by token kind — NOT old-vs-new:

- **standard** = the turtle's PAT → `seaturtle[bot] <seaturtle@ehmpath.com>`
- **alternative** = the app installation token → `seaturtle-by-ehmpathy[bot]`

### accepted tradeoff

- which seaturtle is credited now follows the token: app token → app bot; PAT → `seaturtle@ehmpath.com`. the wisher accepts this token-driven choice as the consistent behavior.

### co-author: KEEP (wisher confirmed 2026-06-26)

- the human `Co-authored-by:` trailer STAYS on the squash commit — the human must remain credited. this is NOT dropped.
- consequence: the human email rides on the squash commit (the push skill strips it only from PR *bodies*, `git.commit.push.sh:370-372`). the wisher accepts the trailer-on-commit. so the 2 credited contributors = the token-derived seaturtle (author) + the human (co-author).

### still open (carry into design)

- the human `Co-authored-by:` trailer still puts the human email on the squash commit; `git.commit.push.sh:370-372` strips it from PR bodies for privacy. confirm whether the trailer-on-commit is acceptable, or whether it too should be derived/masked.
- exact token-introspection path in the skills (App JWT vs installation token context) — design detail.
