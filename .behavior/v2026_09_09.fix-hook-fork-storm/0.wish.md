# wish: the two forbid-terms hooks fork a storm per edit — cut it

## .what

`pretooluse.forbid-terms.gerunds.sh` and `pretooluse.forbid-terms.blocklist.sh` each fork
dozens of subprocesses on **every** Write and Edit. cut that to a handful, with no change to
what either hook blocks or permits.

after this, a file edit costs the same decision and a fraction of the process count.

## .why

### measured on a live grove, 2026-09-09

`grove-ahbode-v20260901` — 4 cpu · 31G ram, ~17 clones. the cpu roll-up by program:

```
  71.4% cpu · n=8    run.bun.rhachet-run.bc
  63.2% cpu · n=17   claude
  35.5% cpu · n=4    node …bhrain/cli/route
   9.0% cpu · n=62   sh -c
   8.0% cpu · n=1    bash pretooluse.forbid-terms.blocklist.sh
   7.0% cpu · n=1    bash pretooluse.forbid-terms.gerunds.sh
```

**15% of a 4-core box, held by two hooks that decide whether a word is allowed** — plus an
unmeasured share of the `n=62 sh -c`, which is the fork storm itself.

### 🔴 the `pcpu 8%` is the tell, and it reads backwards

`pcpu` is cputime ÷ elapsed. **8% means the hook spends ~92% of its wall time BLOCKED**, not
computing — waiting for forked children to be scheduled. so the cost is not arithmetic, it is
**fork latency under contention**: on a box at `runq 27` every fork queues behind 27 runnable
tasks, and each clone pays that on each edit.

⇒ the hooks get slower exactly when the grove is busiest, which is when an edit most needs to
be cheap. and the load they add is itself part of what makes the queue long.

### the fork counts, per invocation

| hook | forks |
|---|---|
| `blocklist.sh` | ~9 fixed, **plus 3 `jq` per term in the list** — a loop that re-parses the same json once per field, per term |
| `gerunds.sh` | ~10 fixed, **plus 1 per candidate word** — an `echo \| tr` per word, inside an O(n) membership scan |

both re-read and re-parse their word list from disk on every single invocation, though the
list changes approximately never.

⚠️ and most invocations find **no match at all**. the common case pays the full parse before
it learns there was naught to check.

## .acceptance

1. a Write or Edit that trips **no** term forks **under 10 processes total, per hook** —
   measured, with the before and after counts in the yield
2. every term either hook blocks today, it still blocks; every term either permits today, it
   still permits. this is a cost change, never a policy change
3. the HARDNUDGE behavior is unchanged — first attempt blocks, a retry within the window
   passes, and the nudge record keeps its shape
4. the block **messages** are unchanged in substance: the same detected terms, the same
   per-term alternatives, the same rationale line
5. a test covers the equivalence in **both** directions — a known-blocked word still blocks
   and a known-allowed word still passes — and it goes red under a deliberate regression,
   per `rule.require.clamp-edge-cases`
6. the fork count itself is **clamped by a test**, not merely reported once. a count that is
   only measured in a yield drifts back on the next edit to the file

## .the boundary — what is NOT in scope

- **do not change what is blocked.** no term added, none retired, no allowlist edit. a
  behavior change smuggled into a cost change is unreviewable
- **do not rewrite either hook in another language.** node or python would pay an interpreter
  boot per invocation, which is the cost this wish exists to remove
- **do not weaken the checks to make them cheap.** a hook that scans less is not faster, it is
  broken. the gerund scan must still handle camelCase splitting; the blocklist must still
  match the same terms
- **do not touch the other PreToolUse hooks** unless a shared-cost fix genuinely lands there
  too — and if it does, say so plainly rather than expand the diff quietly

## .facts already verified, for the headstart

these were measured directly and can be trusted without re-derivation:

- `blocklist.sh` lines ~116-119 spawn **three** `jq` calls per term, in a `for` loop over the
  term count — one for the term, one for the why, one for the alts
- `gerunds.sh` `is_allowed()` runs `echo "$word" | tr` (~line 77) per candidate word, then
  scans the allowlist array linearly for each
- both hooks call `jq` **three separate times** on the same stdin payload to read
  `.tool_name`, `.tool_input.file_path`, and the content field
- both parse their `.jsonc` list with `sed | jq` on every invocation
- both do this work **before** they learn whether a term matched

## .the HOW is yours — advisory only

per `rule.require.wish-outcome-over-proposal`, `.what` / `.why` / `.acceptance` are
authoritative; every other line here is ground, not instruction.

several shapes could deliver it — one `jq` that emits every field at once, a bash associative
array for membership, a cheap pre-scan before any parse, a cached parse keyed on the list's
mtime, or a merge of the two hooks into one process that shares the fixed cost. **the merge is
the largest single win and also the largest blast radius** — weigh it, and if you take it, say
why in the yield; if you reject it, say that too.

you can see the codebase this wish cannot. a shape it did not imagine that meets the
acceptance criteria is a success, never a deviation.
