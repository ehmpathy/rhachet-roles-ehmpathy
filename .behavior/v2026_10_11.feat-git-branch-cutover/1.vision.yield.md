# vision: git.branch.cutover

## .the contract

```
rhx git.branch.cutover begin --from <@main|@tree|branch> --into <branch> [--pick <sha>]... [--mode plan|apply]
rhx git.branch.cutover continue
rhx git.branch.cutover abort
```

three subcommands, the same vocabulary as `git.branch.rebase` (`begin | continue | abort`). two
direction flags, the repo's own pair (`git.release --from main --into prod`, `mvsafe --from --into`),
**both required** — no default:

- **`--into <branch>`** — the new branch to cut over into
- **`--from`** — where the new branch is cut. the source is always the branch this worktree is on;
  `--from` names the base, never the source

| `--from` | the new branch starts at | `--pick` |
|---|---|---|
| `@main` | fresh `origin/main`, after a fetch (falls back to `origin/master`, a5) | allowed |
| `<branch>` | fresh `origin/<branch>`, after a fetch — e.g. a release branch | allowed |
| `@tree` | this worktree's HEAD — a **stacked** branch, all history kept | refused (inv-13): HEAD already holds every commit |

uncommitted changes come along under every `--from`: they live in the worktree, and the worktree
stays put while the branch beneath it changes. no qualifier selects a part of them — a split
(only staged, say) would have to hide the rest somewhere for the old branch, which a commit
on the source (inv-9) or a hidden ref would do. split before the cutover, by commit or stash.

a cutover is a branch switch **within the current worktree**. a fresh peer worktree is a subtree —
a different feature, `git.tree.subtree` (#918).

one verb moves work off a stale branch onto a fresh branch:

1. **preflight** — fetch `origin` (for `@main` and `<branch>`, the base; for every form, the
   `--into` name check); refuse if `--from` is absent, `--from <branch>` is not on origin,
   `--pick` rides with `@tree`, `--into` exists (local or origin), a sha is unknown or a
   merge commit, any git operation is in flight, the `git.branch.uses` quota is absent, or an
   untracked file sits at a path the new base (or a pick) tracks
2. **cut** — make `<branch>` at the base, **no upstream**, and check it out here. under `@tree`
   the base is HEAD itself, so no file changes: no park, no reset, no carry conflict, no collision
3. **replay** — apply each `--pick` in the order given; drop a pick whose change is already
   on the base (an ancestor sha, a squash-merged sha, or a repeat), and report it
4. **carry** — lay the tracked edits back down, still uncommitted. untracked files never move: they
   sit in place on disk the whole time, so they are present on the new branch untouched
5. **report** — base sha, new branch, each pick old → new, the carried files, the commit level
   the new branch will enforce (explicit bind, or inferred from the new name), and **every commit
   left behind** on the source branch (ahead of the base, not picked). plan shows the same list
   before any mutation. picks are an allowlist: a commit not named stays on the untouched source,
   and the report names it, so no commit is ever dropped out of sight (inv-14)

## .above all — untracked work is never at risk

the wisher's top bound. cutover holds it by construction, not by care:

- **untracked files are never written, moved, or deleted** — not by the cut, the replay, the carry,
  or abort. a branch switch leaves them on disk; cutover adds no step that touches them
- **a collision refuses, never resolves** — if an untracked file sits at a path the new base or a
  pick tracks, preflight halts (exit 2) and names each path. the caller moves it; cutover does not
- **tracked edits are parked, then verified, then reset** — the edits are written into a commit
  object at `refs/worktree/cutover/tree`, and its tree is byte-compared against the worktree *before*
  any reset. a mismatch halts with naught changed
- **the park outlives every failure** — it is dropped only after the edits land on the new branch
  or are restored on the source branch. a crash leaves it in place for `abort`
- **gitignored files are never cleaned** (inv-11)

plan (the default) runs preflight and prints steps 2–4. its one write is the fetch, which
refreshes the origin refs — the same as `git.branch.rebase begin`'s plan; no branch, index, or file
changes.

a conflict halts and names `continue` and `abort`: at step 3 the tree is left mid-pick; at
step 4 the carried files hold conflict markers while the original tracked edits stay parked in a
private ref. untracked files are untouched at every step. it never pushes, never force-pushes, and
never moves or deletes the source branch.

## .the meter — `git.branch.uses` (ships with this tree)

no branch meter exists today, so this tree adds one: a peer of `git.commit.uses`, same shape, same
levels, same grant rules. the human decides whether a mechanic may cut branches; cutover asks.

```
rhx git.branch.uses set --quant 3        # grant 3 cutovers in this repo
rhx git.branch.uses allow                # unlimited in this repo
rhx git.branch.uses block                # revoke (alias: del, set --quant 0)
rhx git.branch.uses get                  # read the grant (mechanic may run)
rhx git.branch.uses --global block       # circuit breaker, all repos
rhx git.branch.uses --org ehmpathy allow # per org; --org @all for the default
```

- **state** — local at `.meter/git.branch.uses.jsonc`; global + org under
  `~/.rhachet/storage/repo=ehmpathy/role=mechanic/.meter/`, beside the commit meter
- **precedence** — global block > org > `@all` > local > unset = blocked (the commit meter's order)
- **spend** — each cutover that cuts a branch in apply spends one unit. plan, `continue`, and
  `abort` spend none; a preflight refusal spends none. `allow` is unlimited
- **who grants** — `set`, `allow`, and the `--global`/`--org` grants are denied to the mechanic in
  `init.claude.permissions.jsonc`, as `git.commit.uses set` is today. `get` is allowed
- **no `--push` flag** — cutover never pushes; push stays under `git.commit.uses`

## .the outcome world

### before

measured 2026-10-11 in `uladkasach/nheuron`. a branch's first `feat` squash-merged, so
`git.commit.set` forced every later commit to `cont:` and the next release could not be a `feat`.
the escape by hand: a rebase, ten conflicts, `rebase --quit`, `switch -c`, a second cut. the
`switch -c ... origin/main` set `origin/main` as the new branch's upstream. every step was a raw git
call off the paved list — a permission prompt each, for a mechanic.

### after

```
rhx git.branch.cutover begin --from @main --into turtle/neuron-graph --pick 5a5a5a5 --pick 6b6b6b6
rhx git.branch.cutover begin --from @main --into turtle/neuron-graph --pick 5a5a5a5 --pick 6b6b6b6 --mode apply
printf 'feat(graph): ...' | rhx git.commit.set -m @stdin --mode apply
```

a plan, an apply, a commit — all paved, zero prompts. the next commit is a `feat`. the old branch sits untouched in case
aught was left behind.

### the aha

the stale branch needs no repair. you leave it. you name what to keep — these commits, this tree —
and step onto clean ground. no rebase, no re-conflict with history main already absorbed: only
the commits you named replay, onto main as it is today.

## .mental model

- **to a friend**: "it moves your work to a fresh branch off main. you pick which commits come
  along. uncommitted stuff comes too."
- **analogy**: a house move. you do not renovate the old house; you pack the boxes you want (picks),
  grab what sits on the counter (the tree), and unpack in the new place (fresh main). the old house
  stays, keys in hand, until you are sure.
- **their words vs ours**

  | they say | we say |
  |----------|--------|
  | "start fresh", "new branch off main" | cutover |
  | "take these commits along" | `--pick` |
  | "my changes" | the uncommitted tree |
  | "undo that" | `abort` |

  `cutover` is the seeds' own word (#528 title, #504 body). `--pick` reuses git's verb, so a
  git user reads it with no gloss.

## .evaluation

### goals

| wish demand | met by |
|-------------|--------|
| cut from `origin/main` after a fetch | preflight + cut; inv-5 |
| carry named commits, in order | replay; case 3 |
| carry the uncommitted tree | carry; case 5 |
| no upstream on `origin/main` | cut with no track; inv-7; case 4 t3 |
| conflict halts with settle + abort commands | cases 6, 7, 9 |
| plan shows base, branch, picks; apply reports what landed | cases 1, 2 |
| never push / force-push / delete old branch | inv-9 |
| refuse when `--into` exists, local or origin | inv-1; case 8 |

### pros

- one verb replaces ~6 raw git calls, each a prompt for a mechanic
- only named commits replay — commits main already absorbed never re-conflict (the nheuron
  ten-conflict rebase replayed the whole branch; a cutover replays only the picks). a pick can
  still conflict with main's own changes (case 6), but that conflict is real, not historical
- the paved upstream rule closes a quiet trap a careful human fell into
- abort is total: the source branch and tree come back exactly

### cons

- a new state machine (`continue` / `abort`) beside rebase's — same words, so a mechanic mid-pick
  may run the wrong verb's `continue`
- picks keep their original author. if the last pick is human-authored, `git.commit.push` refuses
  (its guard reads HEAD's author, `git.commit.push.sh:370-372`) until a seaturtle commit lands on top
- the human must still know which shas to keep; the skill does not suggest them

### edgecases and the pit of success

| edge | contract |
|------|----------|
| run on `main` with accidental edits | allowed: the tree moves off main; main never moves |
| detached HEAD | allowed: the source is reported as a sha |
| a sha twice, or a sha already in `origin/main` | dropped and reported (inv-4); plan marks it "will drop" |
| `--pick a..b` range | refused: one sha per flag, explicit order (see q5) |
| a new cutover while one is halted | refused (inv-6); names `continue` / `abort` |
| `continue` with no cutover in flight | refused (inv-8); names the start command |
| crash mid-cutover | the private tree ref survives; `abort` restores from it |
| an untracked file at a path the new base tracks | refused at preflight, exit 2, each path named; cutover never moves it |
| source had staged files | the content carries; the stage split does not — all carried files land unstaged, and the report says so. a staged/unstaged split is a pre-commit intent; the next `git.stage.add` re-declares it |

## .open questions & assumptions

### assumptions

| # | assumption | evidence |
|---|------------|----------|
| a1 | cutover replays commits but authors none, so it needs no push permission | it never pushes (wish bound) |
| a2 | the private carry ref never collides with a real branch | it lives under `refs/worktree/cutover/`, outside `refs/heads/`, private to its worktree |
| a3 | a drop of an empty pick beats a halt | an empty pick carries naught; the motive incident is exactly this trap (case 10) |
| a4 | `git.commit.set` accepts `feat` on the new branch | `get_closest_ancestor_branch` (`git.commit.operations.sh:2234-2299`) measures from `origin/main`; a cutover with no behavioral pick leaves zero behavioral commits. **exception**: an explicit level bind of `fix` (`.branch/.bind/git.commit.level`, per worktree, so it follows the cutover) or a `--into` name the inference reads as `fix` (`infer_level_from_branch`, `git.commit.operations.sh:1683`) still refuses `feat` — hence the report line |
| a5 | the base is `origin/main` | the wish says so; `git.branch.rebase begin` falls back to `origin/master` (`begin.sh:138-161`). cutover mirrors that fallback rather than assume `main` |
| a6 | gitignored files (`.meter/`, `.branch/`, `node_modules/`) stay put and untouched | they are not part of the tree carry, and a branch switch leaves them; the cut, carry, and abort must never clean ignored files (inv-11) |
| a7 | per-branch state of peer skills is theirs to manage | the route bind is a flag named for the branch (`$route/.bind/<branch>.flag`, observed on this route). per the wisher, cutover ignores it (F7) |

| q7 | the git primitive to drop an empty pick | [answered] avoid a version-bound flag (`cherry-pick --empty=drop` is recent). cutover runs its own pick loop: per pick, a no-commit cherry-pick, then an empty-index check — empty → drop and report; else commit with the source message and author. the same loop holds the resume state `continue` needs, so it is one mechanism, not two |
| q9 | should the route bind follow the cutover to the new branch? | [answered by wisher] ignore it — cutover neither writes nor reports the route bind. fulcrum F7 |
| q12 | is cutover still needed beside `git.tree.subtree` (#918)? | [answered] yes. a subtree is a *parallel* clean tree on `<parent>.<slug>`, cut from the parent's head — it keeps the stale history and carries no picks or tree. cutover *leaves* that history: fresh `origin/main`, named picks only. | q10 | pick the base before or after the fetch? | [answered] after. fetch first, then choose `origin/main`, else `origin/master` (a5) — the rebase peer picks before its fetch, which can misread a fresh clone |
| q8 | does git.commit.push's author guard deserve a carve-out for cutover? | [answered] no, out of scope; noted as a con. a seaturtle commit on top clears it |
| q11 | exit code on a conflict halt: `2` or `1`? | [answered] `2` — the caller must settle files, which `rule.require.exit-code-semantics` names a constraint. the rebase peer exits `1` on a conflict (`begin.sh`, after its conflict block); cutover does not copy that. the rebase divergence is a separate fix, caught as a dream, not smuggled into this verb |

## .what is awkward?

- **one settle vocabulary, two verbs** — `rhx git.branch.rebase continue` and `rhx
  git.branch.cutover continue` read alike. a mechanic mid-pick may run the wrong one. mitigation:
  cutover's halt names its own full commands; and rebase continue, when no rebase is in flight,
  could point at cutover — a scouts-honor touch to weigh in execution, not a promise.
- **abort deletes a branch** — the bound forbids a delete of the *old* branch; abort deletes the
  *new* one it made seconds earlier and never pushed. it is the only delete in the verb. it reads
  sharp, so the report names it.
- **the author guard on push** — a cutover of human-authored commits lands a branch that
  `git.commit.push` will not push until a seaturtle commit sits on top. honest, but a surprise.
- **`--pick` is long** — repeated three times the call sprawls. kept for zero-gloss
  recognition; a short alias is a later call.
