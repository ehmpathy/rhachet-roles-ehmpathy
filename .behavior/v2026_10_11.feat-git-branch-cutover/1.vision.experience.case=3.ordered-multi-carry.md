# case=3: ordered multi-sha carry

**cell** C11 · apply · picks many · tree clean · outcome clean · happy × critipath
**actor** human

## .narrative

a human has three commits to keep, and the second edits a file the first creates. order matters.
they pass the shas in the order they want, which is not the order `git log` shows them. the skill
replays them exactly as given — never sorted, never reordered — and the report lists them in that
same order with each new sha.

## .bdd

```
given('[case3] three picks where pick 2 depends on pick 1', () => {
  when('[t0] cutover runs in apply mode with the shas in a chosen order', () => {
    then('git log origin/main..HEAD lists the three commits in the given order');
    then('each new commit keeps its source message and author');
    then('the report lists old → new for each, in the given order');
    then('exit 0');
  });
  when('[t1] the commit graph is read back', () => {
    then("the new pick 1's parent is the fetched origin/main");
    then("the new pick 2's parent is the new pick 1; pick 3's parent is the new pick 2");
    then('pick 2 applied clean only because pick 1 landed first — a sort would have halted it');
  });
});
given('[case3b] the same three shas, passed in the reverse of their dependency order', () => {
  when('[t0] cutover runs in apply mode', () => {
    then('the skill does not reorder them: it applies pick "2" first and halts on its conflict (case 6 render)');
    then('so the order the caller gives is the order git sees — the invariant is observable');
  });
});
```
