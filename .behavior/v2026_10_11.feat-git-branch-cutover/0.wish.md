wish =

## .what

in `ehmpathy/rhachet-roles-ehmpathy`, add `rhx git.branch.cutover` — one verb that moves the work
on a stale branch onto a fresh branch cut from `origin/main`, so the next release starts clean.

## .the seeds this tree closes

- `ehmpathy/rhachet-roles-ehmpathy#528` — add git.branch.cutover, with cherry-pick support
  🔴 **the primary shape**
- `ehmpathy/rhachet-roles-ehmpathy#504` — grant git.branch.sprout for clean branch cutover. the same
  goal under a second name. close it in favor of #528, or say why it earns a verb of its own

⚠️ `#531` (`git.branch.cutback`, abandon a branch and return to main) is a different goal and is
NOT in this tree.

## .the outcome

- `rhx git.branch.cutover --to <branch>` cuts `<branch>` fresh from `origin/main`, after a fetch
- it carries the work over: named commits via `--cherry-pick <sha>` (repeatable, applied in order),
  and the uncommitted tree when there is one
- the new branch does NOT track `origin/main` — a plain push from it must never aim at main
- a conflict halts with the tree left mid-pick and the exact commands to settle or abort
- plan mode (the default) prints the base sha, the new branch, and each commit it would carry;
  apply mode executes and reports what landed
- tests prove: a clean carry, an ordered multi-sha carry, a conflict halt, a carry of uncommitted
  work, and that the new branch has no upstream on `origin/main`

## .why now

measured 2026-10-11 in `uladkasach/nheuron`: a branch whose first `feat` had squash-merged could
only take a `cont:` commit, so the next release could not be a `feat`. the cutover by hand took a
rebase, ten conflicts, a `rebase --quit`, a `switch -c`, and a second branch cut — and the
`switch -c ... origin/main` left the new branch with `origin/main` as its upstream. every step was
a raw git call off the paved list, each one a permission prompt.

## .bounds

- 🔴 it never pushes, never force-pushes, and never deletes the old branch
- it refuses when `--to` already exists, locally or on origin
