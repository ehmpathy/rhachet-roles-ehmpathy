# 1.vision — a push with no ehmpath bot auth falls back to as-human on its own

## the outcome world

### a day in the life
a clone on a seat with no ehmpath keyrack runs `rhx git.commit.set -m @stdin --mode apply --push`. the commit lands as seaturtle[bot]. the push lands. the pr opens under the seat's own gh login. the tree says why, on one line:

```
   ├─ opened: as-human (fallback: ehmpath bot token unavailable)
```

exit 0. the clone moves to `git.release --watch`. no human reads a guide. no one has to remember `--auth as-human`.

### before / after

| | before | after |
|---|---|---|
| token absent, default auth | push lands, guide, exit 2, a human reruns with `--auth as-human` | push lands, pr opens as-human, exit 0, cause named |
| token refused (403 / not accessible by integration) | raw `pr creation failed` status, exit 2 | one retry as-human, exit 0, refusal named |
| bot auth works | as-ehmpath | as-ehmpath; tree byte-identical; json gains `auth_fallback: null` |
| explicit `--auth as-ehmpath`, token absent | guide, exit 2 | guide, exit 2 |
| explicit `--auth as-human` | as-human | as-human |
| no push quota | refused | refused |

### the aha
the bulletin `auth-as-human-stopgap` retires. the tool already knows the bot auth failed; it now acts on that fact instead of asks a human to.

## the contract

- default (no `--auth`): try as-ehmpath. token absent → as-human. gh refuses the token → one retry as-human. render names cause + auth on the `opened:` line.
- explicit `--auth <mode>`: that mode alone, as today.
- json adds `auth_fallback: null | { cause: "token-unavailable" | "token-refused", detail }`. `token-unavailable` covers an absent key and a keyrack that timed out or failed (`fetch_github_token` returns empty for all three, `keyrack.operations.sh:21-37`); `detail` carries the fetch's captured cause; `auth` names the auth used.
- the composer (`git.commit.set`) forwards `--auth` only when its caller passed one (F1).
- gates, sponsor, quota, open-hours, and the commit author: untouched.

## mental model

- to a friend: "if the bot can't open the pr, it opens it with whatever gh is logged in as, and tells you."
- 🟡 "as-human" names the credential kind (the seat's `gh auth login`), not a person. on a human's seat it is that human. on a clone's seat it is often the clone's own github account, `ehm-seaturtle` (`keyrack.operations.sh:204`). the label is extant and this wish keeps it; the render states the auth kind, never a promise of who.
- analogy: a courier with no badge for one office tower hands the parcel to the tenant at the door, and writes it on the slip.
- their words: "it fell back to my login". ours: `as-ehmpath`, `as-human`, `fallback`. both read the same.

## evaluation

- **goals**: every push opens its pr when any usable credential exists; the identity used is always stated.
- **pros**: one less flag to remember; one less human read per forgotten flag; the explicit path keeps a strict mode for callers who need the bot.
- **cons**: under fallback the pr opener is the human, while the commit author is seaturtle[bot]. squash attribution then follows the human. that gap already exists under `--auth as-human` today; #1192 owns it.
- **pit of success**:
  - the fallback runs one way only, bot → human, and never under an explicit mode (f1, f2 forbidden).
  - gates run before any token read, so the fallback cannot lift one (f3 forbidden, caseE).
  - one retry, never two (f4 forbidden).
  - a non-auth gh failure never triggers the retry (F3), so a protected branch still reports its real cause.
  - both auths fail → the extant two-fix guide, exit 2 (case=6).

## open questions & assumptions

- **[answered]** does "push goes as-human" mean the git transport? no. `git push` rides ambient git creds and never used the bot token (`git.commit.push.sh:469-475`). the fallback moves the pr-open alone. a seat whose git credential helper is gh itself pushes as the seat's gh login, before and after this change alike.
- **[answered]** does an empty token mean absent? no: absent, timed out, or keyrack failed all read empty (`keyrack.operations.sh:21-37`). the cause is `token-unavailable`; `detail` says which.
- **[answered]** what text marks a refusal? gh renders `gh: Resource not accessible by integration (HTTP 403)`, pinned by the peer skill (`git.pull.comment.integration.test.ts:2578`). match on `http 403`, `not accessible by integration`, plus the extant auth signatures (F3).
- **[answered]** can plan mode predict the fallback? no. plan fetches no token and calls no gh; a probe would unlock the keyrack in a preview (F5).
- **[answered]** how does the composer pass "default" through? it forwards `--auth` only when its caller passed one (F1). required, or the fallback never fires through `git.commit.set --push`.
- **[wisher]** does the `opened:` value meet "one line" (F2)? best-guessed yes; clean rework.
- **[wisher]** should a bot-id mismatch fall back too? this vision says no (F4).
- **[wisher]** should explicit `--auth as-human` keep its label `(gh cli login, fallback)`, now that "fallback" also names the auto path (F2)?
- **[wisher]** where does the "open-hours" gate live? none in this repo or its installed roles (`grepsafe 'open.hours|openhours|open_hours'` over `src`, `.agent/repo=bhuild`, `rhachet-roles-bhuild/dist`, `rhachet/dist` → 0 hits). this change edits no gate code, so it holds by construction. verification needs the location to cite it.
- **[research]** none. every external fact the vision leans on is pinned by an extant test in this repo.
- every best-guess sits in `.fulcrums/`, each with a clean rework. no fulcrum blocks the drive.

## groundwork

### external research
- gh cli: `GH_TOKEN` overrides the stored login; with it unset, gh uses `gh auth login`. the extant `run_gh` already relies on this (`git.commit.push.sh:599-608`), and `external.contracts.integration.test.ts` runs the real gh with no credential.
- gh renders an app token's refusal as `gh: Resource not accessible by integration (HTTP 403)`. the peer skill `git.pull.comment` already pins that exact text (`git.pull.comment.integration.test.ts:2578`, its snapshot `:1401`). the F3 predicate matches `http 403` and `not accessible by integration` case-insensitive, so it holds for both the `(HTTP 403)` and `HTTP 403:` forms. no new external dependency.

### internal research
- `git.commit.push.sh`
  - `:48,72-79` `--auth` parse; default from `AUTH_DEFAULT`, no explicit-vs-default signal today.
  - `:499-561` as-ehmpath fetch; empty token → `emit_pr_open_guide`, exit 2. caseA turns this into a fallback.
  - `:651-658,704-708` `is_gh_auth_failure` gates the two-fix guide on pr list and pr create. caseB hooks here.
  - `:741` json carries `auth`.
- `git.commit.set.sh`
  - `:1028-1044` token fetch only under as-ehmpath; empty token → commit author = standard seaturtle[bot]. unchanged.
  - `:1141,1153,1264` passes `--auth "$AUTH"` always → F1.
  - `:1257-1260` threads the token via `SEATURTLE_PR_TOKEN_PREFETCHED/VALUE`.
- `keyrack.operations.sh:136-140` `is_gh_auth_failure` does not match 403 / not accessible by integration → F3.
- `git.commit.operations.sh:934-956` `AUTH_DEFAULT`, `AUTH_VALID_VALUES`, `get_auth_who_label`.
- tests: `git.commit.push.integration.test.ts` stubs gh on `PATH` and drives the token via `EHMPATHY_SEATURTLE_GITHUB_TOKEN`. every extant keyrack-guide case (push case15, 16, 20, 24, 25, 32, 38; set `[t0]` at :530, the day-in-the-life case at :966) passes explicit `--auth as-ehmpath`, so all hold under caseD. default-auth apply cases (push case14b, case18) carry a fake token, so they ride caseC. no extant assertion flips; caseA, caseB and case=6 are new clamps.

## what is awkward?

- two words for one fact: the explicit `as-human` label already says "fallback". F2 leaves it; a rename is a clean follow-up.
- the fallback makes the pr opener differ from the commit author, which is the squash-attribution gap #1192 tracks. this wish neither widens nor closes it.
- the composer had to change how it forwards `--auth` (F1); a reader of set.sh must now know that an absent flag means "fallback allowed".
