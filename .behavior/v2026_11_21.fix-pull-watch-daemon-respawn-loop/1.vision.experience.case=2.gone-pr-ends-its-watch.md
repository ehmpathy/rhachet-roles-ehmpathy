# case=2 · a pr that answers 404 ends its watch, with the rewatch named

covers: E2, E15, E18. sharp · critipath.

## .narrative

clone @:mechanic watched ehmpathy/surf-demo#1221. the repo was deleted, so `pulls/1221` answers 404. (a renamed repo is likely not this case: github's rename docs say it redirects calls to the old name. not yet seen in a live `gh api` reply; the blueprint should check.) today that read counts as a plain fault: the cursors hold, the watch never primes, the idle clock never starts. the watch lives forever, and each tick reads the token and the clone list again.

with the fix, the first 404 of the pull endpoint ends the watch. the clone hears one note:

```
🐢 bummer dude...

🐚 git.pull.watch — #1221 answers 404 (gone, or this token cannot see it); watch ended
   └─ rewatch: rhx git.pull.watch set --which 1221 --mode apply
```

(a new `gone` branch of `as_watch_closure_text`, in the shape of its `idle` branch, `git.pull.watch.alert.sh:217`)

the record leaves once the note is out. if the pr was only hidden from this token (E15), the note says so and names the rewatch; the clone decides.

the note names the token that got the 404, since the fix differs by token. where the grove token served (the seaturtle token was absent or locked), a 404 most likely means the grove token cannot see a private repo, and a rewatch would only 404 again:

```
🐢 bummer dude...

🐚 git.pull.watch — #1221 answers 404 to the grove token (@all.prep.GITHUB_TOKEN); watch ended
   ├─ the pr may be gone, or out of the grove token's reach; the seaturtle token was not granted
   ├─ 1. unlock: rhx keyrack unlock --owner ehmpath --env prep --key EHMPATHY_SEATURTLE_GITHUB_TOKEN
   └─ 2. rewatch: rhx git.pull.watch set --which 1221 --mode apply
```
