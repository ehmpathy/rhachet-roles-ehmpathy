# 1.vision — git.release refuses an unreviewed pr

## the outcome world

a commit quota grants commits and pushes. a merge needs a human's APPROVED review. the clone can
still plan and watch any pr; the moment it asks to merge (`--apply`, `--mode apply`), git.release
reads the feature pr's reviews first. no human approval → exit 2, naught merged, a refusal that
names the pr.

| before | after |
|---|---|
| `--into prod --apply --dirty allow` merged sdk-aws-lambda#79 with zero reviews and published v0.8.0 | the same command exits 2 at the feature pr; #79 stays open until a human approves |
| the only apply gate: commit quota | commit quota **and** a human approval on the feature pr |
| a bot or robot approval would have counted, had there been one | only a human login counts |

the aha: the route can finish, the pr can go green, and the release still waits for the
commander. "done" from the clone means "ready for review", never "shipped".

## the contract

- where: before `enable_automerge` on the feature pr, in apply mode only
- read: `gh api -X GET repos/{owner}/{repo}/pulls/{n}/reviews --paginate` → `user.login`,
  `user.type`, `author_association`, `state`, `submitted_at`, `commit_id`. under `--paginate`,
  `--jq` runs per page (verified: `per_page=1` on #1022 → `1 1 1`), so the read emits flat items
  per page and a separate `jq -s` decides across all of them
- head: `gh api -X GET repos/{owner}/{repo}/pulls/{n}` → `.head.sha`, read once. the gate judges
  that head, and the merge pins it (`--match-head-commit`), so a push after the gate cannot merge
  (F9). an unread head → `💥 MalfunctionError`, exit 1
- fresh = an APPROVED review counts only if its `commit_id` is the head; an older one is stale
- human = not `[bot]` in login, not `type: Bot`, not a seaturtle roster login (F3)
- authority = review `author_association` is OWNER, MEMBER, or COLLABORATOR; a stranger's approval
  on a public repo does not count (F6)
- approved = among humans with authority, some one's latest decisive review (APPROVED /
  CHANGES_REQUESTED / DISMISSED, ordered by `submitted_at`) is a fresh APPROVED, and none's is
  CHANGES_REQUESTED (F2, F9)
- refused → `✋ ConstraintError`, pr number + url + a `why:` line that names the cause (no reviews,
  changes requested, stale, dismissed, only comments, or a discounted approval), to stdout and
  stderr, exit 2; an automerge an earlier run left on is disabled first, so github cannot merge
  behind the refusal (F5)
- head moved between gate and merge → github refuses the pinned merge; `✋ ConstraintError`, exit 2;
  `--retry` does not lift it. the pin is proven against the mock; a live run waits on a sandbox
  write grant (dream `2026_09_26.add-real-gh-contract-test-for-git-release`)
- lease: from the gate's approval until a merge is seen, each watch poll re-reads the head and
  re-runs the judge on fresh reviews; drift, a changes-requested, or a dismissal disarms automerge
  and refuses, exit 2. any other exit (checks red, rebase, timeout, a gh error, ctrl-c, SIGTERM)
  disarms through an exit trap. a failed disarm → exit 1, says automerge is still on. the bound is
  one poll interval (5–15s) (F11)
- the release pr carries no gate (F1), so its merge is explicitly unpinned (`@unpinned`)
- query failed → `💥 MalfunctionError`, exit 1, naught merged
- the rule under both: whenever the gate does not reach "approved" (refused, or read failed), it
  disables any extant automerge before it exits; a failed disable exits 1 and says automerge is
  still on
- no flag lifts it; there is no `--skip-review`; no caller is exempt, human or clone (F4)

## mental model

a friend would say: "the robot can open the pr and get it green, but only a person can press
merge." analogy: a pilot's checklist with a second signature; the copilot (clone) runs every item,
the captain (human) signs before takeoff. the human says "review" and "approve"; we say
"decisive review state" and "robot login".

## evaluation

- goals: each "done when" maps to a row of the walked product; no lift flag exists
- pros: one gate at the one merge site; plan and watch untouched; reuses the extant identity roster
- cons: one more github call per apply; a robot account absent from the roster reads as human
- edge cases held in the pit of success:
  - approval withdrawn → refused (F2)
  - query fails → exit 1, never a silent pass (failhide forbidden)
  - pr already merged → naught left to gate; extant path
  - automerge already enabled on an unreviewed pr (by an earlier run): the gate disables it, then
    exits 2 (F5). branch protection stays the server-side backstop; this gate is the client-side one
  - a push or a revoked approval after automerge is on: github keeps automerge for a push with
    write access. the lease disarms within one poll and on every exit short of a merge; SIGKILL, a
    push from outside git.release, and a repo with no required checks stay with the org ruleset
    ("dismiss stale approvals") (F11)
  - clones' own instructions: `rule.require.git-release-confidence` says a review-gate refusal means
    stop and hand the pr to the human, never retry or reflag

## root cause vs this gate

the root: the clone's token can merge, and repos like sdk-aws-lambda carry no review rule. this
gate stops git.release, not a raw `gh pr merge`. the root fix is an org ruleset that requires an
approval — an admin act outside this repo, caught as
`dreams/v2026_11_15.reseed.org-ruleset-requires-human-approval.md`. this gate is defense in depth
on the path that fired.

## what is awkward?

- the gate sits on the feature pr while the release pr merges ungated (F1)
- the robot roster is a hand-kept list; a new clone account slips past until added
- the refusal path mutates the pr (disables automerge) to keep its own promise; a refuse-only path
  that writes is unusual (F5)
