# 1.vision — fix arch fundamentals

## .the wish, in one line

teach architects and mechanics what an invariant is and why it matters, and give them the enforcements that hold one: the abstraction tactics (ours first, the canon second) and the transactional patterns our repos actually need. what only the world can keep, it names as an assumption, holds with evidence, and enforces by assertion: detect the break and fail fast. each call is laid out for the wisher to adopt or reject.

## .the outcome world

**before.** "invariant" appears in 12 briefs and no brief defines it, nor says why it matters. a clone learns each enforcement in isolation — `IsoPrice` for money, a unique key for findsert, a status edge for a task — and never the thread that ties them: each one keeps an invariant. so the next new rule (a minor needs a waiver; a reservation must not exceed stock) gets a scattered guard, and the path that lacks the guard ships the defect.

**after.** a clone meets short say briefs at boot:

- **I01 `define.invariant`** (both roles) — *what*: a statement about the domain that must hold in every scenario a reader can observe. *why*: it is the definition of correct; without it a defect is found only when production breaks it. one of three constraints (invariant, assumption, guarantee); every constraint has an enforcement, structural or operational
- **I06 the software taxonomy** (architect) — operations research (optimization; solvers) vs information logistics, which splits into transactional (live writes) and analytical (reports over history). an architect names which kind it designs before it picks a tool
- **six forbids** (architect, I18–I23) — each bites on one antipattern and names its cure: a guard in one caller · check-then-write · pii egress · a hand-rolled search over scarce resources · an analytical scan on the live store · an unstated assumption
- **I28 `rule.forbid.test-edit-without-named-proof`** (mechanic) — a red test turns green by an assertion edit only when the edit names what the test proves: an implementation contract (glue — most tests; no inventory entry) or a domain invariant. not every test needs an invariant; every test needs a named proof

the depth boots as ref: invariant before operation (I02), the enforcement ladder, earliest first (I04), composition with seam tests (I05), the abstraction philosophy (I07), the abstraction tactics (I08), the transactional patterns (I09), pii quarantine (I17), assumptions with evidence and a required response to each break (I24), the inventory howto and its templates (I25), the history with citations (I26), why invariants are the source now that robots write the code (I27), the converge/contrast term pair (I29), and the heart under all of it: a constraint shrinks the space the system can reach, and every benefit follows from that (I30).

**a day with it.** a mechanic adds gift vouchers beside online signup. before it writes a hold it asks: *which constraint, and how is it enforced?* — *every lesson reservation carries the consent its surfer requires on the lesson date*. the dao masks the birth date into that concept (`SELF` or `PARENT`), so no pii enters the domain; the `LessonReservation` domain object enforces the invariant, and `setLessonReservation` is the one write path. no path forks on age (case 1). an architect who designs `setLessonReservation` writes *reserved boards never exceed stock* first, then walks every writer of that state and maps each break path to one enforcement: a unique key, a version check, a status edge (case 2). the invariant sits, declarative, in the subdomain's `inventory.of=invariant`; the walk sits in the route's review, where a writer with no enforcement is a gap the route closes. a reviewer asks each change one question: *which constraint, and how is it enforced?*

**the aha.** the wisher's t21: *"proof against invariants is the fundamental; mathematical proof via induction is one mechanis. boundary tests is another."* the invariant is the spec. a type, an abstraction, a store constraint, a transaction, a test — each is one way to enforce it, picked by the cost of failure. and an abstraction is where an invariant lives: name the abstraction and you name its enforcement. what the world must keep, we cannot make hold — so we name it an assumption, and enforce it by assertion: its break is seen at once and fails fast.

## .mental model

| a clone would say | we say |
|---|---|
| "the rule that must stay true" | invariant (I01) |
| "what keeps that rule from a break" | enforcement (I04) — structural (by compilation: a type; by abstraction: a domain object, a store constraint, a transaction) or operational (a test; an assertion at runtime; a monitor) |
| "we trust the world on that one" | assumption (I24) — evidence, blast radius, the required response to a break |
| "the tests that poke the edges" | clamps (`rule.require.clamp-edge-cases`) |
| "keep each part's promise small" | additive composition (I05) |
| "it worked alone, broke together" | an untested seam (I05) |
| "a wrapper that hides the mess" | an abstraction, which holds an invariant (I07) |

analogy: the invariant is the load a bridge must hold; the enforcements are its members — some cheap and everywhere (types), some heavy and placed only where the load demands (a saga, a lock). the wisher's t24 stays true: the bounds belong to the domain. the description only decides whether we find them by a crash or by a map.

## .evaluation

**goals met.** every lesson traces to a wisher turn, a verified source, or a practice this repo already ships. the wisher can disagree row by row (`ruled` cells) and call by call (fulcrums). the two calls the wisher ruled in review (no loop focus; ours-first abstraction) are recorded in their rows and fulcrums.

**pros**
- names a term the repo already leans on but never defined, and says why it matters
- ties extant tools to one idea: each ehmpathy abstraction row names the invariant it keeps
- the abstraction tactics rest on 35 sources across five decades, ours first
- the transactional list keeps only what a common invariant in our repos needs
- the history rests on 41 browser-fetched sources, and the robot-era brief on 18 more, each graded ✅ / ☑️ / 🟡
- both boots stay under cap, measured: architect 13,883 / 15,000, mechanic 29,197 / 30,000

**cons**
- 86 inventory rows are a real review load; the blanket line (case 8) is the relief
- 🟡 sources remain: ousterhout's and evans's book text (paraphrase pages only), clean code's stepdown rule, and the seven transactional texts. each needs a fetch before a brief cites it
- I01 ships as a twin in two roles; the twins can drift unless one cites the other

**edge cases, and how the contract holds**
- an unruled row → it takes the inventory's blanket if the wisher set one (case 8); else execution halts that row and asks (case 6; fulcrum F07)
- a ruled say brief that busts the cap → the budget test fails loud (case 7)
- a domain where no whole invariant exists → decompose to local invariants, test the seams (case 4)
- a 🟡 citation that fails its fetch → dropped from the brief, never shipped on recall

## .what is awkward

- **86 rows to rule.** a long table invites a skim. the `.the read across` at each inventory's foot and the blanket line atop it let the wisher rule only the rows they dispute (case 8)
- **"enforcement" now carries two senses in the briefs.** every rule brief ends in an `.enforcement` section that grades a violation; the new term names what holds a domain constraint true in code. context separates them — a section title vs a noun in prose — but a reader may trip once. "guard" stays reserved for the antipattern (a guard in one caller)
- **most abstraction tactics are already practiced, under other names.** the new brief's value is the thread — each tool keeps an invariant — not new tools. a reader who knows the tools may find it obvious; a reader who does not will find it a map
- **the transactional line between core and situational is a judgment of our repo mix.** saga and outbox sit one rung down; a repo with many services would put them in core (F09)
