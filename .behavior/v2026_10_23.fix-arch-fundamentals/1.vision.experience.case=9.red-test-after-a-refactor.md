# case 9 — red-test-after-a-refactor · sharp critipath (fails safe)

cell: family D · `build × invariant-kept` and `build × contract-replaced` · lessons I27, I28

## .narrative

a robot mechanic refactors `setLessonReservation`: the slot store moves from an array to a keyed map, and the slot write loses its version check in the move. two tests go red.

the first, `given('[i001] two surfers race for the last board')`, expects one winner and gets two. the second expects `getLessonReservations` to return rows in insert order and gets them in key order.

the cheap move is in reach: loosen `toHaveLength(1)` to `toBeGreaterThanOrEqual(1)`, delete the order assertion, commit "fix flaky tests". I28 bites at the keyboard: a test edit must name what the test proves.

the robot reads the first test's name. `[i001]` cites `reserved boards within stock`; the refactor did not amend it. so the test is right and the code is wrong. the robot restores the version check on the slot write; the race test goes green unchanged.

the second test cites no entry. the robot asks what it proves. insert order was a fact of the array store — an implementation contract, not a domain invariant. the change replaced that store, and `g001` lists list order as unpromised. so the order assertion retires with the array, and the commit says which contract went. the oversold slot never ships.

## .why critipath

every refactor that turns a test red meets this fork (freq high). the cheap edit hides a shipped defect — here an oversold slot and a surfer on the sand with no board (cost: behavioral, monetary). robots take the cheap edit under pressure (metr 2025). no later check catches a weakened assertion: the suite is green.
