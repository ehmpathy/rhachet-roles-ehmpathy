# inventory: abstraction tactics

## .the ask

the wisher pasted dijkstra's line: *"Therefore I present our recent knowledge of vital abstraction patterns as the fourth argument."* and then set the scope: abstraction tactics as they are known today, ours first, the wider canon second. dijkstra adds one philosophy (the precision argument), and no more.

## .what abstraction is

a name for **what** a concept means, over a hidden **how**, so the caller reasons at the new level and need not look below. six sources converge on it (`appendix/research.abstraction-tactics.md`, `.what abstraction is`):

- access without detail (wikipedia, abstraction (computer science)) ✅
- a named unit, used with no knowledge of its implementation (sicp 1.1) ✅
- a barrier between use and representation (sicp 2.1.2) ✅
- a type defined by its behavior, not its shape (liskov & zilles 1974, via wikipedia) ✅
- a module that hides one design decision from all others (parnas 1972, via acolyer) ✅
- *"not to be vague, but to create a new semantic level in which one can be absolutely precise"* (dijkstra, EWD 340) ✅

**the link to the invariant**: an abstraction is where an invariant lives. `IsoPrice` keeps *money is never a float*. a `DomainEntity` keeps its unique key. a dao keeps *writes converge on retry*. name the abstraction and you name the enforcement of the invariant; leak through it and the invariant has none.
