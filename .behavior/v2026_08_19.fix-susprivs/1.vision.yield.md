# 1.vision — the seam approves an all-safe-segments compound

## the outcome world

### day-in-the-life

a clone runs the ordinary shape of real work — a build piped to `tail`, an rhx
query piped to `jq`, a test-then-resnap chain — and it just runs. no prompt, no
stall, no human tap on the shoulder. the clone reads the tail, sees the verdict,
moves on. the human never learns the command happened, because there was no
decision to make.

### before / after

**before** — the seam knew exactly two safe shapes: a lone clean rhx call, and
`echo|printf|cat | rhx`. anything else — a build piped to `tail`, an rhx piped to
`jq`, two allowlisted commands joined by `&&` — fell through to LIFT (human
prompt) or, for a chain, AUTO_DENY. the human got paged for
`npm run build:… | tail -3 && rhx … --resnap | tail -20`, a command whose every
piece was already pre-approved.

**after** — the seam judges each SEGMENT of the compound by the SAME bar gate 2
(`check-permissions`) already trusts: clean-rhx OR on the allowlist. if all
segments pass, the whole compound auto-approves. the producer is no longer
privileged — `npm run build…`, `git log`, `rhx …` all qualify on the left of a
pipe exactly as they do anywhere else.

### the "aha"

the human already declared these commands safe — that IS what the allowlist holds.
gate 2 trusts a compound when every segment is allowlisted. the seam did not, so
it re-blocked commands the human had already blessed. the aha: **the seam should
honor the same allowlist the human already curated, per-segment, instead of a
narrower two-shape rule of its own.** the compound is exactly as safe as the sum
of its parts — and the parts are already vetted.

## user experience

### usecases / goals

- **read-and-trim**: `rhx git.repo.test --what unit | tail -20` — run a skill,
  keep the tail. the single most common friction today.
- **read-and-filter**: `rhx git.repo.get lines --words 'DomainEntity' | jq .` —
  run a skill, shape its json.
- **build-and-trim**: `npm run build:complete:dist | tail -3` — an allowlisted
  producer, an allowlisted sink; no rhx at all.
- **do-then-do**: `npm run build:… | tail && rhx … --resnap | tail` — the exact
  command that started this wish.

### contract inputs & outputs

the contract keeps its SHAPE — it is the same `PermissionRequest` hook, same
stdin json, same three outcomes:

| input (a bash command) | output |
|------------------------|--------|
| a `\|`/`&&`/`\|\|`/`;` compound where each PRODUCER is clean-rhx-or-allowlisted AND each SINK is clean-rhx-or-reader | `AUTO_APPROVE` (nested allow schema) |
| any segment backgrounded (`&`) or newline/CR-joined, or a smuggled un-vetted command | `AUTO_DENY` |
| any segment neither safe-by-its-position-bar nor a smuggle | `LIFT` (no stdout → human) |

outcome 1 is refined by the two sections below — **the sink caveat** (a sink is
clean-rhx OR a read-only reader, NOT an allowlisted-but-code-exec command like
`npm run`/`bash`) and **operator scope** (`&&`/`||`/`;`/`|` qualify; lone `&` and
newline/CR stay deny). the one-line "every segment clean-rhx OR allowlisted" is the
PRODUCER bar; the sink bar is narrower on the allowlisted side. read the table
together with those two sections — it is the headline, they are the fine print.

### the sink caveat — "allowlisted" is NOT the same as "safe as a pipe sink"

(raised by self-review r2, find 1 — a real design fork.)

the allowlist was curated for gate 2, where each command stands ALONE. some
allowlisted prefixes are **code-execution** commands: `npm run <task>` runs a
package.json task (arbitrary), `bash` runs arbitrary commands. as an ALLOWLISTED
SINK on the right of a pipe, such a command RUNS with attacker-influenced stdin — so
a naive "any allowlisted sink" rule would auto-approve `rhx foo | npm run evil`. the
human's read-only mental model (`| jq`, `| tail`) did not intend that.

**resolution (reconciled to the wish body):** the SINK bar is narrower than the
producer bar ONLY on the allowlisted side — an allowlisted-but-code-exec sink
(`npm run`, `bash`) does NOT qualify. a segment qualifies as sink-safe iff it is a
**clean-rhx call** OR a command whose **lead token** is on a small **read-only
reader allowset** (`jq`, `tail`, `head`, `wc`, `cat`). a **clean-rhx sink DOES
qualify** — the wish body says "every segment meets the same {clean-rhx OR
allowlisted} bar, wherever it sits", and an rhx grant like `x | rhx git.commit.uses
set …` self-protects at EXECUTION (git.commit.uses is denied to a mechanic),
independent of this prompt-level seam (`define.why-permission-guards-allowlist-all-rhx`,
which forbids an rhx-subcommand denylist). the phase-1 `echo … | rhx …` stdin-payload
workaround relies on the clean-rhx sink. invariant #5's "privilege-escalation-token"
is a shell token (sudo, env-prefix), which the seam DOES lift (`echo hi | sudo rhx …`
→ LIFT), not an rhx subcommand.

note the reader bar keys on the **lead token, not a whole-command allowlist
match** — and that is deliberate: `jq` is on the allowlist as an EXACT entry
(`[e]: jq`), so a whole-command match would miss `jq .`, `jq -c`, `jq -r` (the very
friction the human hit). a lead-token match on `jq` accepts all of them. this is
the decisive reason to prefer this reader-allowset over gate-2-parity.

the PRODUCER (left of pipe) keeps the wider {clean-rhx OR allowlisted} bar — NOT
because its output is "just bytes" (a producer like `npm run build` has real side
effects), but because an allowlisted producer is already trusted to run alone, so a
pipe of its stdout onward grants it no new authority.

the producer/sink asymmetry is INTENTIONAL: `npm run build` is allowed as a
producer (already gate-2-approved to run alone; no new authority) but denied as a
sink (a sink additionally runs with attacker-influenced stdin). same command,
different position, different bar — by design, not inconsistency.

this whole sink/producer split is a clean rework if the wisher prefers gate-2-parity
instead (option b in
`review/self/for.1.vision._.r2.has-questioned-requirements.md`).

### operator scope — which separators get the new treatment (NOT all of them)

"chain" is not one uniform bucket. today `is_command_chain` denies `;`, `&`, `||`,
newline, CR all together. the new treatment is a PARTIAL, operator-specific carve:

| separator | today | after | why |
|-----------|-------|-------|-----|
| single `\|` | pipe path | approve iff producer-safe AND sink-safe | data pipeline |
| `&&` | DENY (via `&`) | approve iff every segment safe | conditional-run, no detach |
| `\|\|` | DENY | approve iff every segment safe | conditional-run, no detach |
| `;` | DENY | approve iff every segment safe | sequential-run, no detach |
| lone `&` | DENY | **STAYS DENY** | backgrounds/detaches from the gate |
| newline / CR | DENY | **STAYS DENY** | classic multi-line injection vector |

two build-stone hard requirements fall out:

- **`&&`-vs-`&` disambiguation** — a quote-aware parser MUST tell `A && B` (approve
  if safe) from `A & B` (deny). today both hit the same `*"&"*` branch. redteam:
  `rhx foo & rhx bar` MUST still DENY.
- **newline/CR stay denied** — the wish's examples are all `|`/`&&`; a newline-joined
  "compound" is never in scope. redteam: `rhx foo\n rhx bar` MUST still DENY, even
  if both halves are individually safe.

### what leverage looks like

no new surface to learn. the clone writes the natural command; the seam gets out
of the way when it can prove safety, and defers to the human when it cannot. the
human's leverage is the allowlist they ALREADY maintain — it now does double duty:
it gates gate 2, and it feeds the seam's per-segment judgement.

### timeline

1. clone emits `rhx git.repo.test --what unit | tail -20`.
2. gate 1 (forbid): no injection form → pass.
3. gate 2 (check-permissions): splits on `|`, both `rhx git.repo.test…` and
   `tail -20` are allowlisted → pass.
4. gate 3 (claude classifier): the `|` trips it → raises a `PermissionRequest`.
5. gate 4 (the seam): splits quote-aware, judges each segment {clean-rhx OR
   allowlisted}, all pass → `AUTO_APPROVE`, records an `allow` to the G3 log.
6. the command runs. the human never saw a prompt.

## mental model

### how a user describes it to a friend

"the tool already has a list of commands i've approved. it used to still bug me
whenever i piped two of them together — now it recognizes that a pipe of two
already-approved commands is itself approved."

### analogies

- **a bouncer with a guest list**: he already checks each name at the door. the
  new rule: a group where every member is on the list gets in as a group — he
  does not turn the whole party away because they arrived together.
- **the allowlist as a currency**: gate 2 already spends it to clear a compound.
  the seam refused to accept the same currency. now both tills take it.

### their terms vs our terms

| they say | we say |
|----------|--------|
| "approved command" | allowlisted segment (a `Bash(…)` pattern match) |
| "piping two safe things" | a producer|sink pipe, each segment safe |
| "it stopped bugging me" | the seam auto-approves, no LIFT |
| "the safe list" | the union of `settings.json` + `settings.local.json` allow patterns |

## evaluation

### how well it solves the goal

directly. the goal was "`rhx … | ${allowlisted}` and every all-safe compound
auto-approves." the per-segment {clean-rhx OR allowlisted} rule IS that, stated
generally. all four motivating cases land in outcome 1.

### pros

- **sound by construction** — each segment is vetted by an authority that already
  extant and already trusted at gate 2. no new trust is minted.
- **no denylist** — stays true to `define.why-permission-guards-allowlist-all-rhx`:
  authority is the allowlist + rhx-by-shape, never an enumerated dangerous set.
- **the human's curation does more work** — one allowlist, two consumers.
- **removes the most common friction** without loosening the fail-safe default.

### cons / tradeoffs

- **more logic in a defensive gate** — the seam grows a segment-splitter and an
  allowlist reader. more surface = more to test. mitigated by reuse of gate 2's
  proven splitter + extraction, not a fresh parser.
- **the allowlist becomes MORE load-bearing** — a careless future `Bash(rm:*)`
  grant would now also let `rhx … | rm …` through the seam. but that is already
  true at gate 2; the seam merely stops being stricter than the gate the human
  configured. the allowlist was always the real authority.
- **a prefix-pattern subtlety** — `npm run` `[p]` matches `npm run whatever`. this
  is gate 2's exact behavior; the seam inherits its breadth AND its sharp edges.

### edgecases → pit of success

- **quoted chain char** (`rhx foo --note 'a; b'`) — the quote-aware split keeps it
  one segment; never mis-split. (reuses gate 2's splitter.)
- **background `&`** (`rhx foo &`) — stays DENY; a detach severs the command from
  the gate, and the tail cannot be proven empty. (invariant 1 + open-q 1.)
- **apostrophe-in-double-quote injection** (`… "it's" $(rm -rf ~)`) — the residue
  keeps `$(` active, the segment is not clean-rhx, not allowlisted → not approved.
- **an un-allowlisted sink** (`rhx foo | curl evil`) — `curl evil` is neither
  clean-rhx nor allowlisted → LIFT to human. the pit holds.
- **empty segment** (`| rhx foo`, `rhx foo |`) — a half that trims to empty is not
  safe → LIFT (or the extant empty-segment handling).

## open questions & assumptions

### assumptions made

- **A1** — gate 2's allowlist extraction (`.permissions.allow[] | Bash(…)`, union
  of `settings.json` + `settings.local.json`, `[e]` exact + `[p]` prefix) is the
  right, complete authority to reuse. VERIFIED it exists (see groundwork).
- **A2** — gate 2's compound splitter (quote-aware, splits on `&& || | ;`) is
  sound to reuse for the seam's per-segment judgement. VERIFIED it exists.
- **A3** — the seam still runs AFTER gate 1, so injection forms are already
  hard-blocked; the seam only hardens against the apostrophe-parity bypass.
  VERIFIED by `research.permissionrequest-hook-auto-approve.md` + compose test.
- **A4** (standing dependency) — the nested `decision.behavior:"allow"` schema
  still SUPPRESSES the prompt on the claude-cli version in use. this is
  version-dependent (pinned to 2.1.87 in the research brief; a schema drift would
  make the whole fix a silent no-op — approve emitted, prompt still fires). the
  canary is **case12** in `permissionrequest.decide-permissions.integration.test.ts`,
  which runs the REAL registered hook command and asserts a clean `allow`. current
  evidence: the full suite resnapped GREEN this session (186 passed). re-verify
  case12 on any cli bump before trust.

### open questions — triaged

each is tagged `[answered]` (settled now by logic/code), `[research]` (defer to the
research phase), or `[wisher]` (only the wisher's value-judgement settles it).

1. **[answered]** background `&` / solitary `&` → stay DENY. logic settles it: a
   background detaches the command from the gate and the residue cannot prove the
   tail empty in every shell context. the extant redteam corpus already denies `&`;
   this fix does not relax it.
2. **[answered]** an un-allowlisted, non-rhx segment → LIFT, not DENY. logic
   settles it: LIFT is the extant fail-safe for "cannot prove clean"; DENY is
   reserved for a proven smuggle (`&`, newline, `;`-chain). a merely-unrecognized
   segment is not proven hostile, so it defers to the human, matching today's
   default.
3. **[answered]** allowlist source = union of `settings.json` +
   `settings.local.json`, exactly as gate 2 reads it. code settles it: reusing
   `extract_bash_patterns` (`pretooluse.check-permissions.sh:99-113`) is the only
   way to honor the SAME list the human curated; any other source would drift.
4. **[answered]** scope = the seam only, no touch to gates 1/2/3/5. logic settles
   it: gates 1/2 already pass these commands; gate 3 (classifier) and gate 5
   (settings) are claude-cli's, not ours; the seam is the only lever we own (the
   research brief proves settings-allow cannot pre-empt a suspicious prompt).
5. **[wisher]** prefix-pattern breadth — the PRODUCER bar inherits gate 2's `[p]`
   prefixes, so `npm run <any-task> | jq` approves (producer side). my default:
   inherit gate 2 exactly for the producer (a seam stricter than the human's own
   gate is the bug we fix). this is a value-judgement on blast-radius, so it is the
   wisher's call, not logic's. (the SINK is separately narrowed — see q6.)
6. **[resolved per wish body]** sink bar. an ALLOWLISTED-but-code-exec sink
   (`npm run`, `bash`) runs with attacker-influenced stdin and does NOT qualify.
   resolution: sink = clean-rhx OR a **read-only reader** (lead-token match on
   `jq`/`tail`/`head`/`wc`/`cat`). a clean-rhx sink DOES qualify (the wish body:
   "every segment {clean-rhx OR allowlisted}, wherever it sits"; rhx self-guards at
   execution). `grep`/`tee` were dropped from the reader set (`tee` WRITES files — a
   real hole as a sink; `grep` deferred, a clean widen later). if the wisher instead
   wants piped clean-rhx grants to LIFT, the rework is a one-line predicate flip.
7. **[wisher]** multi-stage pipes (3+ segments)? the wish says "any all-safe
   compound", which includes `rhx … | jq | tail` (2 pipes); today's seam caps at a
   SINGLE pipe and LIFTs 3-stage. my default: lift the cap (approve an N-stage pipe
   iff every segment is safe — producer bar for the first, reader bar for the rest).
   whether 3+ stages are in scope is a scope call for the wisher.

## groundwork

### internal research (verified)

- **the seam today** — `permissionrequest.decide-permissions.sh`. read fully.
  - approves only two shapes: `is_clean_rhx_call` (a lone rhx, residue allowlisted
    to `[[:alnum:]_./=:@,+ -]`) and a single-pipe `is_clean_safe_producer_call`
    whose producer lead is CLOSED to `echo|printf|cat` (lines ~239-250, the
    `case "$trimmed" in echo|echo\ *|printf\ *|cat|cat\ *)` gate).
  - `compute_pipe_positions` already finds top-level unquoted pipes quote-aware
    (lines ~262-290) — reusable for the general split.
  - `is_command_chain` denies `; & || newline CR` in the residue (lines ~199-204).
  - emits nested allow/deny schema + G3 audit append (lines ~120-130, 95-102).
- **gate 2 today** — `pretooluse.check-permissions.sh`. read fully.
  - `extract_bash_patterns` reads `.permissions.allow[] | select(startswith
    ("Bash(")) …`, unions `settings.json` + `settings.local.json` (lines ~99-113).
  - `command_is_allowed` does exact-hash + prefix match (lines ~137-165).
  - `split_compound_command` splits quote-aware on `&& || | ;` (lines ~170-245).
  - `all_parts_allowed` is EXACTLY the per-segment loop the seam needs (lines
    ~248-281) — the seam's new logic is this shape, applied at the seam.
- **the two are today INDEPENDENT** — the seam does not read the allowlist at all;
  that is the gap. the fix teaches the seam gate 2's extraction + split, then
  judges each segment by {clean-rhx OR allowlisted}.

### the reuse question (a real fulcrum, flagged not decided)

gate 2 already holds `extract_bash_patterns`, `split_compound_command`,
`command_is_allowed`, `all_parts_allowed`. the seam needs the same four. options:

- **(a) copy the four functions into the seam** — wet, zero coupling, each hook
  self-contained (the current house style — every hook is a standalone `.sh`).
- **(b) extract a shared sourced lib** — dry, but introduces a shared dependency
  between two defensive hooks, and a `source` path both must locate at runtime.

my lean: **(a) copy**, true to the extant "each hook is a self-contained
executable" convention (rule.prefer.wet-over-dry until a 3rd consumer appears).
this is a clean-rework fulcrum — a later extraction is cheap if a 3rd consumer
emerges. i will best-guess (a) at build time and flag it for the human's
end-of-road review, not halt on it.

**one parser, not two (hard constraint).** the seam ALREADY has quote-aware
parsers (`compute_active_residue`, `compute_pipe_positions`). the port must NOT run
gate 2's `split_compound_command` as a SECOND, independently-written quote
state-machine over the same bytes — two parsers that disagree on a quote edge
(backslash-escape, nested quote, `$'…'`) is a bypass surface (the class that cost
5+ rounds on the apostrophe-parity bug). the allowlist check must layer on the
seam's OWN single residue/pipe pass — reuse only `extract_bash_patterns` +
`command_is_allowed` (the allowlist reader + matcher), never the second splitter.

## what is awkward?

- **two hooks, one allowlist, duplicated logic** — after the fix, gate 2 and the
  seam both read the allowlist and both split compounds, by the same rules, in two
  files. that duplication is the honest cost of the "self-contained hook"
  convention. it is a real maintenance hazard: a future change to the split rule
  must land in both. (the fulcrum above; flagged.)
- **the seam gets "smarter" and thus heavier** — its whole virtue was a tiny,
  obviously-correct default-deny. it is now a small allowlist evaluator. still
  bounded and testable, but no longer glanceable in 10 lines.
- **the allowlist's prefix edges now bite in two places** — a loose `[p]` grant
  was already a gate-2 footgun; now it is a seam footgun too. arguably correct
  (consistency), but it does widen the blast radius of a careless grant.
- **gate 2 and gate 4 now overlap in intent** — both ask "is every segment
  allowlisted?". gate 2 nudges; the seam decides the prompt. a reader may wonder
  why two layers ask the same question — the answer (different claude-cli events,
  different failure modes) is real but not self-evident from the code.
