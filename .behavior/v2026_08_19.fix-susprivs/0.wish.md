# wish: the seam auto-approves a compound whose every segment is independently safe

## .the desire

when i run a compound bash command whose EVERY segment is independently safe, the
`PermissionRequest` seam (`permissionrequest.decide-permissions.sh`) must
**auto-approve** it — never lift it to a human, never deny it.

"independently safe" for a segment means EITHER:

- a **clean single rhx / npx-rhachet call** (the shape the seam already approves), OR
- a command that **fits the pre-approved allowlist** — the exact same allowlist
  `pretooluse.check-permissions.sh` (gate 2) already reads from
  `.claude/settings.json` + `settings.local.json` (`Bash(…)` patterns, both exact
  `[e]` and prefix `[p]`).

if every segment passes that bar, the whole compound is safe by the same logic
gate 2 already trusts — so the seam should agree instead of a block.

## .the cases i want fixed (these MUST auto-approve after the fix)

```
rhx git.repo.test --what unit | tail -20
rhx git.repo.get lines --words 'DomainEntity' | jq .
npm run build:complete:dist | tail -3
npm run build:complete:dist | tail -3 && rhx git.repo.test --what integration --resnap | tail -20
```

every piece of each — `rhx …`, `npm run build…`, `tail`, `jq` — is already on the
allowlist. today the seam LIFTS or DENYs them because it only knows two shapes
(a lone rhx call, or `echo/printf/cat | rhx`). i want it to also recognize
`rhx | <allowlisted reader>` and, more generally, any all-safe-segments compound.

## .the shape, concretely

- **pipes** — `rhx … | jq`, `rhx … | tail`, `npm run … | wc -l`, `git log | tail`:
  auto-approve when the producer is safe AND the sink is safe. **either side** may
  qualify as safe by an allowlist match OR as a clean rhx call — the producer no
  longer has to be rhx (nor the old `echo/printf/cat` set); an allowlisted
  producer like `npm run build…` or `git log` qualifies on its own.
- **chains** — `A && B`, `A ; B`, `A || B`: auto-approve when EVERY segment is safe.
- **mixed** — `npm run … | tail && rhx … | tail`: auto-approve (all four segments
  safe).

the seam's job becomes: split the command quote-aware into segments, judge each
segment against {clean-rhx OR allowlisted}, and approve iff ALL pass. there is no
privileged "producer must be rhx/echo" position anymore — every segment meets the
same {clean-rhx OR allowlisted} bar, wherever it sits.

## .the safety invariants that MUST still hold (non-negotiable)

this is a change to a DEFENSIVE gate, so every one of these must survive:

1. **default-deny stands** — if ANY segment is not provably safe (not clean-rhx,
   not allowlisted), the whole command LIFTS to the human. no partial approve.
2. **quote-aware split only** — reuse gate 2's both-quote + backslash-aware
   splitter, so `rhx foo --note 'a; b && c'` never splits inside a quoted arg. a
   naive split is forbidden.
3. **injection forms never reach here approved** — `$()`, backtick, `<()`, `>`
   stay hard-blocked upstream by gate 1; and if one reaches the seam
   (the apostrophe-parity bypass), the residue keeps it active and the seam does
   NOT approve.
4. **no new auto-approve for a NON-allowlisted, non-rhx segment** — the allowlist
   is the whole authority; a segment absent from it must never slip through.
5. **the redteam corpus is extended and re-proven** — background `&`, newline,
   quote-nest, apostrophe-in-double-quote, and privilege-escalation-token
   payloads must each stay `AUTO_DENY` or `LIFT`, never `AUTO_APPROVE`. the
   "no adversarial command auto-approves" invariant is the acceptance gate.
6. **G3 audit unchanged** — every allow/deny is still recorded to
   `.claude/permission.decisions.local.log`, deterministically (no timestamp).

## .open questions for you to confirm

1. **background `&` and solitary `&`** stay DENY (they detach a gated command
   from the gate)? — my default: yes, still deny `&`.
2. **an un-allowlisted segment** → LIFT (defer to human), not DENY? — my default:
   LIFT, matching today's fail-safe for "cannot prove clean".
3. **the allowlist source** = the union of `settings.json` + `settings.local.json`
   `Bash(…)` patterns, exactly as gate 2 reads them (so an adhoc human grant in
   `.local` also counts)? — my default: yes, reuse gate 2's exact extraction.
4. **scope** = the seam only. i do NOT touch gate 1 (forbid), gate 2
   (check-permissions), or claude-cli's own classifier/settings. correct?

## .out of scope

- a change to WHICH commands are on the allowlist (that's a settings edit, separate).
- the `jq -r` / `jq -c` / `2>&1` friction i hit as i worked — those are gate 1
  / gate 2 near-misses, tracked separately, not this wish.
- any change to claude-cli's own suspicious classifier (gate 3) or settings
  allow/ask/deny (gate 5) — not ours to change.

## .done when

- the four cases above auto-approve (proven by the audit log verdict `allow`);
- all six safety invariants hold, redteam corpus green;
- `rhx git.repo.test --what integration --scope 'path://permissionrequest' --mode apply --resnap` passes;
- `howto.triage-permission-prompts.[lesson].md` reflects the seam's new
  segment-allowlist behavior.
