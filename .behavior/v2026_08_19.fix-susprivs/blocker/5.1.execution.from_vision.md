## .the fork (the clean-rhx-sink fulcrum)

**question**: when a clean-rhx call sits as a pipe SINK — e.g.
`echo hi | rhx git.commit.uses set --quant 999 --push allow` — should the seam
**AUTO_APPROVE** it or **LIFT** it?

2 reviewers (arch-hazards-behavior, behavior-intent-coverage) read invariant #5 literally
and asked whether "privilege-escalation-token" covers an rhx subcommand.

## .the decision (AUTO_APPROVE — verified, not best-guessed)

the seam AUTO_APPROVES a clean-rhx sink. this is the repo's DOCUMENTED design, and i
verified it against the skill code:

1. **the seam is not the authority — the skill is**
   (`define.why-permission-guards-allowlist-all-rhx`): the seam asks only "clean rhx or a
   chain?"; the SKILL, at execution, asks "is this operation allowed for this caller?". the
   seam is DESIGNED to allow every clean rhx call, because the skill self-guards the
   sensitive ones.
2. **VERIFIED execution self-guard** — `git.commit.uses.local.sh` refuses a
   `set/del/block/allow` command unless stdin is a TTY:
   `[[ ! -t 0 && "${__I_AM_HUMAN}" != "true" ]]` → exit 2 "only humans". a PIPE removes the
   TTY, so `echo hi | rhx git.commit.uses set …` is REFUSED at execution. a seam
   auto-approve of the piped grant hands out NO authority the skill would honor.
3. **the wish body is explicit** — "every segment {clean-rhx OR allowlisted}, wherever it
   sits" (0.wish.md) permits a clean-rhx sink; the producer-only narrow-down came from my
   vision, not the wish.
4. **no regression** — the ORIGINAL shipped seam approved `echo|printf|cat | rhx`; the
   phase-1 `echo '{ x }' | rhx sedreplace --old @stdin` stdin-payload workaround (in the
   human's own allowlist) relies on the clean-rhx sink. readers-only would regress ~12
   phase-1 cases to LIFT — a re-add of the exact friction this effort removes.
5. **invariant #5 = shell escalation, NOT an rhx subcommand** — the redteam proves
   `echo hi | sudo rhx …` → LIFT (sudo/env tokens refused). the distinction is principled:
   a shell token like `sudo` has NO execution self-guard, so the seam MUST refuse it; a
   clean rhx call DOES self-guard, so the seam may allow it. the sink bar also excludes the
   code-exec allowlisted sinks (`npm run`, `bash`) — same reason: no self-guard.

i pinned the decision EXPLICITLY in the suite (`echo hi | rhx git.commit.uses set … →
AUTO_APPROVE`, with the verified TTY-self-guard rationale in-test) and documented it in the
5.1 yield's "clean-rhx-sink fulcrum" section.
