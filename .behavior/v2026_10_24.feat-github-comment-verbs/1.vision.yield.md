### before

### after

the mechanic role ships three verbs. a crew reads the pr, writes the body, posts or edits a keyed comment, replies in a thread, and deletes a twin — each planned first, applied on purpose, read back and hash-checked. a re-run is a no-op. no prompt, no local copy.

### a day in the life

```sh
rhx git.pull.comment.get --pr 69                                    # what is there?
rhx git.pull.comment.set --pr 69 --kind body --from ./pr.md --mode apply
rhx git.pull.comment.set --pr 69 --reply-to 4312862587 --key answer --from ./a.md --mode apply
```

### the aha

## .the contract

shared, on all three verbs:

| flag | sense | default |
|---|---|---|
| `--pr <n>` | the pull request (required on every call) | — |
| `--in <owner/name>` | the repo | the current repo (`gh repo view`) |
| `--auth as-ehmpath \| as-human` | whose credential gh uses | `as-ehmpath` |
| `--output tree \| json` | output shape | `tree` |
| `--help`, `-h` | usage, inputs, an example | — |

- exit 0 = shown, planned, written, or no-op · 1 = malfunction (gh failed, read-back mismatch) · 2 = constraint (bad input, absent target, foreign author, absent token)
- every gh call names `--method`; every list call uses `--paginate`
- treestruct stdout; an error also goes to stderr
- an `--id` must belong to `--pr`; elsewise exit 2
- home orgs only: the owner of `--in` (given or derived) must be one of `ehmpathy` · `whodisio` · `ahbode` · `uladkasach`. any other owner → exit 2 before any gh call, and the error names the allowlist (F4). the fleet writes to github only inside its home orgs; with a token that can reach any repo, this fence is the one guard

```
✋ ConstraintError: owner 'seaturtlecorp' is outside the home orgs
   └─ allowed: ehmpathy · whodisio · ahbode · uladkasach

🥥 did you know?
   ├─ to fix it
   └─ target a repo in one of those orgs, via --in <owner/name>
```

kinds: `body` (the pr description) · `issue` (a top-level comment) · `review` (an inline review-thread comment).

### get

- `--pr N` → every row: the body, each issue comment, each review comment, sorted by created time
- `--pr N --id X --kind issue|review` → one row; absent → exit 2
- `--pr N --key K [--reply-to X]` → the own comment with that key; absent → exit 2
- `--pr N --kind body` → the body alone
- row: kind, id, author, created_at, in_reply_to, key, bytes, sha256, url, body

### set — upsert

| target | flags | absent | same | differs |
|---|---|---|---|---|
| top-level comment | `--key K` | POST `issues/N/comments` | no-op | PATCH |
| thread reply | `--reply-to X --key K` | POST `pulls/N/comments/X/replies` | no-op | PATCH |
| a known comment | `--id X --kind issue\|review` | exit 2 | no-op | PATCH |
| the pr body | `--kind body` | — | no-op | PATCH `pulls/N` |

- body from `--from <path|@stdin>`; tail newlines trimmed
- a comment posts as `🐢 ` + body (never doubled) + `\n\n<!-- rhx:git.pull.comment key=K -->` when keyed. the pr body takes no prefix
- a key matches only comments of the current auth identity, and a reply key only within its thread
- a key held by another author → exit 2, names the author and `--auth` fix. two own matches → exit 2, lists both ids
- a new comment with no `--key` → exit 2 — an unkeyed POST would double on retry
- `--mode plan` (default) prints endpoint, current + new bytes and sha256, verdict; writes naught
- `--mode apply` writes, reads back by id, compares sha256; a mismatch → exit 1 with both hashes

### del

- `--pr N --id X --kind issue|review`, or `--pr N --key K [--reply-to X]`
- plan default; apply DELETEs, then reads again; still present → exit 1
- absent → exit 0, `absent — no-op`
- `--kind body` → exit 2; github offers no delete for a pr description

### auth

reuse, not copy: `git.commit/keyrack.operations.sh` (`fetch_github_token`, `is_gh_auth_failure`) and the vocab in `git.commit.operations.sh` (`AUTH_DEFAULT`, `AUTH_VALID_VALUES`, `get_auth_who_label`). `as-ehmpath` passes the keyrack token as `GH_TOKEN`; `as-human` strips `GH_TOKEN` and `GITHUB_TOKEN` and runs under the human's `gh auth login`, the same split as `git.commit.push.sh:599-608`. a token absent under `as-ehmpath` → exit 2 before any write, both fixes named (case=6).

the key's author check needs the current login. it reads graphql `viewer { login }` under the chosen credential, never REST `GET user`: that 403s for a `ghs_` app token (`keyrack.operations.sh:326-327`). the token kind varies — `ghs_` posts as the app's `[bot]`, a pat posts as `ehm-seaturtle` — so the login is read, never hardcoded.

### the suite

- `git.pull.comment.integration.test.ts` (jest, given/when/then, snapshots + assertions): 15 cases against a PATH-stub `gh` that logs argv + stdin (`howto.mock-cli-via-path`), with an inline `.mock / .why / .real` note — the real-api case below is the `.real`
- 15 cases, one `given` each, port the draft's list re-cast for this contract:

## .mental model

- to a friend: "a crud for pr comments, where you name each comment, so a re-run edits it instead of reposts it"
- analogy: a declared resource, like a terraform block — `--key` is the resource address, `set` converges, `del` destroys, plan comes first
- their words vs ours: "post", "reply", "edit", "update" → `set`; "remove" → `del`; "description" → `--kind body`; "conversation comment" → `--kind issue`; "inline comment" → `--kind review`

## .evaluation

- goals: all six "done means" lines map to the contract above; "upserts on a key the caller names" → `--key`; "edits a pr body" → `--kind body`; `--auth` → reused vocab; 15-case suite + one real case → the suite
- pros: one verb family, idempotent by construction; plan by default; read-back proof; refusals name the fix; the auth path is the one git.commit.push already proved
- cons: a marker in every keyed comment (hidden, but present in raw markdown); `--pr` on calls that technically need only an id; a pr body under the noun "comment"
- pit of success: an unkeyed POST is unreachable; a wrong-pr id, a foreign key, and a twin all refuse before a write

## .what is awkward

- `--kind body` stretches "comment" over the pr description (F2)
- a key held by the human after an auth switch cannot be adopted by the bot — the crew must re-run as-human or delete first (case=7). correct, but a step
- the real-api case cannot go green in ci until a human grants a token; the wisher files that ask once the case is real (F6)
- `set` converges: a human's browser edit to a keyed comment reads as `differs`, and apply overwrites it. the plan shows the current sha256 beside the new one, so the overwrite is visible before apply — but it is not refused
- the key lives in the body. a human who edits the marker away orphans the comment; the next `set` posts a fresh one (inventory row 45, case=9 [t3])
- `get` returns review comments flat; the per-review view #996 asks for sits one layer up, so a crew that wants it still waits on #996
