# 1.vision — grepsafe through a role symlink into the main checkout

## the outcome world

a clone works in a worktree. its role dir `.agent/repo=.this/role=any` is a symlink into the main
checkout. it runs:

```sh
rhx grepsafe --pattern 'wave' --path .agent/repo=.this/role=any/briefs
```

**before** — refused: `search path must be within the git repository`, since the link resolves to
`/main/checkout/.agent/...` and the gate compares against the worktree root alone. the clone has no
sanctioned way to search its own briefs.

**after** — the search runs, results print, exit 0. the same command as in any in-repo dir.

the aha: the main checkout is not "outside the repo". it is the same repo, one `git worktree` away.
the gate learns to say so — and only for a path the caller named *inside* the worktree.

## the contract

the repo gate admits a resolved root when either holds:

1. the resolved root sits under the worktree root (unchanged), or
2. the resolved root sits under the **main checkout** of this worktree's repo, **and** the path as
   typed (lexical, no link resolution) sits under the worktree root — i.e. the caller reached it
   through a link inside the tree. a relative typed path joins the physical cwd (`pwd -P`), then
   collapses its `.` and `..` segments with no link resolution; an absolute one only collapses. a
   typed prefix that is itself a link fails this check, so the path is refused — fail-safe

the main checkout = the first `worktree <path>` record of `git worktree list --porcelain`, which git
documents as the main worktree. a bare repo marks it `bare`; then there is no main checkout and rule
2 admits naught. outside a linked worktree it equals the worktree root, so rule 2 adds naught.

## the experiences

the axes, each shown to vary apart from the others, live in `1.vision.experience.dimensions.md`. the record is
`1.vision.experience.case=_.md`: every cell of the walked product verdicted, per value of "is there
a distinct main checkout?" and of target present/absent. each critipath, and each alterpath that
tests a gate, has a `case=N` file with a narrative and a `[tn]` timeline.

the densest walk is case=2 (worktree → role link → main checkout, admitted); its sharp twin is
case=3 (worktree → link → elsewhere, refused with the fix named).

## mental model

"a worktree's role link points home; grepsafe follows it home, and nowhere else."

## evaluation

- pro: one gate, one extra predicate; every other refusal path unchanged
- pro: lexical-inside check means a typed `../main-checkout/...` is still refused (case=4)
- con: results under the main checkout print as absolute paths (the repo-relative strip knows only
  the worktree root). legible, not pretty
