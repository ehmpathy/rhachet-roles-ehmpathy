# wish: `grepsafe --glob` answers the question it was asked, or says it could not

> the authoritative record is **`ehmpathy/rhachet-roles-ehmpathy#620`**. read it first — this wish
> carries the outcome; the issue carries the verbatim repro, the built argv, and a patch its author
> validated locally.

## .what

`rhx grepsafe --pattern <p> --glob <g>` finds every file that matches, for **every** glob shape —
above all the ones that hold a `/`, which is nearly all of them in practice.

today it does not. measured 2026-09-03, same pattern, same files, one character apart:

```
rhx grepsafe --pattern 'the bar was MET' --glob '.agent/**/*.md' --files-only
   └─ matches: 0          # ✋ false — the string sits on line 69 of a real file

rhx grepsafe --pattern 'the bar was MET' --glob '*.md' --files-only
   └─ 4 matches           # ✔
```

## .why

### a false `0` is indistinguishable from a true one

`matches: 0` is exactly what a clean search looks like. so the caller cannot part *"no match
exists"* from *"I could not ask the question"* — and both exit 0. that is `rule.forbid.failhide`
in its purest form, and it is a `term=false-report`: the tool did not fail, and its claim is untrue.

### the harm is not a missed match — it is an ARGUMENT built on one

a search that finds naught is not neutral evidence. aimed at a verification step, it argues that a
real guarantee is **absent**, and the repair it invites is to **delete a correct claim**.

⇒ in the very session that found this, grepsafe's `0` nearly led to the conclusion that **a cited
brief line had been invented.** the tool would have talked a reader into deletion of a true claim.

### it fails on the shapes callers actually use

the fallback matches a glob against the **basename** only. so every pattern that holds a `/` —
`.agent/**/*.md`, `src/**/*.ts`, `**/*.md`, or a bare file path — matches no file at all, by
construction.

⚠️ and the skill's own documented examples are all unslashed (`*.ts`, `*.md`), which is precisely
why this survived: **the defect cannot fire on any example the docs show.**

### the caller cannot see which engine answered

two engines back this skill and they disagree on what `--glob` means. the output names neither. so
even a caller who knows about the split cannot tell which answer they hold.

## .acceptance

1. **a slashed glob finds what it matches.** `--glob '.agent/**/*.md'` returns the same files a
   correct search would, under **either** engine
2. **an unslashed glob is unchanged.** no regression on `*.md`, `*.ts`, and the documented examples
3. **a glob that matches no file returns 0 at once** — it must not hang. see the hazard below
4. **the engine is named in the output.** two engines with different glob semantics, and today the
   caller cannot see which ran. they can still differ at the edges after this fix, so the answer
   must carry its own provenance
5. **a clamp with teeth**, and it must exercise the FALLBACK: a test that asserts a slashed glob
   finds a known file **with the faster engine forced off**. prove it bites — revert, see red,
   restore, see green
6. **the `rg` arm is checked, not assumed.** see below — it is unverified by the report

## ⚠️ .the hazard that makes a naive fix worse than the defect

if a pathed glob expands to **no file**, the expansion must not reach `grep` at all: with no file
operands `grep` reads **stdin** and hangs forever.

⇒ so the obvious repair — expand the glob, hand grep the files — converts a wrong answer into an
**indefinite hang**, which is the one outcome worse than a wrong answer. acceptance 3 exists for
this, and it is the sharpest edge in the round.

## .what is NOT verified — stated plainly so it is not inherited as fact

the report's own admission, and it bounds what you may trust:

> *"the `rg` branch is **untested** by this report."*

on the box that measured this, `rg` resolved only as an interactive **zsh alias**, and `grepsafe`
runs under `bash` — where `command -v` cannot see an alias. so the fast path never executed once,
and every measurement in the issue is a measurement of the fallback.

that carries two consequences:

- **the engine choice is itself suspect.** a `command -v rg` that silently misses a live ripgrep is
  how this defect got reached at all
- **a suspicion about the `rg` arm is on record and deliberately unfixed:** that arm passes an
  ABSOLUTE search root, which the reporter suspected also breaks relative globs. they patched it,
  saw **no change**, and correctly concluded the test proved naught — because `rg` never ran.
  ⇒ treat it as a suspicion. **someone with `rg` truly on PATH should check it**, and this round
  is that party

## .the boundary — what is NOT in scope

- **do not narrow the fix to the fallback if the fast path shares the defect.** acceptance 1 says
  *either engine*
- **do not change what `--glob` means.** the path semantics are the correct ones; the fallback is
  what disagrees with them
- **do not widen `grepsafe`'s surface.** this is a defect fix plus one line of provenance, never a
  redesign
