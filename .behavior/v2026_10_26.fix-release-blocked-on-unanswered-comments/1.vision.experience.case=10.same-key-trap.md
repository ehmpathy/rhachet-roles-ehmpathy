# case=10 — a re-asked thread, answered under the same key

feel: sharp · care: critipath · boundaries: re-open, upsert by key, refusal teaches

## narrative

the clone answered thread 801 with `--key answer`. the commander asked a follow-up in that thread. the clone answers again — same habit, `--key answer`. set finds its keyed reply in that thread and edits it in place; no new comment is posted. the edited answer keeps its old timestamp, so the commander's follow-up is still the latest comment.

the clone runs `--apply` and is refused again on 801. this time the row says why: the thread already holds an answer, and a reused key edits it. the clone answers with `--key answer-2`, and the next apply passes.

## timeline

```
given thread 801: @commander asks · robot answers (key=answer) · @commander asks again

when [t0] rhx git.pull.comment set --pr 700 --reply-to 801 --key answer --from ./a.md --mode apply
  then set edits the extant keyed reply (upsert, key scoped to the thread root, `git.pull.comment.operations.sh:751-760`)
   and no new comment is posted

when [t1] rhx git.release --apply
  then `💬 1 comment(s) unanswered` — row 801
   and the row notes: `answered once — a new --key posts a new answer; a reused key edits the old one`
   and exit 2

when [t2] rhx git.pull.comment set --pr 700 --reply-to 801 --key answer-2 --from ./a.md --mode apply
  then a new reply posts; it is now the latest comment in 801

when [t3] rhx git.release --apply
  then `💬 all comments answered`; release proceeds
```

## fail-safe proven
fast: refused at the gate, before any automerge or merge · loud: exit 2, qualified header · teaches: the row names the exact cause (a reused key edits the old answer) and the exact cure (a new `--key`). without the note, the driver loops on a row that can never clear.
