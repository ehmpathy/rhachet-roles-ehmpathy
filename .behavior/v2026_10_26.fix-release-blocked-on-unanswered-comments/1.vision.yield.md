# 1.vision — git.release refuses a release while a pr comment waits on an answer

## the outcome world

### before

commander approves #693: *"approved, given the comments left are addressed first."* four review comments sit on the diff. the driver runs `rhx git.release --into prod --apply`. the verb reads checks and automerge, never comments. it merges, tags, publishes. four comments, zero replies, shipped.

the condition lived in prose. prose is read by hand, or not at all.

### after

same pr, same command:

```
🐢 hold up dude...

🐚 git.release --into prod --mode apply --watch

🌊 release: feat(reef): add tide sensor
   ├─ 👌 all checks passed
   ├─ 💬 3 comment(s) unanswered
   │  ├─ review 4373390828 · src/reef/getTide.ts:42 · @commander · "why not a findsert here? a retry would…"
   │  ├─ review 4373395361 · src/reef/setSensor.ts:7 · @commander · "this name drifts from the ubiqlang term…"
   │  └─ issue 6407563822 · @commander · "also: the readme still names the old flag"
   ├─ 🌴 automerge unfound
   └─ ✋ ConstraintError: release blocked until each comment has an answer
      ├─ see them: rhx git.pull.comment get --pr 693 --unanswered
      ├─ review:   rhx git.pull.comment set --pr 693 --reply-to <id> --key <slug> --from <file>
      ├─ issue:    rhx git.pull.comment set --pr 693 --key answer-<id> --from <file>
      └─ or the reviewer marks the thread resolved on github
```

exit 2. no merge, no automerge. the driver answers each comment, reruns, and the release rolls:

```
🌊 release: feat(reef): add tide sensor
   ├─ 👌 all checks passed
   ├─ 💬 all comments answered
   ├─ 🌴 automerge enabled [added]
   └─ 🥥 let's watch
      └─ ✨ done! Xs in action, Xs watched
```

### the aha

the commander's condition stops to be a promise and becomes a gate. *"approved, as long as the comments are addressed"* is now what `--apply` enforces, for every driver, on every pr. no human has to remember it; no driver can skip it, since there is no flag to skip it.

and the driver already holds the list: `git.pull.comment get --unanswered` — the verb they answer from — shows exactly the rows the release refuses on. one list, two verbs.

## the contract

| input | today | after |
|---|---|---|
| `git.release` (plan) | checks + automerge | + `💬` line; exit unchanged |
| `git.release --watch` | checks + automerge, then watch | + `💬` line; each poll re-reads comments; never enables automerge; if automerge is already on and any watch read — its first read or a poll — finds an unanswered row, disables it and exits 2 (F11); else exit unchanged |
| `git.release --apply` | enables automerge, watches | refuses exit 2 while ≥1 comment unanswered; each watch poll re-reads, and a new unanswered row disables automerge and exits 2 |
| `git.release --into prod --apply` | feat → main → prod | refuses at the feat pr while ≥1 comment unanswered |

scope: pr transports only (feat pr, release pr). a tag transport (`🌊 release: v1.2.3`) has no comments, so it gets no `💬` line and no gate.

**unanswered = the one definition that already ships**: `rhx git.pull.comment get --unanswered` (`as_rows_unanswered`, `git.pull.comment.get.sh:157-173`). the gate reuses it and never forks a second rule:
- a review thread whose latest comment is not the robot's (robot = the current login, body opens with 🐢)
- a human issue comment newer than the robot's latest issue comment

**three amendments, made in `as_rows_unanswered` itself** (fulcrums F7, F9):
- an issue comment is answered only by a signed issue comment keyed `answer-<that comment's id>` — not by any newer robot comment. the extant bulk rule let an unrelated `set --key status` clear every older human question, a false green (F9, case=11)
- a thread marked resolved (github `isResolved`) is answered — wish: "a resolved thread answers it". the read already holds the state (`thread=open|resolved`, `git.pull.comment.operations.sh:580-598`)
- a row by a bot author (`[bot]` login) is never unanswered — task: "a human comment". without it, `rhelease[bot]`'s "released at" comment (live on #1143) blocks every pr after its first release

**one answer identity across modes** (fulcrum F10): `git.release.sh:334-347` fetches the seaturtle token in apply mode only; plan and watch read under the ambient gh login. the extant rule keys "robot" on the current login, so on a human's machine plan would read every seaturtle answer as foreign and disagree with apply. the gate must judge an answer the same way in every mode. best guess: an answer = a comment whose body opens with 🐢 AND ends with the key claim `<!-- rhx:git.pull.comment key=… -->` (`COMMENT_KEY_CLAIM_REGEX`, `git.pull.comment.operations.sh:52`) — the exact signature `git.pull.comment set` writes (`:898`; a new comment with no `--key` is refused, `git.pull.comment.set.sh:18`), whoever's login reads it. 🐢 alone is not enough: `rhelease[bot]`'s "🐢 released at …" opens with 🐢 and carries no claim.

**no bypass flag**: the cure is an answer via `git.pull.comment set`, or the reviewer's resolved mark.

## mental model

how a driver says it: *"release won't go while a comment waits on an answer."*

analogy: a required review, one level finer — not "did someone approve", but "did we answer each thing the approver said."

| their word | our word |
|---|---|
| comment, review comment, thread | comment (review or issue) |
| addressed, replied, answered | answered — the extant `--unanswered` rule, plus resolved |
| blocked | refused (exit 2, ConstraintError) |

## evaluation

**goals met**
- the condition moves from prose into the verb every driver runs ✅
- refusal names each comment and the answer verbs ✅
- plan and watch show it first ✅
- no bypass ✅
- task #1171's scope (review threads AND issue comments) covered via the extant rule ✅

**pros**
- one definition of "unanswered" across `git.pull.comment get` and `git.release` — no synonym rule
- the read, the pagination, and the answer verbs already exist (#1143)

**cons**
- an answer of "ok" satisfies the gate. it proves a conversation happened, not that it converged. the resolved mark stays the reviewer's stronger signal
- "answered" keys on the robot login + 🐢 header; a human who answers by hand under their own login does not satisfy it (F8)
- one more read per pr transport per run
- every extant git.release snapshot gains the `💬` line

**pit of success**
- no flag to skip → the only path forward is an answer
- a failed read is a malfunction, never a silent 0
- automerge found + unanswered → disabled, so github cannot merge past the gate
- the refusal names `--unanswered`, the exact list to work from

## open questions & assumptions

each question triaged. each best guess is itemized as a fulcrum in `.fulcrums/`.

### [answered] — settled now, by logic or code

- **F2** show the `💬` line also at 0? → yes. the wish: "the count rides in the plan output beside the ci tally"; a line that vanishes at 0 cannot tell "clean" from "gate never ran"
- **F4** do bot rows count? → no. task: "a human comment"; live `rhelease[bot]` row on #1143 would block every pr after its first release. residual: a bot code reviewer passes (noted in F4)
- **F6** re-read comments on each watch poll? → yes. a comment that lands after the gate read and before github's merge would ship unanswered — the #693 harm, through a side door, and a merge cannot be undone. each poll re-reads; a new unanswered row disables automerge and exits 2 (case=9). residual: a comment in the seconds between the last poll and github's server-side merge — not closable client-side; one poll interval wide, accepted
- **F9** what answers a top-level issue comment? → only a signed issue comment keyed `answer-<its id>`. the extant bulk rule (any newer robot comment) lets an unrelated `status` comment clear a human question — a false green, cost ∞. the stricter rule fails closed, reuses the key claim set already writes, and the refusal prints the exact key (case=11)
- **F5** disable an extant automerge when the gate fires? → yes. automerge is server-side; without the disable, github merges past the refusal the moment checks land
- **F10** which identity judges an answer? → its signature: 🐢-opened + the key claim `<!-- rhx:git.pull.comment key=… -->` (`git.pull.comment.operations.sh:52,898`; `git.pull.comment.set.sh:18`). plan reads under the ambient login (`git.release.sh:334-347`), so a login-keyed rule would make plan and apply disagree
- **>100 comments in one thread?** → fails closed. rest rows paginate fully (`git.pull.comment.operations.sh:565-570`); only the graphql state map caps at 100 comments per thread (`:588`). a comment past the cap gets no state, reads as not-resolved, and blocks — never a false green
- **does `--reply-to` need the thread root id?** → no. any id in the thread maps to its root (`get_thread_root_id`, `:757-759`), so the refusal may print the latest row's id
- **where does each row's `path:line` come from?** → the row shape (`shape()`, `git.pull.comment.get.sh:96-113`) keeps `id, author, created_at, in_reply_to, key, url, body` and drops `path`/`line`. github's rest review comment holds both, so the fix is additive: carry `.path` and `.line` into `shape()`. the same row already holds `key`, so F10's test is `key != null and body opens with 🐢` — no new parse

## what is awkward?

- **a reply is a weak proof.** "👍" answers the gate. we gate on conversation, not agreement
- **the answer is keyed to the robot.** the extant rule trusts only the current login's 🐢 body. git.release reads under the seaturtle token, so a human's by-hand reply leaves the row open (F8)
- **a reused key answers no one.** set upserts by key, scoped to the thread root. a second answer in a re-asked thread under the same `--key` edits the first; the follow-up stays latest and the gate keeps refusal. the refusal row must say so (inventory row 19, case=1 [t4])
- **one answer per issue comment.** an issue comment clears only under `--key answer-<id>`; three notes need three keyed answers. prs answered under the old bulk rule will show those rows again (F9)
- **the gate edits a shipped rule.** resolved + bot amendments change what `get --unanswered` shows too — correct, but a behavior change to #1143's verb, so its [case21] snapshots move
- **the race cannot fully close.** each watch poll re-reads, but github merges server-side; a comment in the last poll interval before merge still ships. narrowed to seconds, never zero
- **more reads.** one comment read per watch poll (~6 calls each, per the extant `get`), not one per run
- **apply mutates to refuse.** to disable automerge inside a refusal feels odd, but without it the refusal is theater
- **snapshot churn.** the `💬` line touches every pr-transport snapshot across p1–p8
