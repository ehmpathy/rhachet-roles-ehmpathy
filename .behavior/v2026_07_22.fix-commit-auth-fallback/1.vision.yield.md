# 1.vision — fallback to `--auth as-human` when the keyrack token can't push

## the wish

when the keyrack token can't be used for `git.commit` push, we should **inform the caller**
and **enable a fallback to `--auth as-human`** so the operation still completes. it should
read as a natural guide. **prefer the keyrack creds**, but **allow the fallback** so progress
is never blocked on perfection.

## what "push" actually needs (verified)

the push path has two distinct auth surfaces — only the second needs the keyrack token:

| step | command | auth used today |
|---|---|---|
| **transport the commit** | `git push origin HEAD --force-with-lease` (`git.commit.push.sh:339`) | ambient git creds (already the human's ssh/https) |
| **findsert the PR** | `gh pr list` / `gh pr create` under `GH_TOKEN=$EHMPATHY_SEATURTLE_GITHUB_TOKEN` (`:360`, `:381`) | the keyrack seaturtle bot token |

so `git push` already rides on the human's git creds. the **only** thing the keyrack token
buys is opening the PR **as the seaturtle bot**. that is the surface the fallback swaps.

## the decision

add an `--auth` mode to `git.commit.push` (and pass it through from `git.commit.set`):

| `--auth` | who opens the PR | token source | when |
|---|---|---|---|
| **`as-ehmpath`** (default) | the seaturtle bot | ehmpath keyrack `EHMPATHY_SEATURTLE_GITHUB_TOKEN` | preferred — always tried first |
| **`as-human`** | the human | ambient `gh` login (no `GH_TOKEN` override) | fallback — when the ehmpath keyrack is unreachable |

we **mirror `rhachet-roles-bhuild`'s `--auth` grammar**, but pared to the two modes this wish
needs. bhuild's full contract is `as-robot:via-keyrack(owner)` / `as-robot:shx(cmd)` /
`as-robot:env(VAR)` / `as-human` with a default of `as-robot:via-keyrack(ehmpath)`
(`rhachet-roles-bhuild/src/domain.operations/radio/auth/asGithubAuthMode.ts`,
`getGithubTokenByAuthArg.ts:40`). we do **not** adopt the `as-robot:*` sub-grammar — we expose
only **`as-ehmpath`** (the ehmpath-keyrack default, bhuild's `via-keyrack(ehmpath)` collapsed to
one clean token) and **`as-human`** (identical to bhuild's `as-human` — the `gh` cli login).

and change the ehmpath-keyrack-failure branch (`git.commit.push.sh:307-321`) from a **dead-end
`exit 1`** into a **natural guide** that names the fix: *retry with `--auth as-human`*.

**important — un-gate the push from the token fetch.** in apply mode today the token fetch
(`:266-333`) runs *before* `git push` (`:339`) and `exit 1`s at `:320` on failure — so a
keyrack outage currently aborts **before the push**; the commit stays local and unpushed
(not "pushed, only the PR blocked"). the fix is therefore not merely "swap the PR token": the
build must move the push **ahead of, or independent of**, the token fetch, so the transport
always completes and only the PR-open step depends on auth. (under `--auth as-human` the
PR-open uses ambient `gh`; under `--auth as-ehmpath` it uses the ehmpath keyrack token.)

the commit itself is untouched — `git.commit.set` still authors as `seaturtle[bot]` with the
human `Co-authored-by:` trailer. `--auth` governs only **who opens the PR**, not authorship.

## the outcome world

### day-in-the-life

a mechanic runs `git.commit.set … --mode apply --push`. keyrack is healthy → the bot opens
the PR exactly as today. the happy path is unchanged.

one afternoon the human's keyrack lease has expired. the mechanic pushes and — instead of a
dead-end error — sees a guide (illustrative sketch; the build renders it via the extant
`output.sh` operations and the established emoji set 🐢/🐚/🔐, not the ad-hoc placeholders below):

```
🐢 bummer dude, the keyrack token isnt available right now
   └─ your commit is safe locally, but the push + PR-open are on hold

   prefer: unlock keyrack so the seaturtle can push + open the PR
     rhx keyrack unlock --owner ehmpath --env prep

   or: fall back to your own github login so you dont stay blocked
     retry with --auth as-human
```

the mechanic retries with `--auth as-human`. the push transports under their own git creds and
the PR opens under their `gh` login. work ships. the human unlocks keyrack later at their leisure.

### before / after

| | keyrack healthy | keyrack unavailable |
|---|---|---|
| **before** | bot opens PR ✅ | `exit 1`, dead end, work stuck ❌ |
| **after** | bot opens PR ✅ (unchanged) | guide → `--auth as-human` → PR opens as human ✅ |

### the aha

the token was never needed to **save the work** — the commit is already local and `git push`
already uses the human's creds. the token only picks **whose name opens the PR**. so a keyrack
outage should never block progress; it should just offer the human's own hand as the fallback.

## user experience

- **usecase**: a mechanic wants to commit + push, but the seaturtle keyrack token is expired,
  not filled, or otherwise unreachable, and they don't want to stop to fix credentials.
- **inputs**: a new `--auth as-ehmpath|as-human` flag on `git.commit.push`; passed through
  by `git.commit.set --push`.
- **outputs**: on keyrack failure under the default, a guide (prefer-keyrack first, then the
  `--auth as-human` fallback). under `--auth as-human`, a normal success tree noting the PR
  was opened **as the human**, not the bot.
- **timeline**:
  1. `git.commit.set … --push` → commit lands locally, push proceeds
  2. bot-token PR-open fails → guide printed, exit as constraint (caller must choose)
  3. `git.commit.set … --push --auth as-human` → PR opens under the human's `gh` login → done

## mental model

> "pushing my work and opening its PR are two different keys. the push key is already mine.
> the PR key is normally the turtle's — but if the turtle's key is missing, i can just use
> mine. don't make me stop; let me sign the PR myself this once."

analogies:
- **prefer the bot's stamp; keep your own pen handy.** the turtle stamps the PR by default,
  but if the stamp's out of ink you sign by hand rather than halt the mail.
- **valet vs. your own keys.** the valet (keyrack bot) normally parks the car; if the valet's
  away, you park it yourself. the car still gets parked.

terms — **theirs** vs **ours**:

| we say | the human might say |
|---|---|
| `--auth as-ehmpath` | "let the bot do it" / "the normal way" |
| `--auth as-human` | "just use my login" / "do it as me" |
| keyrack token unavailable | "the turtle creds are down / expired" |

## evaluation

### how well it solves the goal

directly. the wish is "don't block on a missing keyrack token" and this makes the token
**preferred but non-blocking**: the happy path is identical, and the failure path becomes a
one-flag detour instead of a wall.

### pros

- **never blocks progress** — a keyrack outage becomes a fallback, not a dead end.
- **keyrack stays preferred** — default is unchanged; fallback is explicit opt-in.
- **small, localized** — the seam is the PR-open auth in `git.commit.push`; commit logic and
  the transport push are untouched.
- **honest attribution** — under `as-human` the tree states plainly that the human opened the
  PR, so no one is surprised about who shows on it.

### cons / costs

- **the squash author differs under fallback** — an as-human PR opens under the human, so on
  squash the human becomes the squash *author* instead of the bot. the contributor *count* is
  unaffected: squash author = human, co-author trailers = seaturtle[bot] + human, de-dup =
  **exactly 2 (human + seaturtle)** — the same two as the bot-opened ideal
  (`v2026_06_26.fix-seatur-contributor`). so this is an attribution nuance, not a count
  regression. accepted by the wish: "don't block progress on perfection."
- **relies on the human's `gh` being authed** — if the human has no `gh` login either, the
  fallback can't help; we must fail loud and name *that* fix too.
- **new flag surface** — `--auth` must thread `set → push`, and the pre-approved bash
  permission entries for `git.commit.set` (exact-match list) need new variants.

### edgecases & pit-of-success

- **default stays safe** — omit `--auth` = `as-ehmpath`; no one silently opens PRs under
  their own name. the fallback is a deliberate, named choice (`rule.require.safe-by-default`).
- **ehmpath keyrack healthy + `--auth as-human`** — honored: the human explicitly chose their
  login; we don't override their intent.
- **both keyrack AND human `gh` unavailable** — fail loud with two fixes named: unlock keyrack
  (preferred) or `gh auth login` (to enable the fallback). never a bare stack trace
  (`rule.require.errors-name-the-fix`).
- **guide fires only where it helps** — the fallback suggestion appears only on the PR-open
  auth failure, not on unrelated push failures (protected branch, non-turtle author, etc.),
  so the guide never misdirects.

## open questions & assumptions

**[assumptions made]**

- `--auth as-human` = "use the ambient `gh` login for PR ops" (no `GH_TOKEN` override). the
  push transport is unchanged since it already uses the human's git creds (verified: ssh remote
  `git@github.com:…`).

**[answered] — resolved from the wish + code**

- **guide + explicit flag, not silent auto-fallback** — the wish says "inform the caller and
  enable the *caller* to fallback to `--auth as-human` … a natural guide." that describes a
  caller-initiated flag after a guide. auto-fallback (a silent switch with no caller action)
  would contradict "enable the caller to fallback," so it is a **rejected alternative**, not an
  open choice.
- **the flag contract is `--auth as-ehmpath | as-human`, default `as-ehmpath`** — decided by
  the wisher: mirror `rhachet-roles-bhuild`'s `--auth` grammar but pared to two modes. we do
  **not** adopt bhuild's `as-robot:*` sub-grammar (`via-keyrack`/`shx`/`env`); we expose only
  `as-ehmpath` (the ehmpath-keyrack default) and `as-human` (bhuild's `gh`-cli mode), and guide
  to `as-human` on an `as-ehmpath` auth failure.
- **scope = `git.commit` push only; `git.release` excluded** — decided by the wisher: exclude
  `git.release` for now. it stays untouched, and its deliberate keyrack-only stance
  (`git.release.sh:43-44` `unset GITHUB_TOKEN`) is left intact. a later wish may revisit it.
- **the fallback keeps 2 contributors** — an as-human PR de-dups to { human, seaturtle } on
  squash; only the squash *author* flips to the human (see cons). no count regression.

**[wisher] — to confirm before build**

- none remain. the contract (`--auth as-ehmpath | as-human`, default `as-ehmpath`, guide to
  `as-human` on ehmpath auth failure), the guide-not-auto-fallback choice, and the
  `git.commit`-push-only scope are all decided.

**[research] for the build stage**

- **reuse bhuild's auth transformers?** — bhuild already owns `asGithubAuthMode` +
  `getGithubTokenByAuthArg` (`rhachet-roles-bhuild/src/domain.operations/radio/auth/`). confirm
  whether to lift/share those vs. a local pared-down parser for just `as-ehmpath|as-human`.
- **`gh pr create` under unset `GH_TOKEN`** — confirm it resolves the stored `gh auth login`
  credentials for the *create* path (spot-checked: `gh pr list` with no override works in this

- **https-remote counterexample** — a target repo whose remote is https + a credential helper
  that injects the keyrack token would break the "push is ambient" assumption. confirm whether
  any target repo is in that shape (this repo is ssh, so ambient holds here).
- **permission entries** — enumerate the new `--auth as-ehmpath|as-human` variants
  `git.commit.set` needs so the mechanic isn't blocked mid-fallback.

## groundwork

### external research

- **`gh` token resolution**: `gh` uses `GH_TOKEN`/`GITHUB_TOKEN` when set, else falls back to
  the stored `gh auth login` credentials. verified live in this session: `gh pr list` with **no**
  `GH_TOKEN` override ran successfully (exit 0), proving the human's ambient `gh` is authed and
  usable for PR ops — the exact capability `--auth as-human` leans on.

### cross-repo precedent (the `--auth` contract to mirror)

- **bhuild owns the `--auth` grammar we mirror** — `rhachet-roles-bhuild/src/domain.operations/
  radio/auth/asGithubAuthMode.ts` parses `as-robot:via-keyrack(owner)` / `as-robot:shx(cmd)` /
  `as-robot:env(VAR)` / `as-human`; `getGithubTokenByAuthArg.ts:40` defaults to
  `as-robot:via-keyrack(ehmpath)` and (`:109-116`) returns `{ token: null, role: 'as-human' }`
  to let the `gh` cli auto-login open the PR. we adopt the **`as-human`** mode verbatim and
  collapse the ehmpath-keyrack default to a single **`as-ehmpath`** token; we do not adopt the
  `as-robot:*` sub-grammar. (this corrects the r2 self-review's "no extant `--auth` vocab" note
  — there IS prior art; it lives in bhuild, not this repo's tree.)

### internal research (verified against this repo)

- **keyrack-failure dead end** — `git.commit.push.sh:307-321`: when both the primary and the
  ehmpath-fallback keyrack fetches fail, the skill prints guidance and `exit 1`. this is the
  wall the wish replaces with a guide + fallback.
- **token used only for PR ops** — `git.commit.push.sh:360` (`gh pr list`) and `:381`
  (`gh pr create`) run under `GH_TOKEN=$EHMPATHY_SEATURTLE_GITHUB_TOKEN`; the transport
  `git push` at `:339` carries **no** token override → already ambient. this confirms the
  fallback only needs to swap the PR-open auth.
- **shared token fetch** — `keyrack.operations.sh:21-61` `fetch_github_token` is the single
  source; `require_github_token:206-221` is the fail-fast variant. a shared `as-human` fallback
  branch could live next to these, but whether `git.release` opts in is *not* automatic — it
  deliberately unsets ambient tokens (`git.release.sh:43-44`), so reuse is gated on the
  `git.release` wisher question, not a given.
- **pass-through seam** — `git.commit.set.sh:701-723` delegates push to `git.commit.push.sh`
  via `--mode … --output json`; a new `--auth` flag threads cleanly through this extant seam.
- **commit authorship is orthogonal** — `git.commit.set.sh:682-690` composes the human
  co-author trailer (:682-684) and stamps the seaturtle `--author` (:687-690); `--auth`
  touches only PR-open, so authorship (and
  the `v2026_06_26.fix-seatur-contributor` guarantee for bot-opened PRs) is unaffected.

## what is awkward?

- **two "identities" in one flow** — the commit is authored by the turtle while the PR may be
  opened by the human under fallback. that split is a little surprising; the success tree must
  state plainly "PR opened as: human (fallback)" so it never reads as a bug.
- **fallback keeps the count but flips the author** — `fix-seatur-contributor` made bot-opened
  squashes show exactly 2 contributors; an as-human PR *also* yields 2 (human + seaturtle, via
  de-dup of the co-author trailers), so it does **not** regress the count. what it flips is the
  squash *author* (human, not bot). the two behaviors touch the same nerve and should be
  cross-referenced so a future reader sees the fallback preserves the count and only re-labels
  the author.
- **permissions friction** — the pre-approved exact-match list means a brand-new `--auth`
  variant could itself get blocked at the moment a mechanic most needs the fallback. the build
  must add the permission entries alongside the flag, or the guide points at a locked door.
