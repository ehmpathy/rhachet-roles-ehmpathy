# case=4: ci runs uncapped

cell #8 · ci × none · happy · critipath

## .narrative — the ci job's owner

i own a repo whose github actions workflow calls `rhx git.repo.test --what unit --mode apply --thorough`. the runner is mine for the length of the job; no other crew lands on it. my config says `maxWorkers: '50%'`, and on a 16-core runner i expect 8 workers, the same as `npm run test:unit` gives me there.

the job runs. the log shows the suite on 8 workers and the usual wall time. i never pass a flag and never think about a cap: on my own runner, the skill gets out of the way.

if the skill had capped ci too, the unit job would run on 4 workers on a 16-core runner, and every pr would wait on half a runner for no neighbor's sake. i would notice the slower job and have to hunt for why.

today no ehmpathy workflow calls the skill (`rhx git.repo.get lines --repos 'ehmpathy/*' --words git.repo.test --paths '.github/**'` → 0 matches); this repo's `.github/workflows/.test.yml` calls `npm run test:*` directly. the rule guards me, the first owner who wires the skill into ci, and any clone that runs the skill on a ci runner.

a crew on a box that sets `CI=false` sees the other side: the box counts as shared, and the cap applies as in case=1.

## .bdd sketch

```
given my ci runner (CI=true), 16 cores
  and my jest config with maxWorkers: '50%'
  when [t0] my workflow runs `rhx git.repo.test --what unit --mode apply --thorough`
    then my suite runs on 8 workers, the same as `npm run test:unit` on this runner
    then the skill sends jest no worker flag
    then the skill runs no `jest --showConfig` lookup, so my job pays no extra jest start
given a crew's box with CI=false
  when [t0] the crew runs `rhx git.repo.test --what unit --mode apply`
    then the box counts as shared
    then the cap applies as in case=1
```
