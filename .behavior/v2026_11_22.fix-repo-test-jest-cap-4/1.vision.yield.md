# 1.vision: git.repo.test caps jest at 4 workers on a shared box

## .what this builds

on a shared box (a laptop or a grove), `git.repo.test` caps jest at 4 workers. it lowers the count to 4 and never raises it. on ci it adds no cap. a caller's own worker flag always wins.

the rule, per jest run (`--what unit|integration|acceptance`, apply mode):

```
caller passed --maxWorkers / -w / --runInBand / -i after `--`  → add naught
else the npm command's jest call carries a worker flag          → add naught
else CI is set and not "false"                                → add naught
else jest's own count for this config > 4                      → add --maxWorkers=4
else                                                           → add naught
```

the skill reads the npm command's text (never runs it): a worker flag in its jest segment, and the config that segment names.

"jest's own count" comes from jest itself: `jest -c <config> --showConfig` → `globalConfig.maxWorkers`. this is the number jest would run with if the skill added no flag. if the lookup fails, the skill adds naught: an unknown count could be 1, and the cap must never raise it.

## .why it works

- **jest reads the cli flag first.** `jest-config` 30.2.0 `getMaxWorkers` (line 789) checks `--runInBand`, then cli `--maxWorkers`, then the config, then cpu count. one appended `--maxWorkers=4` overrides the repo config, so the cap needs no config edit in any repo
- **the cap lowers and never raises.** a flat flag would also override configs below 4. the survey of 66 ehmpathy repos (198 jest configs) finds 195 at `'50%'` and two integration configs at `maxWorkers: 1` (`declastruct-squarespace`, `sql-schema-control`). those suites run serial on purpose. the lookup leaves them at 1. a 4-core laptop at `'50%'` stays at 2 for the same reason
- **one worker flag, never two.** when the caller passes a count, the skill adds none and skips the lookup. jest never sees two counts to choose between
- **ci is a dedicated box.** github actions sets `CI=true`. the skill then adds no flag, and the repo config governs, the same as `npm run test:*` on that runner
- **shared is the default.** any box without `CI` gets the cap. a box the check misses runs slower but never starves a neighbor
- **the cap adds what `nice` cannot.** the skill already runs jest at `nice -n 5` (`git.repo.test.sh:1254-1266`). nice ranks cpu time against nice-0 work, so it shields a neighbor's `tsc`. it does not bound how many worker processes spawn, and every crew's jest sits at the same nice 5, so suite against suite still splits the box 18 + 18. the two compose: nice ranks, the cap bounds

## .the outcome world

### before

a 36-core grove (this one: `/proc/cpuinfo`, processors 0–35). each crew's jest asks for 18 workers (`'50%'`). two crews' suites fill the box with 36 workers. a third crew's suite then splits cores three ways with them, since all three sit at the same `nice 5`.

### after

three crews run suites at once: 12 jest workers on 36 cores. no crew's suite can take the box from the rest; 24 cores stay free for builds, type checks, clones, and the next crew's suite. each suite runs on 4 workers whether the box is busy or idle, so its time is the same on any grove.

### the aha

the neighbor never calls the skill, yet it is the one who feels the change. the cap is a courtesy one crew pays so that no crew pays a stall.

## .the contract

| surface | change |
|---|---|
| jest args (shared box, no worker flag from the caller or the npm command's jest segment, jest count > 4) | `--maxWorkers=4` appended to `jest_args` in `run_single_test` |
| jest args (all else) | none |
| stdout, a pass | none (F3) |
| stdout, a capped run past `--timeout` | a `🥥 did you know?` block after the extant hint: the run was capped at 4, and the copy-paste command to widen it (`rhx git.repo.test … -- <the caller's jest args> --maxWorkers=8`: safe to paste, no spent `--timeout`) |
| a lookup fault (timed out, or no integer) | a `💥 MalfunctionError: worker cap skipped; the suite runs uncapped` note on both streams, with `why:` and `fix:` (`-- --maxWorkers=4`) beneath it: a `├─ workers:` branch in the stdout tree, the same three lines on stderr; the run continues uncapped |
| `--help` | a `-- <jest args>` passthrough line, and a `workers:` section: the cap, the never-raise rule, the ci rule, the caller and npm-command overrides |
| `types` / `format` / `lint` | none; a multi-mode parent drops jest worker flags from a non-jest child's `-- …` |

a new `git.repo.test.workers.integration.test.ts`, in the shape of `git.repo.test.nice.integration.test.ts`: a fake `npm` on `PATH` records the args it gets; a fake `node_modules/.bin/jest` answers `--listTests` and `--showConfig` with a chosen `maxWorkers`. each case sets `CI` explicitly, so the test holds on a grove and on github actions.

## .mental model

- a crew would say: *"on the grove, tests use 4 cores so we don't hog it. on ci they use the runner. want more? pass `-- --maxWorkers=N`."*
- analogy: a lane on a shared road. on your own track (ci) you drive as fast as the car allows. on the shared road you keep to the limit, unless you know the road is empty and say so
- their words vs ours: they say "cores" and "hog"; jest says "workers". the `--help` line uses "workers", since that is the flag a crew types

## .evaluation

| goal (from the wish) | met by |
|---|---|
| shared box gets a cap of 4 | `--maxWorkers=4` when jest's count > 4 |
| ci uses every core it is configured for | no flag on ci |
| an explicit count wins | no skill flag when the caller passes one |
| a test proves each case | the proof table above |

**pros**
- one flag, zero config edits across 66 repos
- cannot regress a serial config or a small box
- cannot collide with a caller flag

**cons**
- a lone suite on an idle grove runs slower: 4 workers where it had 18. the cap trades a crew's peak speed for every crew's floor. a crew who knows the box is idle passes `-- --maxWorkers=N`
- one extra jest startup per shared-box jest run, for the `--showConfig` lookup. it only loads config; the execution stone times it
- the cap is silent in stdout (F3): a crew who wonders why a suite is slower must read `--help`

**edges and how the contract keeps the crew safe**
- config below 4 → untouched (invariant 1)
- caller count → untouched, one flag (invariant 2)
- `CI=false` → shared, capped
- lookup fails (no `node_modules/.bin/jest`, or jest cannot load the config) → no flag; the run behaves as today. a broken config then fails the real run, and jest's own load error names the fix
- acceptance npm commands carry `--runInBand` in their definition → the skill reads that, sends no flag, and skips the lookup; the suite stays at 1

## .open questions & assumptions

- **[answered]** does a cli `--maxWorkers` override the config? yes: `getMaxWorkers` checks cli before config (jest-config 30.2.0, line 789)
- **[answered]** can the skill learn jest's own count? yes: `--showConfig` prints `globalConfig` as json (`@jest/core` 30.2.0 `logDebugMessages`, line 2473), and `maxWorkers` there is the derived number
- **[answered]** does any ehmpathy npm test command already pass `--maxWorkers`? no: 0 matches across `ehmpathy/*` `package.json`
- **[answered]** does any ehmpathy ci call the skill? no: 0 matches for `git.repo.test` across `ehmpathy/*` `.github/**`. the ci rule guards the first job that does
- **[answered]** is the skill the right place for the cap? yes, for clones: `npm run test:unit` and a bare `npx jest` are not pre-approved (`rhx permissions.get --for 'npm run test:unit'` → blocked), so clones run tests through `git.repo.test`. a human who types `npm run test:*` bypasses the cap; out of scope
- **[answered]** does a grove set `CI`? this one does not (`CI` and `GITHUB_ACTIONS` empty)
- **[research]** how long does `jest --showConfig` take with a `.ts` config? the source bounds it to a config load (it exits before tests); the wall time with a `.ts` loader is unmeasured. time it in execution; if it costs more than ~1s, revisit F1
- **[answered]** does `--showConfig` print clean json on stdout? yes, from source: `@jest/core` 30.2.0 `runCLI` (`build/index.js:1411-1413`) writes the json to `process.stdout` right after `readConfigs`, then exits 0, before any pre-run message or test run. only a config file that itself prints to stdout at load would pollute it; none of the configs read here do. the skill parses it with `jq` (already a dependency, `git.repo.test.sh:214`); a parse failure falls to "no flag"
- **[answered]** does the lookup sit inside `--timeout`? it should not need to: it loads config only. it runs before the timed run, so `--timeout` keeps its sense ("the suite took too long")

- **[wisher]** F1: cap as an upper bound (min of 4 and jest's count) rather than a flat 4 — confirm
- **[wisher]** F3: no stdout line for the cap — confirm, or ask for `├─ workers: 4`
- **[wisher]** F4: on ci, the repo config (`'50%'`) governs rather than a literal 100% — confirm

## .what is awkward

- **the lookup costs a jest startup** to learn one number. the alternative is a config parse in bash, which breaks on `'50%'`, env-driven values (`rhachet-roles-bhrain`: `Number(process.env.ACCEPTANCE_WORKERS ?? 7)`), and `.js` vs `.ts`. jest's own answer is the only exact one
- **the lookup guesses the config the same way the scope preview does** (`.js` before `.ts`, lines 271 and 357), not by a read of the npm command. a repo with both files, where the npm command names the `.ts`, would get the `.js` count. the extant scope preview already lives with this guess; the cap inherits it
- **the cap is invisible** in the run's output. it is the right default and the crew rarely needs to know, but a slow suite with no visible reason is a small surprise
- **4 workers is not 4 processes.** the cap bounds jest's worker pool. a suite whose tests spawn their own children (this repo's skill tests spawn `bash`, `npm`, and fake bins per case) still fans out under each worker. the cap bounds the widest term, not the whole load
- **"4" is a constant** with no per-box tune. the wish fixes it at 4; a 64-core box gets the same 4 as a 16-core box. that is the courtesy, not a defect

## .pushback footnote

- jest `maxWorkers: '50%'` as the only bound on a local run — `jest.{unit,integration,acceptance}.config.ts` across ehmpathy (195 of 198 configs) — overturned on shared boxes by the read: a 36-core grove gives each crew 18 workers, so two crews fill the box
