# case=2: a serial config stays serial

cell #3 · shared × none × at-or-below-cap · sharp · critipath

## .narrative

a crew works in `sql-schema-control`. its `jest.integration.config.ts` says `maxWorkers: 1`, under the comment `// run in series: tests share database state and interfere when parallel` (line 35).

the crew runs `rhx git.repo.test --what integration --mode apply` on a grove. a naive cap would pass `--maxWorkers=4`. jest reads a cli `--maxWorkers` before the config (`jest-config` `getMaxWorkers`), so four suites would hit one database at once and fail at random. the crew would chase flakes the skill created.

the cap is an upper bound, not a set point. the skill asks jest what count it would use (1). 1 is at or below 4, so the skill passes naught. the suite runs serial, as the repo declared. the edge fails safe because the skill makes no change at all.

## .bdd sketch

```
given a shared box (CI unset)
  and a jest config with maxWorkers: 1  (jest derives 1)
  when [t0] a crew runs `rhx git.repo.test --what integration --mode apply`
    then jest receives no worker flag from the skill
    then the suite runs on 1 worker
    then the suites never race on the shared test database
given a shared box with 4 cores
  and a jest config with maxWorkers: '50%'  (jest derives 2)
  when [t0] a crew runs `rhx git.repo.test --what unit --mode apply`
    then jest receives no worker flag from the skill
    then the suite runs on 2 workers, not 4
```
