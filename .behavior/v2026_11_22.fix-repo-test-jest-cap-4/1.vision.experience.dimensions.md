# 1.vision.experience.dimensions

the axes along which a `git.repo.test` run varies, as far as the worker cap cares. each axis is a closed set.

## .axes

| axis | values | what decides it |
|---|---|---|
| **A. box** | `shared` · `ci` | `CI` env var: set and not `false` → `ci`; else `shared` (laptop or grove) |
| **B. caller intent** | `none` · `explicit-count` · `serial` | args after `--`: `--maxWorkers[=N]` / `--max-workers[=N]` / `-w N` / `-w=N` / `-wN` → explicit-count; `--runInBand` / `--run-in-band` / `-i` → serial; neither → none |
| **C. config count** | `above-cap` · `at-or-below-cap` · `unknown` | `jest -c <config> --showConfig` → `globalConfig.maxWorkers`, compared to 4; a failed lookup → unknown |
| **D. test kind** | `jest` · `non-jest` | `--what unit\|integration\|acceptance` → jest; `types\|format\|lint` → non-jest |
| **E. npm command flag** | `none` · `worker-flag` | the jest segment of the `test:<type>` command in `package.json` carries a worker flag in its own definition (today: `--runInBand` in `test:acceptance`, `test:acceptance:locally`) → worker-flag; else none. the skill reads the command's text (never runs it), and only the segment that calls jest |

## .why each axis is orthogonal

- **A × B**: who runs the box (ci vs crew) says naught about what flags a caller passes. a ci job can pass `--maxWorkers`; a crew can pass none
- **A × C**: the config count comes from the repo's jest config and the box's core count. both boxes can land above or below 4 (36-core grove at `'50%'` → 18; a `maxWorkers: 1` config → 1 on either box)
- **B × C**: a caller's flag does not change what the config declares; it only overrides it at run time
- **C × E**: the lookup reads the config file through `jest -c`, not the npm command. so an acceptance config at `'50%'` reports 18 while its npm command forces 1. E is the dimension the lookup cannot see
- **A × E**: the npm command is part of the repo, not the box. the same `test:acceptance` with `--runInBand` runs on a grove and on a ci runner; a box says naught about what the command carries
- **B × E**: a caller's `-- --maxWorkers=16` is appended after the command's own `--runInBand`; jest checks `runInBand` first (`getMaxWorkers:789`), so E can override B inside jest. they vary apart, and their product changes the outcome
- **D × the rest**: non-jest kinds never reach jest, so B, C, E do not apply there. D is a gate: the non-jest block collapses to one cell per box

## .the conditioned walk

the axes are orthogonal as values, but the skill reads them in order. an axis the decision never reads for a cell is marked `—` in the inventory, with the reason:

1. **D** first: non-jest → no flag; B, C, E unread
2. **B** next: explicit-count or serial → the caller's flag passes alone; C, E unread (no lookup runs)
3. **E** next: worker-flag → the command already chose; no flag, no lookup; C unread
4. **A** next: ci → no flag; C unread (no lookup runs on ci)
5. **C** last, only on `shared × none × E none`: above-cap → `--maxWorkers=4`; else no flag

the walk yields 13 cells: 11 jest, 2 non-jest. every one carries a verdict in `1.vision.experience.case=_.md`.

- **jest block** (D fixed at jest): the full product is A(2) × B(3) × C(3) × E(2) = 36. it collapses to 11 because C is read only on `shared × none × E none`, and E is unread once the caller chose (B) and moot where no count reaches jest
- **non-jest block** (D fixed at non-jest): B, C, E are unread, so A(2) = 2

## .the actors

not an axis: every cell has the same two observers.

- **the invoker** — a crew (human or clone) that runs `rhx git.repo.test`, or a ci job
- **the neighbor** — every other crew on the same shared box. it never calls the skill; it only feels the load

the neighbor's experience is the point of the wish. case=1 walks it from the neighbor's side too.

## .axes considered and folded

| candidate axis | why folded |
|---|---|
| single `--what` vs multi (`all`, comma list) | multi re-invokes the skill once per type with the same args; each child walks the same cells. case=5 walks one multi run |
| with vs without `--timeout`, with vs without other jest args | four `npm run` branches in `run_single_test`; the cap rides `jest_args`, which all four branches pass. a test row, not an experience |
| plan vs apply mode | plan mode only lists files (`--listTests`); it runs no workers and no lookup. no experience (workers [case15] pins it) |
| grove vs laptop | same box value: both are shared, neither sets `CI`. the wish names both as one case |
| npm command carries `--maxWorkers` | 0 matches across `ehmpathy/*` `package.json`; E holds only the value that occurs |

## .axes beside the cap

two axes the cap never reads. the route crossed them and found a defect on each, so each earns a cell. neither changes what jest gets for workers.

| axis | values | the cell that carries an experience |
|---|---|---|
| **F. scope** × D | `none` · `set` | `set × non-jest`: `--what types --scope X`, and so every `--what all --scope X`. the scope filters jest kinds only; a non-jest kind runs whole |
| **G. jest major** | `≤29` · `≥30` | `≤29 × scope set × plan`: the scope preview passes jest 29's path flag (`--testPathPattern`); jest 30 takes `--testPathPatterns` |
