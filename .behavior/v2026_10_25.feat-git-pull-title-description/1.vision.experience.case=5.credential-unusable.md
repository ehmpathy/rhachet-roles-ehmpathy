# case 5 — credential-unusable · sharp · critipath (fails safe)

**narrative**

the driver's keyrack session expired overnight (~9h ttl). it runs
`rhx git.pull.title set --mode apply`. the skill cannot act as the seaturtle, so it does not
fall back to whatever gh login the host has — that would write the pull as the wrong identity.
it stops before any write and names the unlock, the same guide `git.commit.push` already shows.

the human who runs the same verb with `--auth as-human` meets the other credential failure: gh is
logged out on the host. the fix differs — `gh auth login`, not the keyrack — so the skill names it.

critipath: expiry is routine. a fallback to the human's gh login would silently misattribute the
edit; a bare gh 401 would leave the driver to guess.

```
✋ ConstraintError: pull-edit credential unusable
   ├─ why: the ehmpath keyrack is locked
   └─ fix: unlock it, then retry
      └─ rhx keyrack unlock --owner ehmpath --env prep
```

**bdd `[tn]` timeline**

```
given pull #812 and a locked ehmpath keyrack
  when [t0] the driver runs `rhx git.pull.title set --title 'x' --mode apply`
    then it exits 2 with "✋ ConstraintError: pull-edit credential unusable"
    and  the message names `rhx keyrack unlock --owner ehmpath`
    and  pull #812's title is unchanged
  when [t1] the driver runs `rhx git.pull.description get`
    then it exits 2 with the same error and the same unlock — read and write share one auth step
  when [t2] the driver runs `rhx git.pull.title get` and `echo b | rhx git.pull.description set --from @stdin --mode apply`
    then each exits 2 with the same keyrack error — all four verbs refuse through the one auth step
given pull #812, `--auth as-human`, and a host where `gh` is logged out
  when [t3] the driver runs `rhx git.pull.title set --title 'x' --auth as-human --mode apply`
    then it exits 2 with "✋ ConstraintError: pull-edit credential unusable"
    and  the why names the cause: gh is not logged in on this host
    and  the fix names `gh auth login` — not the keyrack, which as-human does not read
    and  pull #812's title is unchanged
  when [t4] the driver runs `rhx git.pull.title get`, `rhx git.pull.description get`, and
           `echo b | rhx git.pull.description set --from @stdin --mode apply`, each with `--auth as-human`
    then each exits 2 with the same gh error and the same `gh auth login` fix
given pull #812, `--auth as-human`, and gh logged in
  when [t5] the driver runs `rhx git.pull.title set --title 'x' --auth as-human --mode apply`
    then the title is set — the as-human path is the same set path as cases 1–3, under the host's gh login
```
