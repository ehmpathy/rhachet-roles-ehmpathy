# 1.vision — a paved merge of origin/main into a feature branch

## .the contract, in one screen

```
rhx git.branch.catchup begin [--mode plan|apply]          # plan by default
rhx git.branch.catchup take --whos main|branch <paths…>   # settle a conflict by side
rhx git.branch.catchup lock refresh                       # regenerate a taken lockfile, stage it
rhx git.branch.catchup continue                           # make the merge commit once settled
rhx git.branch.catchup abort                              # back out to the pre-merge state
```

then, unchanged: `rhx git.commit.push --mode apply`.

the name says the outcome; the output says the rest. `--help` and every plan open with
`catch up via merge (no rewrite) from origin/main`, so a clone learns how and from what before
any mutation.

the verb is the merge-shaped twin of `rhx git.branch.rebase`: same subcommands, same tree output,
same guards. it differs in one fact that matters: it writes a new commit on top of the branch and
rewrites none, so the push that follows is a fast-forward.

## .the outcome world

**before.** a clone's pr reads CONFLICTING. its one paved path is `git.branch.rebase`. the rebase
succeeds, and the push it needs rewrites the remote branch. the harness reads that as a force push
and denies it. raw `git merge` is unpaved. the clone stops and waits for a human. measured
2026-10-27 on #1021: green on the full suite, CONFLICTING past its deadline, still CONFLICTING at
this write.

**after.** the clone runs `begin`, reads the plan, runs `begin --mode apply`. either a merge commit
lands, or the verb names each conflicted file. the clone settles them, runs `continue`, then
`git.commit.push`. the pr turns MERGEABLE. no human sees a prompt; the only human levers are the
two they already own: commit quota and sponsor bind.

**the aha.** a merge of main into a branch is the catch-up that does not touch the past. the whole
denial chain (rewrite → force → deny) never starts, so there is no gate to argue with.

**day in the life.** a crew of clones runs `rhx git.branch.catchup begin --mode apply` before each
review ask. on most days it says `already level` and spends naught. on the days main moved, it
makes one commit. on the days it conflicts, the clone gets a list of files and two exits.

the forbidden cells are the invariants:

1. never merge into main or master
2. never merge over uncommitted work, staged or unstaged. the rebase guard `is_worktree_dirty`
   reads only `git diff --name-only` (`git.branch.rebase.operations.sh`), so it passes staged
   changes; a merge would fold them into its commit. the merge guard must also read `git diff --cached`
3. never start a merge while a rebase or merge is in flight
4. never make a merge commit without a commit use left, no global or org blocker, and a sponsor found — the same gates as `git.commit.set`, through one leaf (`refuse_if_commit_gates_fail`: halts → quota read → sponsor). `begin` alone defers an absent or spent quota past the level check, so a level branch never asks for a grant it would not spend; it still refuses before any merge
5. a conflicted merge never commits; it stays in flight until `continue` or `abort`
6. a step with no merge in flight (`take`, `lock refresh`, `continue`, `abort`) refuses loud, never no-ops silent
7. plan mutates naught: where a gate guards only the mutation (uncommitted work, a rebase in
   flight, no quota), plan previews and flags what apply will refuse. on-main and a human's halt
   (global/org block, no sponsor) refuse in both modes

## .mental model

how a clone says it to a friend: *"i pulled main into my branch."* that is the phrase; `catch up`
and `level with main` are the two synonyms it reaches for.

| their word | our word | note |
|---|---|---|
| pull main in, catch up, sync with main | catch up: merge origin/main into the branch | `git.branch.catchup` names the outcome in the clone's own word; the help text names the git act (one merge commit) |
| ours / theirs | `branch` / `main` | git's pronouns flip between merge and rebase; ours never does |
| conflicts | conflicts | same word as rebase |

analogy: a rebase re-lays the branch's bricks on a new foundation. a merge pours one joint between
the old wall and the new one. the wall's history stays as built.

## .evaluation

| goal (from the wish) | met by |
|---|---|
| a paved rhx verb makes a merge commit of origin/main into the current feature branch | `begin --mode apply` / `continue` |
| same commit meter and sponsor as `git.commit.set` | reuse of the meter read/decrement and `read_sponsor_state` path; trailer appended the same way |
| conflicts stop loud, name each file, leave a fixable or abortable state | case=2, case=3; `take`, `lock refresh`, `continue`, `abort` |
| refuses on main/master; plan is the default | case=4; `--mode plan` default |
| the push that follows is plain under `git.commit.push` | HEAD is a seaturtle-authored commit and a descendant of the remote head; see Q1 for the lease flag |
| clamped red then green; temp-repo integration tests | test shape mirrors `git.branch.rebase.journey.integration.test.ts` with a bare origin |

**pros**

- no history rewrite, so no force, so no harness denial
- the shape a clone already knows from `git.branch.rebase`
- one meter spend per catch-up, regardless of the branch's commit count
- `already level` is free, so a crew can run it as a habit

**cons**

- merge commits clutter the branch log. this repo allows squash merge only
  (`gh repo view`: `mergeCommitAllowed: false`), so they never reach main here. a repo that allows
  merge commits would carry them to main
- a second verb beside rebase: a clone must pick one. guidance: `catchup` once the branch is
  pushed; `rebase` before the first push
- a fresh `lock refresh` duplicates the rebase one, because the rebase one demands a rebase in flight

**edge cases and their pit of success**

| edge | the pit |
|---|---|
| remote branch moved since fetch | the push fails non-ff and says so; `begin` merges origin/main only, so it does not cure this; the cure is open for the commander (F25, cell #38) |
| branch has zero commits ahead | a merge would fast-forward to main and leave HEAD authored by a human, so the push guard refuses. `begin` always makes a real merge commit (`--no-ff`); see Q5, inventory #5b, `case=1` `[case1b]` |
| husky `commit-msg` runs commitlint on the merge message | the default header is conventional (`cont(branch): …`), so it passes |
| a delete-vs-modify conflict | named by its git status; `take` of the deleted side runs `git rm`, of the other side checks out + stages (inventory #25) |
| worktree checkouts (`.git` is a file) | detect the merge via `git rev-parse -q --verify MERGE_HEAD`, never a `.git/` path |

**assumptions**

- the robot identity for author follows `git.commit.set`: `seaturtle[bot]`, or `ehm-a-seaturtle[bot]`
  under an ehmpath token (`keyrack.operations.sh:158-164`)
- no commit signatures are in play (none in `git.commit.set`)
- the claude auto-mode check permits `rhx git.commit.push --mode apply` when the push is a
  fast-forward. the evidence for the denial comes from task #1193 alone (rebased head 37e8265, push
  denied as Security Weaken); no merge-then-push has been tried. the final proof is the live push of
  this route's own pr, which carries a merge commit if main moves before release
- the merge commit's committer is the ambient git config, as in `git.commit.set` (only `--author`
  is set, `git.commit.set.sh:1213-1216`)
- `git merge` takes no `--author`, so the seaturtle author and the sponsor trailer need a two-step
  commit: `git merge --no-ff --no-commit origin/main`, then `git commit --author … --message …`.
  `continue` runs that same second step. one commit path for both, so clean and conflicted merges
  cannot drift apart in author or trailer
- husky `pre-commit` (yalc, timestamps) and `commit-msg` (commitlint) run on that commit, as on any
  `git.commit.set` commit
- the permission entry `Bash(rhx git.branch.catchup:*)` joins the allowlist beside the rebase entries
  (`init.claude.permissions.jsonc:424-443`)

## .what is awkward

- **`ours` / `theirs` flip.** in a rebase `ours` is main; in a merge it is the branch. a clone that
  runs both in one week will take the wrong side once. `--whos main|branch` fixes it for merge, and
  leaves the two verbs with different flag values for one concept. that asymmetry is the price
  until rebase gains the same aliases (Q7)
- **"plain" push with a lease flag.** the wish says plain; the push skill says `--force-with-lease`.
  on a fast-forward the two act the same. if a classifier reads the flag as a force, this is where
  it bites. whether this route touches the push skill is the commander's call (Q1)
- **the rebase twin carries debt the merge verb must not copy.** `git.branch.rebase begin` claims a
  meter decrement in its header that it never makes, exits 1 on constraints, and reads `$?` after
  `|| true`. the merge verb must not inherit these by copy; each is a reason to share only the
  operations file, not the scripts
- **the git act and the verb name differ.** the verb says `catchup`; under the hood it is a git
  merge. the name was chosen so, since "merge" here already lands a pr into main
  (`gh pr merge`, `git.release.sh:6`). the help text and the plan output name the act plainly
  ("one merge commit of origin/main into this branch"), so a clone that reads `git log` meets no
  surprise
- **two catch-up verbs.** a clone must choose. the rule of thumb (`catchup` once pushed, `rebase` before)
  must live in the help text, or clones will reach for rebase from habit and hit the force wall again
