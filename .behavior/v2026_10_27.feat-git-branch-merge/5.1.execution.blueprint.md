## .the gate order (vision invariants 4 + 7)

1. on main/master → refuse, both modes (exit 2)
2. global blocker, org blocker → refuse, both modes (exit 2; a corrupt file exits 1, as in `git.commit.set`)
3. no sponsor found → refuse, both modes (exit 2)
4. a rebase or merge in flight → plan flags, apply refuses
5. uncommitted work, staged or unstaged → plan flags, apply refuses
6. no quota file / zero uses → plan flags, apply refuses
7. fetch `origin/main` → fails loud, exit 1
8. behind 0 → `already level`, exit 0, no meter spend

conflict stop: exit 2 with `✋ ConstraintError`, each file named, next steps `take` / `continue` / `abort`.

## .open questions for the commander

each is his call. options are listed in no order of preference.

### C1 — how does the commit step reach the meter, sponsor, and gates of `git.commit.set`?

the gates and the meter write sit inline in `git.commit.set.sh` (:709-998, :1107-1112,
:1324-1354); `git.commit.operations.sh` holds readers only, no meter write.

| option | what it means | cost |
|---|---|---|
| a. compose | `begin` and `continue` call `git.commit.set -m @stdin --mode apply --unstaged ignore`; with `MERGE_HEAD` set, its plain `git commit` makes the merge commit | zero copy, zero drift. the gates run AFTER the merge starts: a refusal there leaves the merge in flight (abortable), unless `begin` also pre-checks. `git.commit.set` plan skips the quota check (:789), so a pre-check needs its own read. a merge whose tree equals HEAD trips its "no staged changes" refusal |
| b. extract | lift the gates, sponsor lookup, and meter write into `git.commit.operations.sh`; `git.commit.set` and catchup both call them | one source; touches a heavily-tested skill, so its suites must stay green; a larger diff |
| c. duplicate | copy the gate and meter code into catchup | smallest touch to extant code; two copies to drift (the rebase twin already drifted: its header claims a decrement it never makes) |
