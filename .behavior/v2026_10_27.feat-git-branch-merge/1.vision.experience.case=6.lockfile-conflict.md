# case=6.lockfile-conflict

cells: #7 · #24 · #25c · #25d (`[case6b]`) · feel sharp → happy · care alterpath (chosen: common enough that the rebase verb paved a cure for it)

## .narrative

main bumped a package; so did the branch. `pnpm-lock.yaml` conflicts. a
hand edit of a lockfile is wrong by construction. beaver takes main's lockfile, then refreshes it
against the merged `package.json`, which re-adds the branch's own bump. the fresh lock is staged.
`continue` commits the merge.

the side names are `main` and `branch`, never `ours` and `theirs`: in a merge git's `ours` is the
branch, in a rebase it is main. a clone that runs both verbs in one week must not have to recall
which is which.

## .bdd

```
given('[case6] branch and origin/main both edit package.json deps; pnpm-lock.yaml conflicts')
  when('[t0] begin --mode apply')
    then('exits 2; names pnpm-lock.yaml')
  when('[t1] take --whos main pnpm-lock.yaml')
    then('the file holds origin/main content and is staged; nudges lock refresh')
  when('[t2] lock refresh')
    then('the lock matches the merged package.json and is staged')
  when('[t3] continue')
    then('the merge commit lands; meter −1')
given('[case6b] pnpm-lock.yaml and package.json both conflict')
  when('[t0] take --whos main pnpm-lock.yaml, then lock refresh, with package.json unsettled')
    then('lock refresh exits 2; names package.json as the file to settle first; the lock is not regenerated')
```

a refresh reads `package.json` as is. while that file holds conflict markers, a refresh would fail
or write a lock against half a manifest, so `lock refresh` refuses until every manifest is settled.
