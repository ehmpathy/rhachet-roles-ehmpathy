# experience dimensions: pressViaPipeline test suite

actor = a test run: ci (pr shard or main publish) or a crew box (clone or human at a terminal).

## .dimensions

| dim | axis | closed value set |
|---|---|---|
| D1 | where it runs | ci · crew box |
| D2 | live flag `BRAIN_LIVE_SCOPE` | unset/empty · `all` · any other value (typo) |
| D3 | suite | deterministic (unit, fake compressor) · live (integration, real brain) |
| D4 | pipeline code state | sound · regressed (a step not threaded, tokens miscounted, mechanisms dropped) |
| D5 | live brain outcome, given keys unlocked | compresses · grows output · placeholder · timeout · transport error (rate limit, 5xx, network) |
| D6 | credential state for the live ask | unlocked · locked · absent (never filled) · rejected (present and unlocked, but the provider refuses it: revoked or expired, a 401/403) |
| D7 | pipeline input shape | single-step · multi-step · req-kernels · empty content · empty pipeline |
| D8 | compression cache state | bypassed (`force: true`) · hit · miss |

orthogonality: D6 is a resource state, apart from what the brain does. a locked or absent key fails before any ask, so D5 occurs only at D6=unlocked. D5 is the full outcome of one ask: a reply (the first three values) or no reply (the last two). an auth refusal belongs to D6, not D5. D7 is what the caller hands pressViaPipeline, apart from where it runs or whether the code is sound. empty content and empty pipeline return before any ask (`pressViaPipeline.ts:48,57`), so they never reach D5 or D6. D8 is the on-disk cache that wraps `compressViaBhrain` (`compress.via.bhrain.ts:462`), apart from what the brain would reply. a hit returns a stored reply and asks no brain.

## .the walked product

- D3=deterministic ignores D2, D5, and D6: it calls no brain and reads no key. it varies on D1 × D4 only.
- D3=live varies on D1 × D2 × D6 × D5. D4 shows through it too, but the deterministic suite owns that clamp.
- D2 unset: the live suite body never runs, so D5 and D6 never apply.
- D2 typo: the gate refuses at collection, so D3, D4, D5, and D6 never apply.
- D2=`all`: D1 does not change the outcome. ci × `all` (#6) inherits every D6 and D5 cell below, so those cells are walked once, not per D1 value.
- D7 in the deterministic suite: each shape is its own cell, walked at D4=sound. D4=regressed is walked once (#2, #4), on the multi-step shape that exposes a broken thread.
- D7 in the live suite: one run asks all three ask shapes (single-step, multi-step, req-kernels) in sequence, so a D5 or D6 outcome applies per run, not per shape. the two empty shapes are not in the live suite: they never ask.
- D8 collapses to one value per suite. the deterministic suite injects a fake, so the cache is never in its path (nature). the live suite must pass `force: true` on each ask case, so a hit or miss there is forbidden (nurture); see forbidden in the inventory.

reduced cells (see `1.vision.experience.case=_.md`):

1. D1 × D4, deterministic suite → 4 cells (#1-4)
2. D1 × D2, live gate → 6 cells (#5-10)
3. D2=`all` × D6 ∖ {unlocked} → 3 cells (#15 locked, #17 absent, #23 rejected)
4. D2=`all` × D6=unlocked × D5 → 5 cells (#11-14, #16)
5. D7 × deterministic suite, D4=sound → 5 cells (#18-22)

total: 23 cells, the 23 rows of the inventory.
