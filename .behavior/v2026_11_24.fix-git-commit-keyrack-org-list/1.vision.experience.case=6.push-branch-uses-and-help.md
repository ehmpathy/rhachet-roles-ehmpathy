# case=6 — push and branch.uses share the gate; help declares the rule

feel: happy (t0, t3, t4, t5), sharp (t1, t2, t6, t7) · care: critipath · cells: A.14a, A.14b, A.15, A.15b

## narrative

a clone in a list repo commits with `git.commit.set --push`. the push half runs `git.commit.push`, which calls the same `check_org_blocker`. so one fix serves both; a list repo whose orgs all allow pushes too.

push has its own refusal print. today it tells a missed keyrack file apart by a string match on the reason (`git.commit.push.sh:321`), and every other keyrack fault falls to the meter remedy. after: push keys off the same named keyrack-fault flag as `git.commit.set`. it prints the keyrack.yml remedy for any keyrack fault: absent, empty, or unreadable.

a clone in the same list repo runs `git.branch.cutover`. `git.branch.uses` gates the switch on the same reader, so the list admits or refuses the cutover the same way: pass when both orgs allow, refuse and name bhanya when bhanya is blocked. its remedy has the same defect as set's: `git.branch.uses.operations.sh:380` names `allow --org <org>` for any org refusal. after: it reads the keyrack-fault flag too.

a clone that wonders why a list repo refused runs `git.commit.set --help`. the help states the rule in one line: every org in `.agent/keyrack.yml` `org:` must allow commits. a human about to grant runs `git.commit.uses --org --help` and reads the same rule from the grant side.

## bdd sketch

```
given a repo whose .agent/keyrack.yml declares org: [ahbode, bhanya], both allowed
  when [t0] git.commit.push --mode apply
    then the org gate passes (no org refusal in output)
given the same repo, bhanya blocked
  when [t1] git.commit.push --mode apply
    then exit 2, gate org bhanya, remedy: git.commit.uses allow --org bhanya
given a repo whose .agent/keyrack.yml declares org: []
  when [t2] git.commit.push --mode apply
    then exit 2, output names the keyrack.yml remedy, not allow --org
given any repo
  when [t3] git.commit.set --help
    then its requires: section states: every org listed in .agent/keyrack.yml org: must allow
    then output names the accepted shapes: scalar, block list, flow list
  when [t4] git.commit.uses --org --help (the help a human reads to grant)
    then output states: a repo whose keyrack lists several orgs needs each one allowed, or @all
given a repo whose .agent/keyrack.yml declares org: [ahbode, bhanya], both allowed for branches
  when [t5] a clone runs git.branch.cutover, gated by git.branch.uses
    then the org gate passes (no org refusal in output)
given the same repo, bhanya blocked for branches
  when [t6] the clone runs git.branch.cutover
    then exit 2, gate org bhanya, remedy: rhx git.branch.uses allow --org bhanya
given a repo whose .agent/keyrack.yml declares org: []
  when [t7] the clone runs git.branch.cutover
    then exit 2, output names the keyrack.yml remedy, not git.branch.uses allow --org
```

`[t4]` matters as much as `[t3]`: the human grants, so the human must learn the rule at the moment of the grant. otherwise they allow member 0 alone and meet a refusal on the next run.

`[t5]`-`[t7]` walk `git.branch.uses` through the same three verdicts as push's `[t0]`-`[t2]`, each with its own remedy text.
