# case=2 — a list with one blocked org is refused

feel: sharp · care: critipath (t0, t1), alterpath (t2) · cells: A.3, A.4, A.5

## narrative

the human paused all work for bhanya: `git.commit.uses block --org bhanya`. `@all` stays allowed for the fleet.

a clone in a repo with `org: [ahbode, bhanya]` runs `git.commit.set`.

before: the flow form read as one org literally named `[ahbode,bhanya]`. the meter held no such key, so the gate fell to `@all: allowed` and the commit landed. the human's bhanya block leaked.

after: the gate checks every member. bhanya is blocked, so the gate refuses, names bhanya, and says why bhanya is in play:

```
🐢 bummer dude...

🐚 git.commit.set
   └─ ✋ ConstraintError: commits blocked for org bhanya
      ├─ .agent/keyrack.yml org: lists ahbode, bhanya
      └─ every listed org must allow commits

ask your human to allow:
  $ git.commit.uses allow --org bhanya
```

(the header and instruction match extant `output.sh` `print_tree_constraint` / `print_instruction`; the two sub-branches are new.)

exit 2. the remedy names the one org that blocked, not a placeholder.

`[t2]`: a member the human never configured, with no `@all`, refuses the same way and names that member: `no org config for bhanya`.
