# case=5 — a consumer patches an installed file

feel: happy (t0), sharp (t1, t2), happy after the upstream fix (t3) · care: critipath · cells: B.0, B.1, B.2, B.3

## narrative

a consumer needs a one-line local fix to `git.commit.operations.sh`. they run `pnpm patch rhachet-roles-ehmpathy` and hit `ERR_PNPM_PATCH_FAILED`: the files are `r-xr-xr-x`.

they wipe `node_modules` and re-install, and expect fresh files. the role files still read `r-xr-xr-x`, and the patch fails again.

this package does not cause it. the tarball carries 0644 / 0755 like any npm package. the 0555 arrives later: `rhachet roles link` walks each linked role dir and runs `chmodSync(path, 0o555)` on every file. pnpm hardlinks package files to its content store, so the chmod likely lands on the store copy too (inferred from the file/dir mode split; see F2). that would explain why a re-install does not clear it.

after this work:

- this package proves its own half. a test packs the package and asserts every file is 0644, or 0755 for an executable skill.
- the cause gets fixed where it lives. a task to `ehmpathy/rhachet` asks the link step to leave package files alone, or to restore their modes on unlink.
