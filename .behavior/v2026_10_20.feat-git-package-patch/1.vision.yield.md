# 1.vision — git.package.patch

## .the outcome world

a crew hits a defect in a dependency. it dispatches the fix upstream, then patches its own tree
through one paved verb:

```sh
rhx git.package.patch begin  --package rhachet --mode apply
# edit files in the dir it names
rhx git.package.patch commit --package rhachet \
  --why 'enroll hook leaks into peer repos' \
  --upstream https://github.com/ehmpathy/rhachet/issues/580 \
  --mode apply
```

the patch file, the `patchedDependencies` entry, and a note that says who, when, why, and where
the upstream fix waits all land in the tree, ready for the pr. no harness prompt fires.

| | before | after |
|---|---|---|
| the call | raw `pnpm patch rhachet@1.48.1` — a novel shell command | `rhx git.package.patch` — pre-approved |
| the harness | auto-mode reads it as a weakened control; crew sits until a director clicks | no prompt |
| the version | `pnpm patch rhachet` opens an interactive picker; crew stalls, hand-writes hunks | version resolved from the tree, or named `name@version` |
| the why | the patch file records none | a note beside the patch: who, when, why, upstream |
| the bound | whatever the shell allows | edit dir and patches dir inside the tree, or refused |

**the aha:** the commander says patches are expected. now the paved path says so too — the cheap
command is the safe one, and it leaves the trail a reviewer needs to retire the patch later.

## .the contract

| subcommand | inputs | does |
|---|---|---|
| `begin` | `--package <name>[@<version>]`, `--edit-dir <dir>` (optional, default `node_modules/.pnpm_patches/<name>@<version>`), `--mode plan\|apply` | `pnpm patch <name>@<version> --edit-dir <dir>`; reuses an open dir |
| `commit` | `--package`, `--why` (required), `--upstream <url>` (required), `--edit-dir` (optional), `--mode plan\|apply` | `pnpm patch-commit <dir> --patches-dir patches`; upserts the note; removes the edit dir |

- plan is the default; `--mode apply` writes
- exit 0 success · 2 constraint (bad input, escape, absent edit) · 1 malfunction (pnpm failed)
- every refusal is `✋ ConstraintError:` on stdout + stderr and names the fix
- the note lives at `patches/<name>@<version>.patch.note.md`, beside the patch it explains
- `commit` refuses when git identity is absent (`user.name` / `user.email`), since the note needs a who
- permissions: `rhx git.package.patch:*` and its `npx rhachet run --skill` twin join the mechanic
  allowlist; `pnpm patch` and `pnpm patch-commit` join `commands.alternatives.jsonc`, so a raw
  call is redirected to the verb

## .mental model

to a friend: *"it's `git rebase` for a dependency — `begin`, edit, `commit` — and it makes you
say why and where the real fix is."* the crew's words: patch, why, upstream issue. ours: edit dir,
`patchedDependencies`, note. the verb uses the crew's words at its surface (`--why`, `--upstream`).

## .evaluation

**goals met**
- one paved verb → no novel command for the classifier to judge (wish 1, 6)
- why + upstream required → no orphan fork (wish 2, 3)
- edit dir resolved and bounded to the tree; no store or global flag exists → wish 4
- plan default, apply explicit, re-run converges → wish 5

**pros**: removes the picker stall from #926; reuses the `begin`/`commit` shape crews know from
`git.branch.rebase`; the note gives a later reviewer the retire signal.

**cons**: two calls, not one — the edit sits between them by nature. the note is a second file
beside each patch.

**edgecases held in the pit of success**: several versions installed → refuse and list them;
not installed → name `set.package.install`; npm lockfile → refuse (pnpm-only); no edits → refuse;
escape → refuse. see the inventory for each.

## .open questions & assumptions

no route research stone exists (nano: vision → execution → verification), so `[research]` items
are settled by the execution tests, before any code leans on them.

- **[research]** where does pnpm 10.24 `patch-commit` record `patchedDependencies` — `package.json`
  under `pnpm`, or `pnpm-workspace.yaml`? does it run an install after? the note path does not
  depend on the answer; the tests assert whichever pnpm does
- **[research]** does `pnpm patch --edit-dir <dir>` refuse a non-empty dir? the design does not
  depend on it: `begin` detects an open dir and skips pnpm either way
- **[research]** do several installed versions show as `node_modules/.pnpm/<name>@<version>*` dirs?
  under `node-linker=hoisted` only the top-level copy is visible, so the verb resolves that one
- **[answered]** default edit dir — the verb's own choice, passed explicitly; it never leans on
  pnpm's default
- **[answered]** "who" = `git config user.name <user.email>` of the tree that made the patch; no
  sponsor lookup. on a clone's box it names the bot, which did author the patch
- **[answered]** error format — follow `rule.require.qualified-error-headers` (`✋ ConstraintError:`),
  a divergence from the peer `set.package.*` verbs' bare `print_error`
- **[answered]** workspace scope — the verb targets the git root's `package.json`, which is where a
  pnpm workspace rooted there keeps `patchedDependencies` (c21). a workspace rooted below the git
  root is out of nano scope; the verb refuses when the git root holds no `package.json` (c21b)
- **[answered]** hoisted repos (#772) — fail loud via pnpm's own error; the `git apply` fallback is
  deferred with F2
- **[wisher]** F1–F5 (name, nano scope, two calls, note location, why on commit) — best-guessed,
  all clean reworks; listed in `.fulcrums/`
- **[wisher]** close #1014 as superseded, and keep #926 open for get/check/del, or close it with the
  dream as follow-up? the pr will propose: close #772 + #1014, keep #926 open

## .what is awkward?

- **two calls.** a one-shot `--diff @stdin` form would be one call, but it asks the crew to
  hand-write hunks — the exact pain #926 records. the edit belongs to the crew's Edit tool
- **the name.** the wish fixes `git.package.patch`, yet the verb is a pnpm act, not a git act;
  the sibling verbs are `set.package.*`. kept as the wish names it (fulcrum F1)
- **why on commit only.** a crew can edit, then learn at commit that `--why` is required. cheap to
  retry; `begin` prints the full commit command with both flags so the ask is seen up front
- **hoisted repos** still lose: pnpm cannot apply there. out of nano scope
- **vendor edits meet our term hooks.** the gerund + blocklist hooks have no `node_modules`
  exemption, so an edit of third-party code that holds a blocklisted word is refused once (a retry
  overrides). our prose rules should not grade vendor code — a dream, not this round
