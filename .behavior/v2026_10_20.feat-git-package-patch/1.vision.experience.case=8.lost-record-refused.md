# case=8 — a rebase dropped the record that applies a sealed patch

feel = sharp → happy · care = critipath (a patch on disk that pnpm no longer applies is a silent revert) · covers c25, c25b

## .narrative

a crew sealed a patch last week. today it rebases onto main, and the merge drops the
`patchedDependencies` line, or the lockfile's `path:` for the patch. the patch file and its note
are still in `patches/`, so at a glance all is well — but pnpm no longer applies it.

the crew reruns the same commit, out of habit. the verb does not say "already sealed". it says
which record is absent and how to restore it, in one line: put back the entry it names, or run
`pnpm install` for the lockfile. it refuses `begin` too: a pristine reopen would open the package
without the patch, and a reseal from there would quietly drop the edits. the crew restores the
line, reruns, and gets the no-op it expected.

## .timeline

```
given a pnpm repo where patches/is-number@7.0.0.patch was sealed with its note
  when [t1] the lockfile loses its `path:` line, and the same commit reruns
    then exit 2: the lockfile record is absent; run pnpm install, then rerun this same commit
    then the output never says "already sealed"
  when [t2] the patchedDependencies entry is dropped, and the same commit reruns
    then exit 2: the entry record is absent
    then the fix names: restore the patchedDependencies entry "is-number@7.0.0": "patches/is-number@7.0.0.patch"
  when [t3] begin --package is-number --mode apply, with the entry still absent
    then exit 2: no patchedDependencies entry names it; no edit dir is opened
  when [t4] the entry is restored, and the same commit reruns
    then exit 0: already sealed with this note; naught changed
```

proven by `[case7c]` in the integration suite (`[t4]` by `[case1]`'s rerun no-op).
