# 1.vision.experience.case=10 — an upgrade past a patch lands, and the stale patch surfaces

cells: c27, c28, c29, c30, c33 (critipath)

## .narrative

a crew patched `is-number@6.0.0` last month; the seal also wrote `allowUnusedPatches: true` and
`ignorePatchFailures: true` into `pnpm-workspace.yaml`. today `rhx upgrade` moves the tree to
`is-number@7.0.0`. the install lands: the old entry is unused, and pnpm warns rather than fails.

the fork has quietly dropped, so the crew's next stop says so. the onStop hook prints a nudge:
`is-number@6.0.0: underapplied`, the reason, and two commands. the first reopens the patch on
7.0.0; the second retires the stale one. the stop is not blocked.

the crew runs `rhx git.package.patch check` by hand, sees the same verdict on exit 2, then decides
upstream already fixed it. `del --package is-number --mode apply` drops the entry, the patch, and
the note, reinstalls the pristine copy, and names each file to stage. a rerun says naught changed.

## .timeline

given a pnpm repo with `is-number@6.0.0` installed
  when [t0] the crew begins, edits, and commits a patch
    then the patch, note, and entry land, and `pnpm-workspace.yaml` is upgrade-safe
    then a frozen install under `CI=true` still lands
  when [t2] `check` runs, and the stop hook fires
    then `check` exits 0 with `applied`; the hook prints naught
  when [t2.1] the keys are stripped and the package is upgraded
    then the install fails on the stale patch (the clamp the keys cure)
  when [t3] the keys stand and the package is upgraded to 7.0.0
    then the install lands
  when [t4] `check` runs, and the stop hook fires
    then `check` exits 2 and names `underapplied` with the reopen and `del` commands
    then the hook prints the same nudge and exits 0
  when [t6] `del --package is-number --mode apply` runs
    then the entry, patch, and note are gone, and the lockfile no longer names the patch
  when [t7] `del` runs again
    then it is a no-op, and `get` names no patch
