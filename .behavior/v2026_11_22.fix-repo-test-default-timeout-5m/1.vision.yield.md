# vision: a slow git.repo.test run halts at 5 minutes

## .what this builds

`rhx git.repo.test` gains a default time bound of 300s. a run with no `--timeout` that passes 5 minutes is halted, and the halt says "woah, too slow" and names the speed defect as the driver's own to root cause.

five changes, all in `src/domain.roles/mechanic/skills/git.repo.test/git.repo.test.sh`:

1. **default bound** — `TIMEOUT` defaults to `300` (today `""`, `git.repo.test.sh:550`). an explicit `--timeout N` replaces it, wider or tighter
2. **the halt speaks to the owner** — the halt branch (`git.repo.test.sh:1686-1718`) renders `⏱️ too slow`, header "woah, too slow", names the bound and its source (`default` or `--timeout`), and says the speed defect is the driver's to root cause. it exits **2** (constraint), not 1
3. **multi-mode carries the bound** — `--what all` and comma lists forward `--timeout` to each child (today dropped, `git.repo.test.sh:1445-1461`). the bound is per type
4. **bad bounds fail fast** — `--timeout` that is not a positive integer halts at parse with `✋`, before any suite runs
5. **the bound is visible from the start** — the run tree opens with `bound: Ns (default|--timeout)`, so the fuse is known before it blows (`rule.require.status-feedback`)

a test file proves the halt, its message, the exit code, the explicit bound, and the multi-mode carry.

one brief follows: `src/domain.roles/mechanic/briefs/practices/code.test/lessons.howto/howto.run-tests.[lesson].md` lists the commands (lines 15-23) and names no bound; it gains one row for `--timeout` and one line on the 5m default, so a driver learns the fuse before it first blows — plus one line that the caller's own shell call needs a limit above the bound, or the caller's clock fires first.

## .why it works

- the bound is enforced where the cost lands: one `timeout` wrap around `npm run`, already in place for explicit bounds (`git.repo.test.sh:1254-1259`). the change makes that path the only path
- one path for default and explicit: the same halt, the same exit; only the `bound:` line differs. no new branch to keep in sync
- exit 2 routes the slow suite to its owner. per `rule.require.exit-code-semantics`, 1 = "retry may help", 2 = "caller must fix". a slow suite is the caller's code; a retry only burns another 5 minutes
- the 5m default targets the common case: runs are scoped by default (`--changedSince`, `git.repo.test.sh:305-307`) or by `--scope`; a suite long by nature states its own `--timeout` (see "does 5m fit the common case?" below)

## .the outcome world

before: a drive runs `--what integration`. it takes 14 minutes. it passes. the seat and the core are held the whole time, and the next drive inherits the same 14 minutes.

after: the same run halts at 5 minutes with "woah, too slow — this speed defect is yours to root cause". the driver reads the log, finds the suite that boots a server per test, hoists the setup, and the run drops to 90s. the aha: the slowness was always a defect; it only now has a voice.

## .mental model

a driver would tell a friend: "test runs have a 5 minute fuse now. if yours blows, your suite is slow — fix it, or say up front it needs longer."

| driver says | we say |
|---|---|
| fuse, time limit | bound |
| blew the fuse | halted, too slow |
| "it needs longer" | explicit `--timeout` |

## .evaluation

goals:
- halt past 5m with no explicit bound → yes, default `TIMEOUT=300`
- "woah, too slow" + owner named → yes, the halt render
- explicit bound wins → yes, `--timeout` replaces the default, and now also in multi-mode
- a test proves it → yes, see the test plan below

pros:
- reuses the extant `timeout` path; small diff
- one halt path for default and explicit
- fixes a latent bug: multi-mode drops `--timeout`

cons:
- a suite long by nature now needs `--timeout`; the first run of such a suite halts once
- exit code for an explicit-bound halt moves 1 → 2 (a contract change; see pushback footnote)

edges, and how the contract keeps the driver in the pit of success:
- **suite at 4m59s** → passes; the bound is a cap, not a target
- **`--timeout abc` / `0`** → `✋` at parse, valid shape named, exit 2; never reaches `npm run`
- **`--when hook.onStop`** → a slow suite halts at 5m with exit 2, so the stop hook blocks with the "too slow" message. the stop is not silently held for 14 minutes
- **plan mode** → runs no suite; the bound has no effect
- **routes that run whole suites** → `declapract.upgrade`'s stone `3.1.repair.test.defects.guard` (lines 78-80) runs `--what integration` and `--what acceptance` with no `--timeout`. a slow suite there now halts "too slow" mid-upgrade. that is the wish at work, not a regression: the route's driver meets the speed defect it would have silently paid for. no template change
- **halt with `--resnap`** → jest writes snapshots per file, so a cut run leaves them partly updated. the halt adds one line: snapshots may be partial; rerun once the suite is fast
- **halt skips jest `globalTeardown`** → a local server or fixture may outlive the run. see [research] below
- **orphan workers** → gnu `timeout` signals the whole process group (only `--foreground` spares children), and jest workers share it (see "does the halt reach jest's workers?" below)

### test plan

the default is 300s; a test cannot wait 5 minutes. tactics, all hermetic temp repos like the extant `[case22]` (`git.repo.test.integration.test.ts:1327-1395`):
- **message + exit**: `--timeout 1` with `test:lint = sleep 5` proves the halt render, `bound: 1s (--timeout)`, exit 2 (extant case, snapshot updated)
- **default bound is 300s**: a PATH-shim `timeout` (`howto.mock-cli-via-path.[lesson].md`) records its argv and delegates; assert `300s` was passed when no `--timeout` is given, and that the render names `bound: 300s (default)` when the shim exits 124
- **multi-mode carry**: same shim; `--what lint,unit --timeout 7` asserts each child got `7s`

## .open questions & assumptions

- [answered] **exit code on halt?** 2. the wish calls the slow suite the driver's own defect; that is a constraint by `rule.require.exit-code-semantics`. fulcrum F1
- [answered] **does the explicit-bound halt also say "too slow"?** yes. one halt path; the `bound:` line names the source. fulcrum F2
- [answered] **validate `--timeout`?** yes, positive integer seconds. today a bad value reaches `timeout` and exits 125, read as a test failure. fulcrum F4
- [answered] **opt-out (`--timeout none`)?** no. the wish names no opt-out; a long suite states a number. fulcrum F5
- [answered] **does the halt reach jest's workers?** yes, under gnu `timeout`. it signals its process group; jest-worker 30.2.0 forks each worker with no `detached` option (`node_modules/.pnpm/jest-worker@30.2.0/node_modules/jest-worker/build/index.js:762-777`), so workers share that group. execution still clamps it with a test (a `test:lint` that spawns a child `sleep`, asserted gone after the halt), and adds `--kill-after` if a child ignores SIGTERM
- [research] **teardown on halt**: SIGTERM ends jest before `globalTeardown`. execution checks whether a halted `test:acceptance:locally` leaves a server alive (its process group should die with `timeout`); a detached server (own session) would need its own cleanup, which is the suite's defect to own, named in the halt hint
- [research] **`timeout` on every host**: gnu `timeout` ships on linux; stock macOS has none (coreutils installs it as `gtimeout`). today only `--timeout` callers need it; an always-on default makes every run need it. execution looks up `timeout` → `gtimeout` → a bash watchdog so the bound never depends on the host. a run must never fail only because the fuse tool is absent. pavement exists: `run_watch_bounded_bare` (`git.pull.watch/git.pull.watch.operations.sh:316-345`) is a tested watchdog that yields 124 on the bound. it signals only the direct pid, which here would orphan jest under `npm`; reuse needs a group signal, and reuse across two skills lifts it to a shared home (`rule.prefer.most-common-denominator`). what stays to research: a group signal with no `setsid` on macOS (`set -m`). fulcrum F6
assumptions, each settled or sent on:

- [answered] **does the bound cover the suite, or the whole call?** the suite. it wraps `npm run` only (`git.repo.test.sh:1254-1259`). keyrack unlock and the `--listTests` scope preview run before it, unbounded. they are the skill's own setup, not the caller's suite, so a slow unlock is a tool defect, not "too slow"
- [answered] **does exit 124 always mean the fuse fired?** no. the halt branch keys on exit 124 (`git.repo.test.sh:1686`). a suite that exits 124 by itself would read as a halt; and `--kill-after` yields 137 on a KILL. execution keys the halt on "the bound expired" (elapsed ≥ bound, or the fuse's own code), not on 124 alone
- [answered] **does the skill's fuse fire before the caller's own clock?** only if the caller allows it. a clone calls the skill through its harness's shell tool, which has its own limit (claude code's Bash tool: 2 min default, 10 min max; background runs of this skill are blocked by `pretooluse.forbid-test-background.sh`). a caller limit under 300s kills the run first, with no "too slow". the skill cannot see that clock; R11's brief line tells the caller to give the shell call more than the bound (e.g. 330000 ms for the default)
- [answered] **does 5m fit the common case?** taken as given: a scoped or `--changedSince` run of a healthy suite ends well under 5m. not measured here; the wish sets 5m, and a run that disproves it is itself the slow-suite signal the wish wants
- [wisher] **`--what all`: 5m per type, or 5m for the whole call?** the wish says "a git.repo.test run"; one `--what all` call is one run to its caller, yet it spawns one child run per type. the vision drives on per type (fulcrum F3: smaller diff, each child already a full run). a total bound is a clean rework in the multi-mode loop

## .what is awkward

- the extant halt render repeats `status` twice (a `status` parent, then `status: malfunction`). the new render should drop the second, or tests will pin the blemish again
- `DISPLAY_ARGS` does not echo `--timeout`, so the tree header hides the caller's bound. the `bound:` line covers it; to echo `--timeout` in the header too is a small fix in reach
- a legit long acceptance suite pays one halt before its caller learns to state `--timeout`. the halt's last hint names that move, so the cost is one run
