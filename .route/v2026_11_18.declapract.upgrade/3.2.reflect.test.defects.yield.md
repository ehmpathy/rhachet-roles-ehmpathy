## D1a — repo quirk
- this repo's devDependencies include `rhachet`, `declastruct-aws`, `@aws-sdk/*`: a role-package tree few repos carry
- the practice allows exactly this: `lint/best-practice/.dpdmrc.yaml:10` — "a require cycle inside a third-party devDependency: allowed, one entry per package, each with a comment"

## D1b — practice bug (guidance gap) + adoption candidate
- the practice: `lint/best-practice/.dpdmrc.yaml:12-13` — "a require cycle inside a prod dependency: never … dispatch the fix upstream or replace the dependency"
- the gap: it names only the slow cures. it does not name the two that green a consumer today, both sanctioned by `rule.forbid.dpdm-exclude-change`:
  - a cycle-free release via `pnpm.overrides`, where one exists
  - a `pnpm patch` of the dep, with the upstream fix dispatched beside it
- so a consumer that reads only the practice concludes the check must stay red until upstream ships
- every ehmpathy repo on `wrapper-fns@1.1.7`, `@ehmpathy/as-command@1.0.5`, `with-bottleneck`, or `simple-on-disk-cache` carries both cycles, so each hits this on its next upgrade
- adoption candidate: `patches/bottleneck@2.19.5.patch` + the `helpful-errors@1.5.3 → 1.7.5` override, as the interim cure, until the pinners release
- upstream fixes for the pinners: dispatched in 3.1 (`wrapper-fns`, `as-command`, `with-bottleneck`, `rhachet-artifact`)

## D2 — repo quirk
- the hook behaved as designed: `husky/best-practice/.husky/check.secrets.sh:18` matches its `private key block` shape (a private-key header), and `:29` scans `--diff-filter=ACM`, so a renamed fixture reads as an add
- the keys were dead fixtures no test read. that is this repo's state, not a practice defect
- note for the practice: a repo whose fixtures hold real-shaped test keys has no escape but removal or a key minted at test time. that is the right default (`rule.forbid.real-identities-in-fixtures` spirit); no change proposed

## D3 — practice bug
- two practices floor `simple-on-disk-cache` at `1.8.1`:
  - `cache/best-practice/package.json:5` — `check.minVersion('1.8.1').ifInstalled()`, beside `with-simple-cache` at `:8` `minVersion('0.17.3')`
  - `config/best-practice/package.json` — `check.minVersion('1.8.1')`, no `.ifInstalled()`, so every repo on the `config` practice lands on 1.8.1
  - source: `gh search code --repo ehmpathy/declapract-typescript-ehmpathy "minVersion('1.8.1')"`
- 1.8.1 changed the value contract: string-in, string-out. a wrapper that kept `with-simple-cache`'s no-op default deserializer now gets a JSON string back
- neither practice ships a migration or a `// @declapract:review:` marker: `gh search code --repo ehmpathy/declapract-typescript-ehmpathy deserialize` → 0 results
- every consumer with a `withSimpleCacheAsync` over `simple-on-disk-cache` and no explicit serde breaks silently at runtime; types do not catch it (`value: any`)
- the fix in the practice: on that floor bump, either mark each such wrapper for review, or ship the serde as part of the practice's cache template (the pattern `withSimpleCacheOnDisk` already embeds)

## D4 — repo quirk
- the race lives in this repo's own test (`getHeld` matched staged `.json.tmp.*` files); the skill and its write-whole contract are unchanged vs main

## E1 — repo quirk (test hermeticity)
- root cause: each suite reads a fact of the host it runs on, which a hermetic test would pin
  - `git.commit.push` / `.set` inherit `RHACHET_CLONE_SERIAL` from the clone session
  - `git.commit.sponsor` / `.uses` / `.operations` read the host's global git identity
  - `git.pull.real` needs `GIT_PULL_REAL_TARGET`; `git.pull.comment.real` holds a snapshot older than its skill's `ledgerFault` field
- not upgrade-caused: every skill dir is unchanged vs `origin/main`, and ci was green on all at main (pr #1222, run `43796229329`)
- no practice owns it; the cure is in-repo (scrub `RHACHET_CLONE_SERIAL` and point `HOME` / git config at a temp dir in each suite). outside this upgrade's scope; caught as a dream
