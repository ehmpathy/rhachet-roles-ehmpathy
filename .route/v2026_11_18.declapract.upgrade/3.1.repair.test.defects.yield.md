## D3: brain-cache suites read `undefined` fields
- **what**: `checkRetention`, `clusterKernels`, `pressViaPipeline` (integration, THOROUGH) fail with `input.compressed` / `result.clusterCount` / `input.text` undefined. each reads a field off the output of an on-disk-cached procedure (`compressViaBhrain`, `clusterKernels`).
- **how**: `git diff origin/main -- package.json` — `simple-on-disk-cache` 1.7.10 → 1.8.1 and `with-simple-cache` 0.16.2 → 0.17.3. no call site changed.
- **why**: 1.8.1 is string-in, string-out: `asValueFromEnvelope` returns `JSON.stringify(envelope.value)` on every read, and `with-simple-cache` re-reads after each set with a no-op default deserializer, so the caller receives the JSON string, whose fields are `undefined`. a side-by-side probe through `git.repo.test` proved it: the same wrapper returned `object` on 1.7.10 and `string` on 1.8.1, on the first call and the cached one.
- **fix**: each of the 12 `withSimpleCacheAsync` wrappers over `simple-on-disk-cache` now declares `serialize.value: JSON.stringify` + `deserialize.value: JSON.parse` — the pattern the new `withSimpleCacheOnDisk` embeds. prod: `extractKernels.ts`, `clusterKernels.ts`, `compress.via.bhrain.ts`; evals: `cluster.perfeval.ts`, `kernelize.perfeval.ts`, `runPerfevals.evals.ts` (3), `compress.via.bhrain.perfeval.integration.test.ts` (4). extant cache entries still read: their get yields a JSON string, which the deserializer parses.
- **verified**: the three suites, red before, pass after (39 passed). every kernel / compress / cluster / condense suite passes; `checkRetention` once judged 0 kernels retained (a live-brain verdict) and passed on rerun (15/15). types + format pass.

## D4: `userpromptsubmit.git-pull-watch` parses a half-written outbox entry
- **what**: `[case1][t0]` throws `SyntaxError: Unexpected end of JSON input`; t2 + t3 then fail as cascades (the wait in t0 never completed). red on 2 of 2 runs.
- **how**: `git diff origin/main -- <this file>` — import paths only (`__test_utils__` → `.test.utils`, relative → `@src`); the race it exposes is not new. what changed is how often a poll lands mid-write on this host; the read was always unsafe.
- **why**: `set_watch_file_atomic` stages each entry at `<entry>.json.tmp.<pid>.<rand>` in the same `outbox/` dir, then `mv`s it in. the test's `getHeld` read every name that contains `.clone=<serial>.`, which matches the staged temp file too, so a poll mid-write parses an empty file.
- **fix**: `getHeld` reads only names that also end in `.json` — whole entries.
- **verified**: 10/10 pass after; 6/10 failed before.
