# 🌙 dream: `sedreplace` silently matches naught when a pattern starts with `--`

**kind:** fix · **owner:** mechanic · **caught:** 2026-09-09

## .the cue that fired

a flag rename across a route — `--from me` → `--who @me` — reported **zero matches** on files that
provably contain the string.

```sh
$ rhx sedreplace --old '--from me' --new '--who @me' --glob '.behavior/…/*.md'
   └─ result: no files contain pattern          # 🔴 false

$ rhx sedreplace --old 'sponsor set' --new 'sponsor set' --glob '.behavior/…/*.md'
   ├─ files: 9
   └─ matches: 50                                # ✅ same glob, same files
```

⇒ the glob, the directory, and the untracked-file handling are all fine. **the leading `--` is the
whole difference.** `--include-ignored` changes it not at all.

## .the gap, precisely

🔴 **it fails SILENTLY, and that is the severity.** the skill reports `no files contain pattern` —
which is indistinguishable from a genuine zero-match — rather than *"pattern rejected"* or *"use
`--old @stdin`"*.

⇒ a driver reads "no matches", concludes the rename is unnecessary, and moves on with the rename
**not done**. ⚠️ worse in `--mode apply`: it exits 0 and changes no file, so a scripted rename
reports success.

⇒ this breaks `rule.forbid.failhide` — a real failure absorbed into a benign-looking result — and
`rule.require.errors-name-the-fix`, since the message names no fix.

## .the shape of the fix

the escape hatch already exists and is documented for a **different** hazard (shell-safety
heuristics on `{ } ( ) [ ]`):

```sh
printf '%s\0%s' '--from me' '--who @me' | rhx sedreplace --old @stdin --new @stdin --glob '…'
```

⇒ so the repair is **detection plus a pointer**, not new machinery:

1. in `sedreplace.sh`, after arg parse: if `$OLD_PATTERN` begins with `-`, and the underlying
   matcher would treat it as an option, pass it after a `--` terminator (`grep -- "$OLD_PATTERN"`,
   `sed` likewise). that alone likely fixes it outright.
2. if it cannot be fixed, **fail loud**: exit 2 with the `@stdin` one-liner above, per
   `rule.require.errors-name-the-fix`.
3. either way, add an `.integration.test.ts` case with a `--`-leading pattern — this is exactly
   `rule.require.clamp-edge-cases`: the clamp must go red under the un-fixed skill.

⚠️ **the likely root cause is an un-terminated `grep`/`sed` invocation** — the pattern is read as an
option and consumed. worth a check before anything more elaborate (`rule.require.solve-at-cause`).

## .why it is not done in this round

**SAFE: no. CLEAN: no.**

- **safe** — `sedreplace` is a repo-wide tool with a permission-guard surface and its own hooks
  (`pretooluse.forbid-sedreplace-special-chars.sh`). a change to its arg parse touches every caller.
- **clean** — it ripples into that skill's test suite and snapshots, none of which this route opened.

⇒ deferred deliberately, not overlooked. **no fulcrum is owed**: this is an unrelated tool defect
found in passing, not a design fork of the sponsor contract, so a row in that council would mislead.

⚠️ **and the rename it blocked was done by hand instead** — which is the right call anyway, since
several of those occurrences are historical sentences that must keep the old flag name.
