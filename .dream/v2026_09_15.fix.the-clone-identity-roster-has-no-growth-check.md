# 🌙 dream: the clone-identity backstop has no check against fleet growth

- **kind** = fix
- **owner** = ehmpathy/rhachet-roles-ehmpathy
- **caught** = 2026-09-15

## .the cue that fired

`enroll-impl-arch-defects` (i038, stone `5.1.execution.from_vision`) found that
`keyrack.operations.sh`'s `SEATURTLE_CLONE_NAME` / `_LOGIN` / `_EMAIL` hardcode exactly one
github account as "the clone's own identity" for the `is_identity_robot` backstop that catches
`--who @me` on a cloud grove. the same file already declares TWO other distinct bot identities
for different auth paths (`SEATURTLE_STANDARD_*`, `SEATURTLE_APP_BOT_*`) — proof the fleet
already juggles multiple bot accounts and is likely to grow more (a new org, a token rotation, a
second provisioning path).

## .the gap, precisely

if a second clone identity is ever provisioned, this backstop silently fails to recognize it:
`--who @me` there would bind the clone as its own sponsor — reproducing the exact defect this
feature exists to close — with no way to test for it in advance and no comment, lint rule, or CI
check that says "update this roster when a new identity is provisioned."

this is adjacent to but distinct from `F11`'s already-closed concern (which asked whether a
route existed at all, not whether the roster stays correct as the fleet grows).

## .the shape of the fix

one of:

- a comment at the roster's declaration site naming the invariant ("every clone identity that
  can run `git.commit.sponsor set` must be listed here — the `@me` backstop is only as complete
  as this list")
- an integration test that asserts the roster is non-empty and documents the update procedure
- (longer-term) a single source of truth for "known clone identities" shared with whatever
  system provisions a new clone, so the roster updates itself rather than a human remembering to

## .why it is not done in this round

**SAFE: yes — no code change is proposed, only a fixed instruction for the roster's next edit.**

**CLEAN: no.** `Q1` (this wish's own fulcrum council) already ruled no automated cloud dispatch
exists today, so no second clone identity is provisioned. a repair here would harden the code
against a fleet shape that does not yet exist, on a wish whose own scope decision (`F5`, `F3`)
was "defer everything gated on a dispatcher until one exists."

⇒ fulcrum `F12` ask 7 carries the record. **re-open trigger: the first clone identity beyond
the roster's current single entry is provisioned.**
