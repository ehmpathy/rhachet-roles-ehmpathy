# 🌙 dream: git.pull.watch paginated read truncates at 8 KiB under load

- kind: fix (flake)
- owner: ehmpathy/rhachet-roles-ehmpathy, mechanic role, `git.pull.watch`
- caught 2026-11-24

## .the cue that fired
a full local `rhx git.repo.test --what integration --mode apply --thorough` failed `git.pull.watch.events [case2c]` and `git.pull.watch.faults [case10]`. each suite alone passed (72/72, 32/32); CI on #1222 passed both.

## .the gap, precisely
the daemon log in both failures reads:

```
jq: parse error: Unfinished string at EOF at line 1, column 8192
github paginated read failed: repos/ehmpathy/surf-demo/.../comments?per_page=100
read of ehmpathy/surf-demo#1220 failed; cursors hold
```

the `--paginate` response reaches `jq` cut at exactly 8192 bytes, so the watch never primes and `waitForWatch` times out at 90s. 8192 is a pipe or stdio buffer size: the read is taken before the writer (the fake `gh` under test, or the real one) has flushed, and the race only loses under CPU load. it hits the paths with long pages (150 comments; a check-run list past one page).

## .the shape of the fix
find where the daemon captures the `gh api --paginate` output (a pipe, a `$(...)`, or a temp file read while still open) and read the whole stream to EOF before `jq` parses it; check the fake `gh` in `__test_utils__` for an unflushed or partial write too. clamp: a case that forces a large paginated body under a busy loop, red before, green after.

## .why it is not done in this round
the route's wish is push's `--help`; `git.pull.watch` is another skill, and a daemon read-path change is not safe to slip into a help-text pr.
