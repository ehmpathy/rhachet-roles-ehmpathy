# 🌙 dream: fold the stage meter into the commit meter

kind: fix · owner: rhachet-roles-ehmpathy · caught 2026-10-19

## .the cue that fired

the human asked, while F12 was ruled: "why do we need a stage meter of its own to begin with?"

## .the gap, precisely

- the commit grant already stages every file: `git.commit.set --unstaged include` runs `git add -A`
  (`git.commit.set.sh:1063`) with no stage check. so `stage: block` beside a commit grant guards
  naught; the crew stages and commits in one step
- stage only touches the local index — reversible, no remote effect; a commit still spends the
  commit grant
- the field came with #302 (`d950204`), next to `git.stage.add`; its message gives no why
- the one combination it serves — commit blocked, stage allowed (a crew stages for a human to
  commit) — survives a fold as a commit grant of `--quant 0`

## .the shape of the fix

- `git.stage.add` requires a live commit grant, spends no use (this subsumes F12's rebase rule)
- `git.commit.uses set --stage` refuses and names the replacement (same pattern as F8's `--push`)
- the `stage` field drops from `.meter/git.commit.uses.jsonc`; a read of an old file ignores it
- `allow` shorthand stops to write `stage`

## .status — adopted into the route, 2026-10-19

the human ruled the fold into `v2026_10_18.feat-split-release-uses`: "if you can commit, you can
stage. if you can rebase, you can stage. otherwise, no stage." F12 now records (d); the vision act
table holds one `git.stage.add` row on the commit meter. no separate work remains here.

one correction to `.the gap` above: under the ruled rule a commit grant of `--quant 0` does NOT
keep a stage-only use — quota 0 means no stage. the human confirmed that use is never wanted.
