route `v2026_10_07.fix-check-permissions-reads-settings-repo`, stone 5.3: the full integration run

## .the gap, precisely

`src/domain.roles/mechanic/skills/review/review.by.sh`:

- `:159` stores each rubric's exit code in `EXIT_CODES`; no later line reads it
- `:172-173` parse counts with `grep ... || echo 0`, so a rubric that printed no count tallies `0`.
  `contract.reviewer-output` says the opposite: an absent count is a `💥 malfunction`, never zero
- `:144-147` a rubric skill not found prints a note to stderr and `continue`s
- `:183-192` the header and `FINAL_EXIT` derive from the counts alone

so a rubric that crashes (412, timeout, absent creds) yields `0 blockers 0 nitpicks`, the
`cowabunga!` header, and exit 0. the header comment at `:21` promises `1=malfunction`; no path
emits it. this is `rule.forbid.failhide`.

observed live, `.log/role=mechanic/skill=git.repo.test/what=integration/2026-10-08T13-53-34Z.stderr.log:6247-6278`:
`review.by.integration.test.ts` `[case5]` passed `exit code is 0` and `shows cowabunga header`
while both rubrics rendered `✗` (each crashed on the 412). only its snapshot failed, on the
`✓`→`✗` glyph. the suite's explicit assertions bless the malfunction.

## .the shape of the fix

- a rubric whose exit is neither 0 nor 2, or whose output lacks BOTH numeric counts, is
  `💥 malfunction`: mark it per-rubric in the tree, set the header `bummer dude...`, `FINAL_EXIT=1`
- a rubric skill not found → `✋ ConstraintError`, exit 2 (the `--rubrics` arg named a rubric that
  does not exist)
- precedence: malfunction (1) vs blockers (2) when both occur — pick one, name both in the tree,
  and pin it in a test
- clamp: a stub rubric under a temp `ROLE_DIR` that exits 1 with no counts. assert exit 1 and the
  `bummer dude` header. revert the fix → it must go red (it reads `cowabunga!`, exit 0)

## .why it is not done in this round

- SAFE? yes in isolation, but it changes the exit contract of a skill that route guards and humans
  call; a guard that reads exit 0 today would start to halt.
- CLEAN? no. `review/` is outside the permission-hook subsystem this route touches, and the clamp
  needs a new stub-rubric harness. it rides its own change.
