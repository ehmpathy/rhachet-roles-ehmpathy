# 🌙 dream: cache the jest worker-count lookup in git.repo.test

- kind: followup
- owner: mechanic (rhachet-roles-ehmpathy)
- caught 2026-11-22

## .the cue that fired

the worker cap's `jest --showConfig` lookup was timed at ~1–2s per shared-box jest run (one-file unit scope: 0–1s with the lookup skipped, 2s with it on). the vision set ~1s as the bar to revisit.

## .the gap, precisely

`get_jest_derived_worker_count` in `git.repo.test.sh` spawns jest on every shared-box jest run to learn one number. a clone's tight scoped loop pays it each time.

## .the shape of the fix

- cache `globalConfig.maxWorkers` under `.log/role=mechanic/skill=git.repo.test/.cache/`
- key on: the config file path + a hash of its content + `nproc` (a `'50%'` config derives from the core count)
- an env-driven config (`maxWorkers: Number(process.env.X ?? 7)`) breaks a content-only key: either fold the env into the key, or skip the cache when the config text reads `process.env`
- a miss or bad entry falls back to the live lookup; never cache a failed lookup
- clamp: a test that proves a second run skips `--showConfig`, and that a config edit busts the cache

## .why it is not done in this round

the cache adds a second state store and a subtle key (env-driven configs). the wish asks for the cap; the exact lookup is correct today, and 1–2s is a cost, not a defect. the cache is a clean add-on with no ripple to the cap's contract.
