## .the gap, precisely

bash's `trap EXIT` does not chain — each call REPLACES the prior handler process-wide. today
this is safe only because every function explicitly `rm -f`s its own resource before it returns,
so by the time the next trap sets up, the prior one is already a no-op. that safety is an
unenforced property of CALL ORDER, not of the code's structure.

a future function that holds a temp resource at the same time as another (rather than strictly
one after the other) silently loses one cleanup on a signal-kill, and no test would catch it.
with four sites it is still past `rule.prefer.wet-over-dry`'s rule-of-3 threshold.

## .the shape of the fix

a shared helper in `operations.sh`, e.g. `with_temp_file` or a register-then-trap function that
composes rather than replaces:

```bash
# accumulates paths across calls, one trap for the whole process
register_temp_file_for_cleanup() {
  TEMP_FILES_TO_CLEAN+=("$1")
}
trap 'for f in "${TEMP_FILES_TO_CLEAN[@]:-}"; do rm -f "$f"; done' EXIT
```

each of the four call sites then calls `register_temp_file_for_cleanup "$err_file"` in place of
its own trap.

## .why it is not done in this round

**SAFE: yes — a pure extraction, no caller-visible change intended.**

**CLEAN: no.** each site traps a DIFFERENT local variable name (`err_file`, `file_temp`,
`GLOBAL_METER_FILE_TEMP`), so a shared helper needs either a rename at all four sites or an
indirection pattern (an array of paths, or `trap "rm -f \"\$$var_name\"" EXIT`) that is itself a
new pattern the reviewers have not yet seen. four files, mid-convergence on eleven review lanes,
is the wrong moment to introduce it.
