# 🌙 dream: org state mutations are an unlocked read-modify-write

- **kind**: fix
- **owner**: ehmpathy/rhachet-roles-ehmpathy
- **caught**: 2026-09-12

## .the cue that fired

`arch-hazards-behavior` r007 nitpick.1, at i024 of the `feat-require-commit-sponsor` drive:

> *"`set_org_state` / `del_org_state` read the whole org meter (`read_org_file`) and write it back
> through `write_org_file` […] There is no lock and no write-then-rename, and the actor guard admits
> any number of terminals — so two concurrent `allow`/`block` org operations (valid case under the
> tty guard) interleave as read-modify-write: both read the same base, both write, and the last
> writer silently drops the other's update."*

## .the gap, precisely

`git.commit.uses.org.sh`:

```bash
set_org_state() {
  updated=$(printf '%s' "$(read_org_file)" | jq --arg org "$org" --arg state "$state" '…')
  write_org_file "$updated"
}
```

⇒ read → edit → write, with no lock across the three. two terminals interleave as:

```
A: read {a: allowed}
B: read {a: allowed}
A: write {a: allowed, b: blocked}
B: write {a: allowed, c: allowed}     ← A's edit is gone
```

**the lost update is SILENT** — B's render reports `c: allowed`, which is true, and says naught
about the `b` that vanished.

## .what WAS repaired in that round

the **write** is now atomic — `write_org_file` builds a temp file inside the state dir and `mv`s it
into place, so no reader ever sees a truncated org meter. that closes the **torn READ**.

🔴 **it does not close the lost UPDATE.** those are two different hazards on one function, and the
atomic write is the smaller of the two.

## .the shape of the fix

a lock around the whole read-modify-write, held by every mutator:

```bash
with_org_lock() {
  local lockfile="${ORG_METER_FILE}.lock"
  exec 9>"$lockfile"
  flock 9
  "$@"
  exec 9>&-
}
```

then `set_org_state` and `del_org_state` run under it.

⚠️ **`flock` is not POSIX and is absent on macos by default.** so the fix owes a portability
decision first: `flock` where present with a documented degradation, or a portable
`mkdir`-as-mutex (atomic on every filesystem) with a stale-lock timeout. ⇒ that choice, not the
lock itself, is the expensive half.

**the clamp**: two concurrent `allow` calls on DIFFERENT orgs, both spawned before either returns;
assert both keys survive. it goes red today.

## .why it is not done in this round

**SAFE ✅ · CLEAN 🔴 — and it fails CLEAN on portability, not on ripple.**

the lock primitive has to work on every host this repo's tests run on, and `flock`'s absence on
macos makes that a real decision with a real alternative. ⇒ a lock chosen mid-stride, inside a wish
about commit sponsors, is a cross-cut concurrency primitive picked by whoever happened to be in the
file.

⚠️ **and the same hazard sits on THREE more meters** — the local `git.commit.uses.jsonc`, the global
blocker, and the sponsor state each carry the same unlocked shape. a lock that lands on the org
meter alone would be the first of four, and the other three would then read as "not yet done"
rather than as "never needed". ⇒ the right scope is the family, which this wish never opened.

🟡 **the practical severity is low today**: every mutator is tty-gated, so the two writers must be
two humans at two terminals inside the same second. that is what keeps it a nitpick rather than a
blocker — never the size of the outcome.
