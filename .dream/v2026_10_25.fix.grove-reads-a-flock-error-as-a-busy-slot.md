# 🌙 dream: the grove reads a flock error as a busy slot

kind: fix · owner: ehmpathy/mechanic · caught 2026-10-25

## .the cue that fired

self review role-standards-coverage on the grove (route `v2026_10_25.fix-repo-test-grove-suite-bound`)
asked which failure of `flock -n 9` the claim cannot tell apart.

## .the gap, precisely

`set_grove_claim_once` (`git.repo.test.grove.operations.sh`) treats any nonzero `flock -n 9`
as "held by another run". a lock call that fails for another cause — a pool dir on a filesystem
with no `flock` support (some NFS mounts via `GIT_REPO_TEST_SLOTS_DIR`), a bad descriptor — makes
every slot read held, so the run waits forever with `?` holders and no cause named.

## .the shape of the fix

`flock -n -E 75 9 || rc=$?` — util-linux `-E` sets the exit code for a conflict alone. rc 75 →
busy, try the next slot. any other nonzero → `💥 MalfunctionError: grove slot lock failed`, the
file, and the rc; exit 1. clamp: a slot file on a mount (or an fd) where `flock` errors.

## .why it is not done in this round

SAFE yes, CLEAN unsure: `-E` is util-linux (≥2.25). the brew `flock` on macOS (discoteq) may not
take it, and F4 / F9 keep mac hosts in scope; an unknown flag there would fail every bounded run.
the probe needs a mac. the default pool sits on tmpfs `/run/lock`, where `flock` always works.
