# 🌙 dream: a permission denial can be declared and never enforced

**kind:** fix · **owner:** mechanic · **caught:** 2026-09-10

## .the cue that fired

a coverage self-review walked invariant 2 — *"only a human mutates the sponsor"* — and checked the
denial **where it is enforced** rather than where it is declared:

```
src/domain.roles/mechanic/inits/init.claude.permissions.jsonc   ← 8 sponsor deny entries ✅
dist/domain.roles/mechanic/inits/init.claude.permissions.jsonc  ← 8 sponsor deny entries ✅
.claude/settings.json                                           ← 🔴 ZERO
```

⇒ the denial existed in the source, survived the build, and **was absent from the one file the
engine reads.** the guard was decorative in the very repo that declares it.

🔴 **`./node_modules/.bin/rhachet roles boot --repo ehmpathy --role mechanic` did NOT close the
gap.** the boot ran clean and `settings.json` still lacked the entries. the file had to be edited
by hand.

## .the gap, precisely

`.claude/settings.json` is **tracked** (`git ls-files` confirms), and repo history shows it ships in
the same commit as a permissions change (`29af51d` touches both). so it is a maintained mirror of
`init.claude.permissions.jsonc` — with **no mechanism that keeps the two in step and no check that
reports a drift.**

the two failure modes it permits:

| drift | what a reader believes | what happens |
|---|---|---|
| a **deny** in the source, absent from settings | the act is forbidden | 🔴 the act is **permitted** |
| an **allow** in the source, absent from settings | the act is paved | the act prompts, and a delegation stalls |

⚠️ **the first is the dangerous one, and it is silent in both directions.** the author reads their
own `permissions.jsonc` and sees the rule. the engine reads `settings.json` and does not. no test
fails, no gate reddens, no log line mentions it.

### .why it survives

the extant entries are all **correct**, which is what makes the gap invisible:

```
settings.json holds: git.commit.uses set / allow / --global / --org, git.commit.bind set / del,
                     Write(.meter/*), Edit(.meter/*)  … every one current
```

⇒ so a reader who spot-checks *"is settings.json maintained?"* sees a file in perfect sync and
concludes the propagation works. **it does — for every rule added before the last hand-edit.** the
mirror is accurate about the past and silent about the present.

🟡 and the incentive runs the wrong way: an author who adds a **deny** never notices the omission,
because the omission's symptom is *"my command works"*.

## .the shape of the fix

three candidates, cheapest first:

1. **a gate** — a test that reads both files and asserts the source's `deny`/`allow` sets are
   subsets of `settings.json`. it catches every future drift and needs no boot change.
   ⇒ ⚠️ **watch the sort:** `settings.json` is alphabetised and the source is grouped by concern,
   so compare as **sets**, never as ordered lists.
2. **a boot that writes it** — find why `roles boot` leaves the file untouched, and make it the
   generator. ⇒ this is the root-cause repair, and it removes the mirror entirely.
3. **a warn on session start** — the `sessionstart.notify-permissions` hook already reads both
   worlds; a drift line there costs one comparison.

⇒ **1 and 2 are not alternatives.** the gate is the clamp; the boot is the cause. a repo that fixes
only the boot has no guard against the next mechanism that bypasses it.

## .why it is not done in this round

**SAFE: no. CLEAN: no.**

- **safe** — it edits the permission propagation path for every role in the repo. a gate that
  compares the two files wrongly would either block every build or pass every drift, and both are
  worse than the extant silence
- **clean** — the root-cause repair (candidate 2) means a read of the `roles boot` flow in the
  `rhachet` package, which is a **different repo**. that is a reseed, not a ride-along

⇒ the sponsor's own entries **were** repaired by hand in this round, because that half is safe and
clean and the invariant it carries is this wish's second one. what is deferred is the **mechanism**
that would have caught it.

## .the lesson worth more than the fix

🎯 **check a guard where it is ENFORCED, never where it is declared.**

the source file is the author's intent. the engine's file is the behavior. this drive has now found
the same shape three times — a snapshot that vouched for a defect, a checkbox that vouched for a
pass, and now a denylist that vouched for a guard.

⇒ **all three are artifacts that report on themselves**, and the check that catches each is the
same: go one hop downstream and read what actually consumes it.
