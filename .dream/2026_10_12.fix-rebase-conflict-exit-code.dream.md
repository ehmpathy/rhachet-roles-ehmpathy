# 🌙 dream: git.branch.rebase exits 1 on a conflict, where the caller must act

kind = fix · owner = ehmpathy/rhachet-roles-ehmpathy mechanic · caught 2026-10-12

## .the cue that fired

the git.branch.cutover vision (`.behavior/v2026_10_11.feat-git-branch-cutover`, q11) chose exit `2`
for a conflict halt and cited the rebase peer for its conflict render. that peer exits `1`.

## .the gap, precisely

- `src/domain.roles/mechanic/skills/git.branch.rebase/git.branch.rebase.begin.sh` — the conflict
  block (`if is_rebase_in_progress; then ... exit 1`) exits `1`
- `git.branch.rebase.continue.sh` — the "conflicts must be settled" guard exits `1`
- `rule.require.exit-code-semantics`: `2` = constraint (the caller must fix it), `1` =
  malfunction. a conflict to settle is a constraint
- the same files also open errors with `hold up dude...` and no `✋ ConstraintError:` qualifier
  (`rule.require.qualified-error-headers`)

## .the shape of the fix

- conflict halt and unsettled-continue → `exit 2`, header `✋ ConstraintError: ...`
- every guard that names a caller fix (no quota, no push permission, dirty tree, on main) → `exit 2`
- keep `exit 1` only for a failed fetch / unexpected git failure
- update the snapshots and any test that asserts exit `1` on these paths

## .why it is not done in this round

safe, but not clean: it changes the exit contract of a released skill with its own tests and
snapshots, outside the cutover diff. it rides its own `fix(rebase)` change.
