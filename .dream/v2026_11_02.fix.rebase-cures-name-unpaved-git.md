# 🌙 dream: pave the git cures the rebase refusals name

kind: fix · owner: ehmpathy/rhachet-roles-ehmpathy (`src/domain.roles/mechanic/inits/init.claude.permissions.jsonc`, or a new rhx verb) · caught 2026-11-02

## .the cue that fired
the has-consistent-mechanisms self review ran `rhx permissions.get --for` on each cure the new rebase output prints. two came back `not pre-approved`, `no paved path fits this part`.

## .the gap, precisely
- `git checkout HEAD -- <path>`: the "take main's" cure when main also changed a held path (`print_aside_report`)
- `git restore --staged <path>`: the "unstage them" cure in begin's staged-content refusal

a clone that follows either cure meets a permission prompt, which pulls in a human. the paved stand-in for the first (`git show HEAD:<path> | rhx teesafe --into <path> --idem upsert`) is not equivalent: it writes a regular file, so it turns a symlink (the ambient `settings.of.grove.json`, the very path this skill exists for) into a file.

## .the shape of the fix
either
- allowlist path-scoped forms: `git checkout HEAD -- ` and `git restore --staged ` (each restores tracked content from HEAD or the index; neither touches history), with a `.why` note in the permissions jsonc; or
- a paved verb that restores one path from HEAD link-safe, e.g. `rhx git.path.restore --from HEAD --path <p>` / `--staged`, and point the cures at it

then update the two cure lines and their snapshots.

## .why it is not done in this round
an allowlist entry for a command that discards an edit is a policy call for the human, and a new verb is a new skill. both sit outside this wish. the raw git cures are correct as written; they cost one prompt, not a wrong result.
