# 🌙 dream: the brain suites must not race each other under a full-repo run

- **kind**: repair
- **owner**: `ehmpathy/rhachet-roles-ehmpathy`
- **caught**: 2026-09-24

## .the cue that fired

a full-repo `--thorough` integration run turned three suites red, each with one shape: a
`withTimeout` expiry, then a cascade of `useThen: tried to access value before test ran` in every
later step. one timeout yields many reds, so ~20 red steps are 3 defects.

## .the gap, precisely

| suite | under the 87-suite run | alone | per-call budget |
|-------|------------------------|-------|-----------------|
| `pressViaPipeline` | 83.6s — red | 84s, 21 passed | 60000 ms |
| `checkRetention` | 97.1s — red | 32s, 15 passed | — |
| `imagineIsContentAdmissible` | 442.1s — red | not measured | 30000 ms |

`checkRetention` inflates ~3× under load. the suites fail because a dozen brain-call suites run at
once and each call crosses its budget. `pressViaPipeline` already sits near its edge alone.

not established:

- `imagineIsContentAdmissible` has no solo control; it is classed by its error shape. it also carries
  `withRetry`, so its inflation may compound.
- contention is sufficient to explain the reds. quota is not excluded; both surface as a timeout.

## .the naive fix is wrong

the timeouts live in production operations — `extractKernels.ts:167,482,596`,
`imagineIsContentAdmissible.ts`. to raise them loosens how long a real caller waits, to suit the test
runner's concurrency. it also hides the contention until a slower model crosses the new number.

## .the shape of the fix

1. bound brain-suite concurrency — a small `--maxWorkers`, or a serial band.
2. leave every `withTimeout` in `src/domain.operations/` as is. a wrong prod budget is its own change.
3. clamp: a full-repo run greens all three; a control proves the band did not disable them.
4. separately: one `useThen` failure that surfaces as N reds misleads triage. a `test-fns` point.

## .why it is not done in this round

- **SAFE?** no. it changes the execution model of every integration run.
- **CLEAN?** no. it touches the runner and jest config, which share no line with `grepsafe`.
