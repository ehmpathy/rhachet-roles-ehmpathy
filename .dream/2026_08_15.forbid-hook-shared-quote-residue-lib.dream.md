dream = harden the forbid hook with a shared quote-residue lib

## .what

extract the both-quote-aware residue parser (`compute_active_residue`, proven in
`permissionrequest.decide-permissions.sh`) into a shared `_lib.shell-quote-residue.sh`,
source it in both `pretooluse.forbid-suspicious-shell-syntax.sh` and the decider, and
retrofit the forbid hook's `appears_executable()` to use it.

## .why

the forbid hook's `appears_executable()` is single-quote-only. an earlier unpaired `'`
(e.g. `rhx foo --arg "it's a test" $(rm -rf ~)`) throws off its parity, so the `$(` scan is
skipped and the hook fails to `exit 2`. the command then reaches the `PermissionRequest`
decider, which correctly lifts it (the auto-approve invariant holds — never rubber-stamped),
but defense-in-depth degrades from hard-block to human-prompt. one shared lib closes this
divergence and absorbs the `find_claude_dir` dedup in the same decompose-for-recompose move.

## .why deferred (not done in the decide-permissions behavior)

- the forbid hook predates that wish and guards EVERY bash command repo-wide.
- a parser rewrite on shared security infra needs its own redteam suite (over-block AND
  under-block classes) and its own review pass — not a rider on the decider's review.
- the decider is provably safe against this class today; the gap is a defense-in-depth
  downgrade, not an auto-approve hole. so it is real but not urgent.

## .the scope

1. `_lib.shell-quote-residue.sh` — the residue parser + balance report, one home
2. retrofit `appears_executable()` to scan the residue (both quote kinds + escapes)
3. a redteam suite for the forbid hook: apostrophe-parity `$(`/backtick bypass class,
   plus the over-block guard (quoted `$(` stays inert)
4. absorb the `find_claude_dir` duplication across the hook family in the same pass
5. **(higher priority — over-approve risk, not merely structural)** a shared "safe rhx"
   source of truth: `.claude/settings.json`'s `permissions.deny` escalation families and the
   decider's own hardcoded privilege-escalation denylist (`is_dangerous_rhx_subcommand`) have
   no shared definition today. **the drift can over-approve** — this is the central
   correction: `is_clean_rhx_call` trusts ANY `rhx` / `npx rhachet` lead by default, so a
   FUTURE escalation family added to `settings.deny` but NOT mirrored into the decider's
   hardcoded `case` patterns, IF it reaches the seam (suspicious-classified), reads as a clean
   rhx call and is **auto-approved**. the failure mode is exactly over-approve — the opposite
   of the earlier "safe-directioned" claim, which was wrong. the `case5` drift-clamp in
   `permissionrequest.compose.integration.test.ts` catches this only for the current
   `git.commit.uses`/`bind` shape; a structurally different family slips it. a shared manifest
   sourced by both settings and the decider (with a clamp that reads EVERY rhx/npx-rhachet
   mutation deny entry) is the real fix. caught by peer review r010 (i008 nitpick), corrected
   by r011 (i010).
