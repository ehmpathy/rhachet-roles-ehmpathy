# 🌙 dream: a real positive visibility read, once ci holds a github test token

kind = followup · owner = mechanic (test) + a human (the secret) · caught 2026-11-18

## .the cue that fired
5.3 peer review (ergo-contract-snapshots, mech-external-contracts, ergo-acceptance-journey-coverage) asked for a real integration test of the github visibility read that gates pr text into a public repo.

## .the gap, precisely
`external.contracts.integration.test.ts` [case4] runs both real readers (`set_repo_visibility`, `gh api repos/<o>/<n> --jq .visibility`; `set_pr_repo_visibility`, `gh repo view --json nameWithOwner,visibility`) through the real gh, with no credential and with a revoked token: both read `unreadable`, so the gate holds. the POSITIVE read, a real answer of `public` parsed by each reader, has no test: github answers visibility only to a credential, and ci holds none for tests. the last ci run's keyrack firewall shows `EHMPATHY_SEATURTLE_GITHUB_TOKEN status: absent`.

## .the shape of the fix
1. a human grants the test job a read credential, by either route:
   - add `EHMPATHY_SEATURTLE_GITHUB_TOKEN` (read scope suffices) as a repo secret, so the env-test firewall grants it
   - or pass the run's own `GITHUB_TOKEN` into `test-integration` in `.github/workflows/.test.yml` (it holds none today); it reads a public repo's visibility with no new secret
2. add `[case4][t2]`: with that token, both readers read `ehmpathy/rhachet-roles-ehmpathy` as `public`, cause empty, and the push reader names the slug. absent token = ConstraintError with the unlock hint, never a skip
3. optional: a private repo the token reads, to pin `private`

## .why it is not done in this round
the credential is a human's to grant. a test that needs it would turn ci red on every run until the secret exists. the rule's floor, a real test with the lack-of-creds case, holds now; the positive shape was proven by hand in the 5.3 live walk (both readers returned `(public)` for this repo under a gh login).
