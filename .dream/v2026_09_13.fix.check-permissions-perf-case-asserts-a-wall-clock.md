# 🌙 dream: a perf case asserts a wall clock, so it flakes exactly when the box is busy

- **kind** = fix
- **owner** = ehmpathy/rhachet-roles-ehmpathy
- **caught** = 2026-09-13

## .the cue that fired

`pretooluse.check-permissions.integration.test.ts` failed at `[case23] performance with 500 rules ›
[t0] hook completes within 3 seconds`.

⚠️ **it had been GREEN in a `--thorough` run 40 minutes earlier**, on the same commit, on the same
box. what differed was load: that run finished in **753s**, this one in **1346s**, because two of my
own runs raced.

⇒ **the cue was the delta, never the failure.** one red tells you naught about a timed test; two runs
of the same commit at different loads tell you the whole story.

## .the gap, precisely

the case asserts a **duration**:

```
then: disallowed command blocks in under 3s with 500 rules
```

a duration assertion measures the box, not the code. it holds a fixed budget against a quantity that
moves with every other process on the machine.

### 🔴 the failure mode is the worst-shaped one there is

| | |
|---|---|
| when it passes | the box is idle — which is when nobody needs the guarantee |
| 🔴 when it fails | the box is loaded — which is **exactly** the condition the perf case exists to grade |

⇒ a red here is ambiguous by construction: it means *"the hook got slow"* **or** *"the box got
busy"*, and the test cannot say which. a test that cannot name its own cause trains a reader to
re-run it, and a test everyone re-runs guards naught.

### checkable evidence

```
path://claude.hooks 2026-09-13  548s total → [case23] PASSED
--thorough          2026-09-12  753s total → [case23] PASSED
path://claude.hooks 2026-09-13 1346s total → [case23] FAILED
```

same commit, same box, opposite verdicts — and **monotone in total time**, with the flip somewhere
between 753s and 1346s. the third run was added 2026-09-13 at peer round 13.

⚠️ **n=2 could not tell a correlation from a coincidence; n=3 can.** two points make any pair of
verdicts look ordered, because two points always are. the third is what makes the order evidence.

🔴 **and the control is the sharper half**: this drive's own exec-tally clamp returned the **identical
count on all three runs**. so the environment moved enough to flip a verdict, and the discrete-event
instrument beside it did not move at all. ⇒ the difference is the unit, never the rigor of the case.

and:

```
git diff --stat origin/main...HEAD -- …check-permissions…   → empty
git status --short                  -- …check-permissions…  → empty
```

⇒ byte-identical to `main`, committed and in the tree alike. the defect predates this branch.

## .the shape of the fix

count **discrete events**, never elapsed time.

the fork-budget clamp in `pretooluse.forbid-terms.forkbudget.integration.test.ts` is the worked
example: it grades *"how many processes does this hook exec?"* via a PATH shim that tallies each
invocation. that number is **identical on an idle box and a loaded one**, so a red means the code
changed and naught else.

| | this case today | the shape that holds |
|---|---|---|
| measures | seconds of wall clock | execs, or rule comparisons, or syscalls |
| moves with load | 🔴 yes | no |
| a red means | "slow **or** busy" | "the code changed" |

⇒ for a 500-rule scan the natural invariant is **complexity, never latency**: assert the rule walk
stays O(n) — e.g. that 500 rules cost a bounded multiple of what 50 rules cost, measured in
comparisons — or tally the execs the way the fork budget does.

⚠️ **if a latency bound is genuinely wanted**, it belongs in a benchmark that is reported and never
a gate, so a busy box degrades a number rather than a build.

## .why it is not done in this round

| question | answer |
|---|---|
| **SAFE?** | ✅ yes — test-only, zero production behavior |
| **CLEAN?** | 🔴 **no.** `check-permissions` is one of the five hooks the wish's boundary fences off, and the fix is a re-design of what the case measures, never a threshold bump |

⇒ the wish says plainly: *"do not touch the other PreToolUse hooks unless a shared-cost fix genuinely
lands there too."* this is not a shared-cost fix; it is an unrelated flaky test in a hook next door.
⚠️ and the cheap move that beckons — raise 3s to 10s — **is the defect, restated with a larger
constant.** it fails later on a busier box and teaches the next author that the bound is negotiable.

## .the note worth a keep beyond the fix

🔴 **this is first-hand evidence for a claim the fork-storm drive made about its own instrument**,
and could not otherwise prove:

> *"a cost test feels wrong. tests assert behavior; a fork budget asserts a bill. it works only
> because we count **discrete events** rather than elapsed time. count time and it flakes on a busy
> grove — the exact condition the wish exists for."*

⇒ that was written as a design argument. **it is now a measurement**: the drive's own exec-tally
clamp stayed green across a 753s run and a 1346s run of the same commit, while the wall-clock case
in the next file over went red on the second.

⚠️ the transferable half: **a flaky test is usually reported as a test-quality problem, and this
class is a measurement problem.** the case is well-written, well-named, and asserts the right
intent — it simply picked a unit that the environment owns.
