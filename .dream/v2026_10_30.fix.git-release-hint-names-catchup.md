# 🌙 dream: git.release hints catchup, not rebase, for a pushed branch

- kind: fix
- owner: mechanic (git.release, git.branch.rebase)
- caught 2026-10-30

## .the cue that fired

peer review i005 r010 of route `v2026_10_27.feat-git-branch-merge`: `git.release --watch` on a
CONFLICTING pr still prints `hint: rhx git.branch.rebase begin`, the path that led #1021 into the
force-push wall.

## .the gap, precisely

- `git.release._.emit_transport_watch.sh:198`, `git.release/output.sh:182`, `git.release.spec.md:223`
  name rebase for "needs rebase now, has conflicts"
- `commands.alternatives.jsonc:85` (the `git rebase` entry) names only rebase
- `git.branch.rebase.begin.sh:255` ends `ready to push → rhx git.commit.push`, a push that needs
  `--force-with-lease` once the branch was pushed
- the rule "catchup once pushed, rebase before" lives only in catchup's `--help`

## .the shape of the fix

1. the three git.release sites: hint `rhx git.branch.catchup begin` for a pushed branch
2. `commands.alternatives.jsonc`: add catchup beside rebase, with the pushed/unpushed rule
3. rebase success: when the branch has an upstream, say the push needs force, and name catchup
4. resnap the git.release and rebase snapshots

## .why it is not done in this round

it changes git.release output for every clone, outside the catchup verb; the call is the
commander's (fulcrum F22).
