# 🌙 dream: hooks-reachable reads the hook tree where rhachet ≥1.54 puts it

- kind: defect
- owner: ehmpathy/rhachet-roles-ehmpathy, `src/domain.roles/mechanic/getMechanicRole.hooks-reachable.integration.test.ts`
- caught 2026-11-22

## .the cue that fired

a full integration run in a worktree whose `rhachet` was bumped `1.51.0 → 1.54.0` (an uncommitted upgrade) failed two `[case1]` assertions: `mechanic hooks are read from MORE than one event key` (received 1) and `every lib a hook sources ships byte-identical beside it` (received `[]`).

## .the gap, precisely

`[case1]` reads `.claude/settings.of.repo.json` and expects role hooks under many event keys. `rhachet init` at 1.54 folds every hook into one dispatcher per event (`hooks.dispatch.sh .claude/hooks.dispatch.manifest <Event>`) and lists the role hooks in `.claude/hooks.dispatch.manifest`. so the settings file no longer names the role hooks, and the reach and lib checks find naught. on the committed tree (rhachet 1.51) the suite passes.

## .the shape of the fix

when the rhachet ≥1.54 upgrade lands: read the role hooks from `.claude/hooks.dispatch.manifest` when settings names the dispatcher, else from settings as today; keep every assertion (reach, byte-identical libs). clamp: run on both shapes.

## .why it is not done in this round

the rhachet upgrade is not part of this branch (fulcrum F6); on this branch's committed tree the suite is green. the fix belongs with the upgrade.
