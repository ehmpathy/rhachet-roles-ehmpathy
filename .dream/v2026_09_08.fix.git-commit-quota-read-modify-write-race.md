# 🌙 dream: guard the commit-quota meter against a concurrent read-modify-write

- **kind:** fix
- **owner:** ehmpathy / mechanic
- **caught:** 2026-09-08

## .the cue that fired

peer review r1 of `.behavior/v2026_09_08.feat-require-commit-sponsor/1.vision` raised a nitpick:
the experience decomposition walks `actor × act × identity × grove` and never a **concurrency**
axis, which `rule.require.dimensional-decomposition` names among the usual omissions.

the sponsor's own writers turned out benign — a human at a tty, one tree at a time. ⚠️ **but the
walk of the axis found a real race one concept over, in the quota meter the sponsor guard sits
inside.**

## .the gap, precisely

`git.commit.set.sh` reads the quota and later overwrites it, with no lock and no compare-and-swap:

```sh
# :511 — read
USES=$(jq -r '.uses' "$STATE_FILE")

#  … ~338 lines, and a `git push` network round-trip among them …

# :849 — unconditional overwrite
cat > "$STATE_FILE" << EOF
{ "uses": $NEW_USES, "push": "$PUSH_ALLOWED", "stage": "$STAGE_ALLOWED" }
EOF
```

⇒ **a read-modify-write whose window is ~338 lines and spans a network call.**

two concurrent `git.commit.set` runs on one tree:

| t | run A | run B | state |
|---|---|---|---|
| 1 | reads `uses: 2` | | `2` |
| 2 | | reads `uses: 2` | `2` |
| 3 | commits, pushes | commits, pushes | `2` |
| 4 | writes `uses: 1` | | `1` |
| 5 | | writes `uses: 1` | 🔴 `1` |

⇒ **two commits spent, one decrement.** the meter is the mechanism by which a human bounds how
much a clone may commit, so a race in it is a quota a clone can exceed — quietly, and with no
error on any path.

⚠️ **the same window covers `push`,** so the auto-revoke at `:868-870` (block push once uses
deplete) can also be lost.

## .how likely

low today — one mechanic per tree is the normal mode. ⚠️ **it rises with exactly the automated
dispatch that `F5` / `Q1` contemplates**, where several clones could share a tree, and it is
invisible when it fires.

## .the shape of the fix

- take an exclusive lock around the read-modify-write — `flock` on the state file for the
  duration, or a lockfile beside it with a trap-based release
- **or** decrement **first**, under a lock, and refund on failure — that narrows the window to two
  short critical sections rather than one long one wrapped around a push
- ⚠️ either way, the decrement must not straddle the `git push`. that is the expensive half of the
  window and it buys nothing to hold a lock across it
- a regression clamp per `rule.require.clamp-edge-cases`: two concurrent invocations against one
  temp-repo state file, which assert the meter lands at `0` rather than `1`. it must go **red**
  without the lock

## .why it is not done in this round

the **SAFE / CLEAN** test (`rule.always.fix-forward-under-scouts-honor`):

| question | answer |
|---|---|
| **safe?** | 🔴 **no.** it changes the write order of the meter that gates every commit in every repo that boots this role |
| **clean?** | 🔴 **no.** it lands in `git.commit.set.sh` plus a new concurrent integration test, and it ripples into the `git.commit.uses` snapshots |

⇒ and the round's own bound: this is a **vision** stone. it writes no code
(`rule.forbid.commits-the-route-did-not-ask-for` governs what the route asked for). a lock in a
production skill is not in the diff a vision opens.

⇒ **the sponsor design neither creates nor widens this window** — its guard sits at `:586`, inside
the extant window, and it adds no write. so the deferral carries no defect forward; it declines to
fix a neighbour's.
