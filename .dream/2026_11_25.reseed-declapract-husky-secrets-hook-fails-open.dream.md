# 🌙 dream: the husky secrets hook fails open on a grep error

- kind: reseed
- owner: ehmpathy/declapract-typescript-ehmpathy, practice `husky` (`.husky/check.secrets.sh`)
- caught 2026-11-25

## .the cue that fired
the 5.1 peer lanes of route `v2026_11_24.fix-crew-pr-edit-via-paved-verb` read the `.husky/check.secrets.sh` that `declapract apply` wrote into the worktree (declapract-typescript-ehmpathy 0.50.0), and flagged its scan.

## .the gap, precisely
- the hook runs `set -eu` (line 12) with no `pipefail`
- the scan (line 48): `line=$(printf '%s\n' "$content" | grep -nIE -e "$regex" | head -n 1 | cut -d: -f1)`
- grep exits 1 on no match and 2 on error: an invalid ERE in a regex row, or a read fault. without `pipefail` the pipeline status is `cut`'s 0, and the grep error writes an empty `line`. an empty `line` reads as "no match"
- so a grep error passes the commit, and a staged secret goes through with it. the gate fails open
- `grep -I` also skips content grep judges binary, so a secret inside a blob with a NUL byte is never scanned
- also seen: an empty regex row matches every line, or none, by grep flavor

## .the shape of the fix
- `set -euo pipefail`, or capture grep's status by hand: `rc=0; out=$(… | grep -nE -e "$regex") || rc=$?`
- branch on it: `0` = match (block), `1` = no match (pass), `≥2` = `💥 MalfunctionError: secrets scan failed` and exit 1, which fails the commit closed
- drop `-I`, or scan binary blobs on purpose and say so
- refuse an empty regex row at load, with `✋ ConstraintError`
- clamp: a test with an invalid ERE row and a staged fake secret; red (commit passes) before the fix, green (commit refused) after

## .why it is not done in this round
the hook is the declapract practice's output, not this repo's code: a local patch is overwritten by the next `declapract apply`. the fix belongs at its source repo.
