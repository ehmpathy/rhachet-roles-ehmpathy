# 🌙 dream: guardBorder acceptance reads an unlocked key as locked

- kind: fix
- owner: whoever holds `guardBorder.onWebfetch`, this repo
- caught 2026-11-22, on route `.behavior/v2026_11_21.feat-pull-thread-reply-watcher` (5.3 verification)

## .the cue that fired

a full local acceptance run failed 16 tests across the four `blackbox/guardBorder.onWebfetch*.acceptance.test.ts` suites, each `exitCode: 2` with `🔐 OPENROUTER_API_KEY locked — run: rhx keyrack unlock --owner ehmpath --env prep --key OPENROUTER_API_KEY`. after that exact unlock (`expires in: 540m`), a rerun failed the same 16 with the same line.

## .the gap, precisely

- the hook runs inside the suite's temp repo (`.temp/genTempDir.symlink/…`), and there the key reads locked even after the named unlock
- so the fix the error names does not cure it, which breaks `rule.require.errors-name-the-fix`
- this route touches no guardBorder file (`git diff --stat origin/main` over its paths is empty); ci runs these suites with its own secrets

## .the shape of the fix

1. find where the hook resolves keyrack: the temp repo's root, owner, or env, versus the unlock's
2. either the harness passes the unlocked session into the temp repo, or the hook names the unlock that reaches it
3. clamp: an acceptance run after the named unlock passes locally

## .why it is not done in this round

another feature's harness, outside this wish; a fix here would ripple into files this pr does not own.
