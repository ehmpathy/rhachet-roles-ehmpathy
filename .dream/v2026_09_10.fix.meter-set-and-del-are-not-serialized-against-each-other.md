# 🌙 dream: meter `set` and `del` are not serialized against each other

- **kind** = fix
- **owner** = `ehmpathy/rhachet-roles-ehmpathy`
- **caught** = 2026-09-10

## .the cue that fired

peer review `i004` `arch-hazards-behavior` nitpick.2, on `git.commit.sponsor.sh` `del`:

> *"If a human runs `del` while another human's `set` has already written its temp file (or
> between that set's write and its mv), the `rm` removes the state file and then the late `mv -f`
> re-materializes the sponsor — the clear succeeds in the render but the bind is back one instant
> later."*

the observation is correct. ⚠️ **the remedy the lane offered is not** — see below.

## .the gap, precisely

`set` and `del` are two processes with no mutual exclusion. the interleave that loses an update:

```
  set:  write $STATE_FILE.tmp.$$      …
  del:                                 rm -f $STATE_FILE   ⇒ renders "cleared"
  set:  mv -f $STATE_FILE.tmp.$$ $STATE_FILE               ⇒ the bind is back
```

⇒ `del` reports a clear that did not hold. for a **sponsor** that is the sharp case: a human
clears precisely because the bound name is wrong, and commits then continue to name it.

🔴 **and it is family-wide, not new here** — verified:

| file | line | shape |
|---|---|---|
| `git.commit.sponsor.sh` | 757 | `rm -f "$STATE_FILE"` |
| `git.commit.bind.sh` | 197-199 | `if [[ -f … ]]; then rm "$LEVEL_FILE"; fi` |
| `git.commit.uses.global.sh` | 125 | `rm -f "$GLOBAL_METER_FILE"` |

no mutex mechanism exists anywhere in `src/domain.roles/mechanic/skills` — checked.

## ⚠️ .the remedy the lane offered does NOT close it

> *"A cheap fix is to make `del` atomic too (rename the file to a tombstone then remove:
> `mv -f "$STATE_FILE" "$STATE_FILE.tmp.$$" && rm -f "$STATE_FILE.tmp.$$"`)"*

⇒ 🔴 **that is a no-op for this defect.** a `rm` is already atomic from a **reader's** point of
view, so the rename buys no atomicity a reader can observe. the race here is a **lost update
between two WRITERS**, and a rename-then-unlink interleaves with `set`'s `mv` exactly as an
unlink does.

⇒ the lane's own second clause is the real one: *"or gate both on the same advisory lock"*.

## .the shape of the fix

serialize every writer of a meter file, family-wide:

1. one `with_meter_lock <file> <cmd…>` in `git.commit.operations.sh` — the shared home the
   sponsor reader already established
2. `set` and `del` both run their mutation under it, in all three files above
3. 🔴 **a bounded wait and a curated timeout**, never an unbounded block. `flock -w 5`, or a
   `mkdir`-mutex with an age check
4. a clamp per file: two concurrent writers, assert last-write-wins is *reported* honestly

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`), and **SAFE is the one that
refuses it**:

| question | verdict |
|---|---|
| **SAFE?** | 🔴 **no, and the failure mode is the worst one available.** a mutex introduces a stale-lock state: a process killed mid-write leaves the lock held, and every later `set` then hangs or refuses. ⇒ that would **stop a human from a sponsor bind**, which is the single act this whole design rests on. a rare lost update traded for a reachable total outage |
| **CLEAN?** | 🔴 **no.** a mutex on `git.commit.sponsor` alone, while `bind` and `uses` stay unlocked, is the partial repair `arch-opport-decomposition` graded a design defect. the honest scope is three files |
| portability | `flock` is absent from a default macos install, so the mechanism itself needs a decision this round has no reason to make |

⇒ 🎯 **the scope line is the same one a reviewer already endorsed**: the atomic *write* was this
change's to get right, because the sponsor file is **new**. a *mutex across commands* is a
property of the meter family, and it is prior art.

⇒ the judgment to defer is itemized at fulcrum **F12**.
